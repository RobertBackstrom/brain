1. The Model — at a glance

BADASS staffing decomposes into five top-level groups, with cost rolling up via:

Total = Management + Marketing & Comms + Platform + Σ(active_projects × Customisation_Core_template_cost) + Shared_Services_scaled_to_concurrent_count + Sub_overflow

GroupWhat it isScaling
ManagementCEO, CCO, CFO/Finance, COO, Head of Eng, Chief of Staff, Legal, Team AssistantFixed
Marketing & CommsBrand/Marketing Manager, Marketing Assistant, PR Manager, eSports Community & Partner Manager (Adam)Fixed (own bucket — distinct from per-project marketing in Shared Services)
PlatformBadassXR core engineering, 1st-party game products, reusable infrastructure, shared CERTRelatively fixed; step-up per new project type / new platform supported
Customisation CorePer-project Core teams instantiated from one of 5 templates. Each active client project gets a dedicated Core.Linear: active_projects × template_cost; bigger projects scale via subcontractors added to the Core (not by adding more FTE).
Shared ServicesSpecialist roles pooled across all active projects. Demand-driven for art / UX / SFX / lighting; fixed-then-step-up for Account Manager / Customer Support / Backend Engineer.Demand-driven; sum of sub-50% allocations × concurrent count.

The 50% threshold rule

Roles allocated more than 50% on a single project sit in the Customisation Core team for that project. Roles at 50% or less are pulled from Shared Services. This is the cleanest way to keep the per-project Core lean without losing access to specialist talent.

Surplus hours

FTEs in Customisation Core are dedicated to their project but rarely at 100% load. Surplus hours flow upstream to Platform work and internal assignments. This means every "Customisation" FTE also contributes to Platform — blunting the optic that BADASS is a services shop. Important talking point for investors.

Concurrent projects

Each concurrent project gets a fully duplicated Core team — no role-sharing across instances of the same template. Client focus is the headline value-prop; one Customisation Team Lead per project, one set of engineers per project. Surplus capacity flows to Platform per the rule above.

Parking lot: we may want to introduce T-shirt-sized Core variants (small / medium / large per template) in a future iteration. Out of scope for v3.

8. Sub-Overflow Rules — hybrid per template

Default: Core engineering FTE-pure for lead roles; surge / specialty roles sub-eligible; all Shared Services roles sub-eligible by default.

Per-template sub-eligibility specifics will be locked when scenarios are built (post v3 sign-off). The structural commitment now is that scaling happens via subs, not by inflating Core FTE.
