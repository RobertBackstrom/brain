## 2026-06-29 — WhatsApp bridge "half-connected ready-stuck-false" wedge: plain restart, NO QR (db-086/db-117)
**Learned:** 2026-06-29 | **Project:** WhatsApp bridge (db-086) | **Category:** whatsapp, puppeteer, whatsapp-web.js, half-connected, restart, liveness-vs-readiness

**Scenario:** `whatsapp_status` returned `ready:false`, `authState:"connected"`, `statusProbe.actualState:"CONNECTED"`, `lastError:null`, `me` populated — but every op (`list_chats`/`search_chats`) returned `Bridge error 503: whatsapp client not ready`. `lastReadyAt` was ~5 days stale. Service was `active (running)` 4 days, Chromium children alive, port 4501 listening, `/health` `{ok:true, ready:false, watchdog:"healthy"}`. **NOT a zombie** (db-117/db-166 had dead Chromium) and **NOT a LOGOUT** (db-086).

**Root cause — the third distinct WA failure mode.** `bridge.log` showed a clean re-pair `ready` event, then nothing but repeating `change_state OPENING→PAIRING→CONNECTED` cycles every ~1-3h, and the cycling itself **stopped logging 2+ days before**. whatsapp-web.js fired `change_state:CONNECTED` on reconnects but never re-emitted the `ready` event after one cycle, so the bridge's `ready` flag (gated on the `ready` event) stayed `false` forever. The db-117 status probe correctly reports `getState()==CONNECTED` (hence `authState:connected`, probe CONNECTED) but `ready` is event-driven, not probe-driven, so the two disagree indefinitely. The 503 comes from the bridge gating all ops on `state.ready`.

**Distinguishing the three WA failure modes (decision tree):**
- `ready:false` + Chromium children **dead** + RSS ~10M → **zombie** (db-117/166): restart; if start fails on SingletonLock, clear locks (db-086 steps).
- `bridge.log` last `"reason":"LOGOUT"` is **after** the last successful `ready` → **deauth** (db-086): re-pair, QR REQUIRED.
- `ready:false` but Chromium **alive** + probe `CONNECTED` + last log line is a stale `change_state:CONNECTED` with no following `ready`/`disconnected`, and last LOGOUT predates the last `ready` → **half-connected wedge (this one)**: plain `systemctl --user restart`, NO QR.

**Fix (safe, ~5s, no QR):** `systemctl --user restart whatsapp-bridge.service`. Re-authed from intact LocalAuth in ~5s: `authenticated`→`ready`, `state.ready=true`, `authState:ready`, fresh `lastReadyAt`. Verified end-to-end: `whatsapp_status ready:true` + `whatsapp_list_chats` returned 345 live chats. Did NOT touch `.wwebjs_auth/`. Confirmed laptop change was a red herring — bridge is 100% VPS-side.

**Open gap (still db-167, backlog):** the watchdog reports `healthy` here because `getState()` returns CONNECTED — it only catches dead-Chromium, not this ready-stuck-false split. A real liveness check should assert `state.ready===true` (or that a known-disconnected→connected transition actually re-emitted `ready`) and `process.exit(1)` if `ready` has been false past a grace window despite probe CONNECTED. That converts this from a 5-day silent outage into a ~5-min self-heal. db-167 already exists for the dead-state watchdog gap; this is the same ticket's broader fix.

## 2026-06-29 — Password-gate a pitch page per-slug (no restart)
**Project:** Blue Scarab (bsc) — pitch.aurorapunks.com

Pitch pages are public by default but can be gated **per-slug** with HTTP Basic Auth via `assistant/pitch-auth.json` — a file kept OUTSIDE the served root, shaped `{ "<slug>": { "user": "...", "pass": "...", "realm": "..." } }`. `pitches-server.js` `loadAuth()` re-reads it on **every request**, so adding/editing a cred needs **no restart**; a slug absent from the map stays public. ## 2026-06-26 — Pleo Playwright read-layer (single-instance MFA discipline)
**Project:** AP P&L H1 reconciliation (apb-002 / db-238) | **Category:** integration, playwright, headless-mfa

**Pleo headless login works up to MFA** — verified the hardened `pleo-login.js` reaches the 6-digit SMS step as ONE clean process: cookies → "Login with email" → `input[name=email]` → Continue → `input[name=passcode]` → Enter → `input[name=code]` (SMS to phone ending 79, ~10 min expiry, "Resend"). Headless needs real UA + `--disable-blink-features=AutomationControlled` + `navigator.webdriver` spoof or the SPA hangs on a spinner.

**Root cause of the prior failure was process discipline, not the login.** Overlapping detached `node ... &` launches each fired a fresh SMS that invalidated earlier codes, and stale chromium held the `.pleo-profile` SingletonLock. Fix pattern (reusable for any flaky SMS-MFA scrape):
- **Single-instance guard:** `pgrep -af "<script>"` BUT filter to lines whose command (after stripping the leading PID) starts with `node` — otherwise the tmux/bash wrapper command lines (which contain the script path) self-match and the script refuses to start. Also exclude `process.pid` AND `process.ppid`. Back it with a pidfile (`process.kill(old,0)` liveness check, clear if stale, `unlink` on exit).
- **Stale lock cleanup:** on start, `rm` `SingletonLock`/`SingletonSocket`/`SingletonCookie` from the persistent profile — safe only because the guard already proved no live instance exists.
- **One MFA window, NO auto-resend:** auto-clicking "Resend" on expiry is the trap (new SMS invalidates the code the human is about to type). Wait on a single `/tmp/<x>-mfa-code.txt`, fed ONCE; on CODE_EXPIRED/CODE_INVALID, print "restart the script" rather than loop.
- **Distinguish outcomes from URL + body:** LOGGED_IN (url left /login), CODE_EXPIRED (/expired/i), CODE_INVALID (/invalid|incorrect|wrong/i). Screenshot after `.fill()` and after submit.

**Run method that guarantees one process:** `tmux new-session -d -s pleo 'cd ... && node pleo-login.js 2>&1 | tee /tmp/pleo-login.log'`, tail the log, `echo CODE > /tmp/pleo-mfa-code.txt` once, `tmux kill-session -t pleo` to stop. Detached tmux persists reliably where `node ... &` did not.

**Export script mirrors fortnox-sie-download.js:** separate `pleo-export.js` reuses `.pleo-profile`, never logs in, detects /login bounce → "re-run pleo-login.js". Selectors left as `TODO(live)` because login stalled at MFA during discovery so the export UI was never reached headless — also flagged the possibility that Pleo *emails* the export (→ switch to Gmail-attachment pull) rather than streaming a download.

## 2026-06-25 — Google Sheets batchUpdate API format: GridCoordinate field names (db-230)
**Learned:** 2026-06-25 | **Project:** Google Sheets formula-driven standard (db-230) | **Category:** sheets-api, batchupdate, formatting

**Symptom:** Created `assistant/gsheet-style.js` (formula detector + auto-formatter) but Google Sheets batchUpdate API rejects GridCoordinate field names. Both camelCase (`rowIndex`, `columnIndex`) and snake_case (`row_index`, `column_index`) return "Invalid JSON payload received. Unknown name" errors in the range object.

**What works:** The formula detection itself (via `includeGridData` + `userEnteredValue.formulaValue`) correctly identifies all formula cells in a sheet.

**What doesn't:** The batchUpdate request format for updateCells + GridCoordinate. Official docs show camelCase in proto format, but the REST endpoint rejects it. Attempted:
- Full camelCase: `{ updateCells: { range: { sheetId, rowIndex, columnIndex, ... } } }` → rejected
- Full snake_case: `{ update_cells: { range: { sheet_id, row_index, column_index, ... } } }` → rejected
- Mixed (snake_case outer, camelCase nested): Same rejection

**Hypothesis:** The REST/JSON protocol might use a different field structure than the proto definition, or there's a transformation layer not documented. The gRPC vs REST mismatch in Google APIs can cause this.

**Next steps:** (1) Check Google Sheets Node.js client library source to see how it structures batchUpdate requests, (2) Try `appendCells` or `updateCells` via the values API instead, (3) Check if there's a different endpoint or format for GridCoordinate in REST.

**Pattern for next time:** When Google APIs batchUpdate rejects field names despite matching proto docs, always check the official client library for the actual REST format — docs ≠ implementation.

## 2026-06-25 — linkedin-sd MCP cookie schema + Windows→VPS push pattern (db / LinkedIn restore)

**linkedin-sd MCP (stickerdaniel/linkedin-scraper-mcp@latest) cookie internals — reverse-engineered from source, not docs:**
- Source lives in the uv cache: `~/.cache/uv/archive-v0/*/linkedin_mcp_server/`. Cookie logic is in `core/browser.py` (`import_cookies`, `_BRIDGE_COOKIE_PRESETS`, `_normalize_cookie_domain`). `session_state.py`/`bootstrap.py` handle `source-state.json` (`login_generation` uuid) and the `invalid-state-*` marker dirs.
- `~/.linkedin-mcp/cookies.json` is a **JSON array** of cookie objects, each `{domain, expirationDate, httpOnly, name, path, sameSite, secure, value}` (Cookie-Editor / Playwright-ish export shape). The last-known-good invalid-state snapshot used exactly this; the MCP imported it fine.
- On import the MCP **filters**: keeps only cookies whose `domain` contains `linkedin.com` AND whose `name` is in the active preset. Default preset is `auth_minimal` = `{li_at, JSESSIONID, bcookie, bscookie, lidc}` (env `LINKEDIN_DEBUG_BRIDGE_COOKIE_SET=bridge_core` widens it). It **hard-fails if `li_at` is absent**. So a restore strictly needs only `li_at`; `JSESSIONID` helps write actions. Other bridge names are optional (absent = just not imported).
- `_normalize_cookie_domain` rewrites `.www.linkedin.com`/`www.linkedin.com` -> `.linkedin.com` on import, so the LinkedIn host used at export doesn't matter.
- Cookies go straight into Playwright `add_cookies`. Historical exports carried `expirationDate` (Cookie-Editor key, not Playwright's `expires`) plus extra fields and still worked -> patchright/the MCP tolerates them. Safest move: emit the exact shape of the last good snapshot rather than inventing a minimal Playwright object.
- **Restore = file-write, no login.** No headful browser needed. Write `cookies.json` (0600), move stale `invalid-state-*` aside, and a NEW Claude session re-reads it (stdio MCP spawns fresh per session — no daemon to restart). If it still 401s, the `li_at` itself is stale.
- Built `assistant/linkedin-restore-cookie.js`. **Secret-handling pattern worth reusing:** take the secret via `--<name>-file` or `--stdin` only (never a literal CLI arg -> would land in bash history), validate length/whitespace, write 0600 atomically (tmp+rename), and **never echo the value** — report only cookie NAMES and byte-lengths. Same shape as `assistant/scripts/slack-cred-set.sh`.

**Windows laptop -> VPS file transfer (Robert is on Windows, connects via VS Code Remote-SSH):**

**Scenario:** `whatsapp-bridge.service` went `inactive` after WhatsApp server-side session LOGOUT (`{"msg":"disconnected","reason":"LOGOUT"}` in bridge.log). **Key facts:**
- `LOGOUT` reason = WhatsApp actively deauthenticated the device (e.g. Robert removed it from Settings → Linked Devices, or WA's server-side session expired). Stored `LocalAuth` creds at `.wwebjs_auth/` are dead. **A fresh QR scan from Robert's phone is the only fix** — no code change can recover credentials after a LOGOUT.
- The SingletonLock contention is a **secondary** crash-loop artifact: every restart attempt creates a new Chromium instance, fails to get the lock, writes `state.json: init_failed`, and exits. This repeats until systemd's start-limit fires.
- `DevToolsActivePort` also needs removal — Chromium writes it on launch and won't overwrite it if one exists.
- The `.wwebjs_auth/` dir itself must NOT be deleted wholesale — it contains the session profile data that Chromium needs for fast boot. Only the 4 lock files need to go.

**Clean recovery steps (2-minute fix once you know the pattern):**
1. Kill any orphan chromium/bridge.js processes: `pkill -f 'wwebjs_auth' 2>/dev/null; pkill -f bridge.js 2>/dev/null` (idempotent if nothing running).
2. Remove Singleton locks: `rm -f .wwebjs_auth/session/SingletonLock .wwebjs_auth/session/SingletonSocket .wwebjs_auth/session/SingletonCookie .wwebjs_auth/session/DevToolsActivePort`
3. Reset systemd start-limit + start: `systemctl --user reset-failed whatsapp-bridge.service && systemctl --user start whatsapp-bridge.service`
4. Wait ~8s, check: `cat whatsapp/state.json` → `qrPresent: true` means it's waiting for scan.
5. Verify port: `curl -s http://127.0.0.1:4501/health` → `{"ok":true}`.
6. Tell Robert: scan `whatsapp/qr.png` via WhatsApp → Settings → Linked Devices → Link a Device.

**What NOT to do:** don't delete `.wwebjs_auth/` wholesale unless the Chromium profile itself is corrupt (rare). The session profile data makes subsequent boots faster; only the 4 lock files block restart.

**How to confirm LOGOUT vs other disconnect:** `grep '"reason"' bridge.log | tail -5` — `"LOGOUT"` = re-pair required; `"CONFLICT"` / connection drop = reinitialize without QR scan usually works.

**After QR scan:** bridge transitions `qr_pending → authenticated → ready`; QR files deleted automatically; `state.json.ready` flips to `true`. MCP shim resumes normally.

## 2026-06-19 — code.runatyr.games "logged out mid-session" = CF Access session-token expiry, fix is Session Duration (devops Q)
**Learned:** 2026-06-19 | **Project:** infra / Cloudflare Access | **Category:** cloudflare-access, session-duration, code-server, websocket, auth-timeout

Don't remove Access from this host — it's correctly gated; the lever is session length.

**Tooling wall:** the scoped `CLOUDFLARE_API_TOKEN` (`assistant/.env`, registry `cloudflare.api-token`) is DNS:Edit + Tunnel:Edit only — `GET /accounts/{acct}/access/apps` returns `10000 Authentication error`. So Access app/session config is **dashboard-only from the VPS today.** To make it API-managed, mint a token with **Account → Access: Apps and Policies: Edit** and register it.

**Diagnostic shortcut:** ambiguous code.runatyr.games disconnect → `journalctl --user -u cloudflared --since '10 min ago' | tail -20`; if connector is clean and the code-server process is up, it's Access expiry, just reload to re-auth. Don't restart anything.

**Learned:** 2026-06-08 | **Project:** opensign-deploy (OpenSign self-host) | **Category:** opensign-api / completion-bug / p12-signing / env-config / compose-interpolation | **Ticket:** db-046

## 2026-06-05 — OpenSign `placement:'sub'` profile for 3-signer K2C outsourcing subcontracts (k2c / db-046)

- **The 'sub' profile is NAME-DRIVEN, not order-driven.** Each signer's signature/date geometry is located by matching a distinctive token of the signer's *name* (the surname/last word) against name lines that also carry a role marker (`, Board Member|Director|CEO|Member`). Always assert `res.placement === 'sub'` after staging; `'last(fallback)'` means the names didn't match.
- **These contracts carry the SAME signature block TWICE** — once ending the Master Agreement, once ending Exhibit A (the true last page). `buildSubSignatureWidgets` places a signature+date on EVERY occurrence of each signer's name line across ALL pages, so both blocks get signed in one signing action. - **Two name-line layouts coexist and both are handled:** inline (`<Name>, <Role> ( <email> ) Date: ____` on one row, Date label at x≈365–423) and two-line (name line, then `Date: ____` ~24pt below at x≈72). Signature widget sits just ABOVE the name line (SIG 170×22, DATE 95×16, x over the underscores = `labelEnd-70`).

## 2026-06-05 — OpenSign placeholder GEOMETRY convention (derived from server image) + anchor-based field placement + voidDocument (opensign-deploy / db-046)
**Learned:** 2026-06-05 | **Project:** opensign-deploy (OpenSign self-host) | **Category:** opensign-api / placeholder-geometry / pdf-coordinates / corpbot-tooling / signature-block | **Ticket:** db-046

CorpBot staged a real NDA (doc `FmxryAgBzX`) via `opensign.js` and the signature+date fields rendered in the MIDDLE of page 1 over clause 1.1. **Root cause:** the original `_buildPlaceholder` hardcoded `pageNumber:1` and fixed `xPosition:80 / yPosition:600` for EVERY signer — never anchored to the doc, never targeted the last page. Fixed it with a fully-derived coordinate convention + text-anchor placement. **This is the high-value entry — the same geometry is needed for all 6 K2C subs and every future contract.**

- **OpenSign placeholder coordinate convention (verified from THREE code paths in the running client image `src/constant/Utils.js`, not guessed):**
  - **Origin = TOP-LEFT, units = RAW PDF POINTS.** `xPosition` = distance from left edge; `yPosition` = distance from the TOP of the page. (A4 = 596 × 842 pts; US-Letter = 612 × 792.)
  - **Display** (`components/pdf/Placeholder.jsx`): box rendered at CSS `left = xPosition * containerScale`, `top = yPosition * containerScale`, where `containerScale = renderedPageWidthPx / pdfOriginalPageWidthPts`. So stored coords are raw points; the viewer just scales to fit.
  - **Image-widget embed** (`embedWidgetsToDoc` → `getWidgetPosition`): scales coords by `pageRatio = pageWidth / vpWidth`, and **defaults `vpWidth = pageWidth` when the pos has no `vpWidth` → pageRatio = 1**. Then top→bottom flip: `drawY = pageHeight − (yPosition + Height)`. **KEY GOTCHA: do NOT set `vpWidth` on the pos** — leave it absent so pageRatio stays 1 and image coords are raw points (matching the text path). If you set vpWidth to anything other than the true page width, signatures shift but date text does not (they use different code paths) and they desync.
  - **Text-widget embed** (date/name/email/etc): drawn straight via `compensateRotation` with NO vpWidth scaling and a small `+6` y nudge. So text coords are ALWAYS raw points. Setting vpWidth would break only the image widgets relative to text — another reason to omit it.
  - `pageNumber` is **1-BASED**. `Width`/`Height` are the widget box size in points; defaults from `defaultWidthHeight(type)`: signature 150×60, date 100×20, name/text/email 150×19, checkbox 15×19, initials 50×50, image 70×70.
  - Date widget: set `options.response:'today'` — the server resolves `'today'` to the configured format at sign time (`changeDateToMomentFormat(validation.format)`). Don't bake an ISO date.

- **Anchor-based placement (the robust path, now implemented).** Use `pdfjs-dist` (already in `assistant/node_modules`, **v5 ESM-only — load via `await import('pdfjs-dist/legacy/build/pdf.mjs')` from CommonJS**). Per text item, `transform[4]` = x, `transform[5]` = y(bottom-left); convert to top-left with `yTop = viewport.height − transform[5]`. `it.width` gives label width (to offset the date field past a "Date:" label). For the AP NDA template the last-page signature block has: party 0 "For and on behalf of <Company>" → Name:/Title:/Date: lines; party 1 "Freelancer:" → underscore line + Name:/Title:/Date:. - **`opensign.js` API changes:** `createSignatureRequest` now takes `placement` (`'nda'` default = anchor to two-party signature block on last page; `'last'` = parameterized bottom-of-last-page fallback; `'manual'` = caller supplies `signerWidgets` [array per signer of `{pageNumber,type,xPosition,yPosition,Width,Height}`, raw points, top-left]). `'nda'` auto-falls back to `'last'` if anchors aren't found (returns `placement:'last(fallback)'` so you can tell). The `signPdf`/`PDF.js` doc query does `notEqualTo('IsDeclined',true)` AND `notEqualTo('IsArchive',true)`, so an archived doc is **un-signable** and hidden from the dashboard — without hard-deleting the row (which would orphan the audit trail). `--hard` does a true DELETE if ever needed. ## 2026-06-05 — Silent append-no-op bug: meeting notes archived but never logged (db-186)

**The bug:** `appendActivity` (server.js AND gmail-gemini-backlog.js) did `if (/\*\*Activity:\*\*/.test(body)) body.replace(/(\*\*Activity:\*\*\n)/, ...)`. ## 2026-06-05 — Inbox-zero method: triage unread, never blanket-archive it (db-186)

**Method to take an inbox to (near) zero safely:**
1. Archive noise via the sweep (triage-policy.json) + digest newsletters.
2. Archive read-AND-old mail (read + >30d = effectively handled).
3. LLM-triage the remaining UNREAD into ACTION / FYI / NOISE (`gmail-triage-unread.js`, Sonnet batched); archive FYI+NOISE, keep ACTION.

## 2026-06-05 — rag-indexer embedding insert is non-idempotent (db-186)

## 2026-06-03 — Discord bot permission audit technique + findings (db-190)

## 2026-06-02 — Locking a Discord channel @everyone-private locks the bot out too (no Administrator) (db-190)
**Learned:** 2026-06-02 | **Project:** Death Board / Discord (db-190) | **Category:** discord, permissions, ordering, self-lockout, gotcha

**Context:** Tasked to make `#board` (id `1511348246558019705`) in the AP guild (`616345869490454593`) private, keep the Death Board bot's access, then add member overwrites. Robert authorized it. The bot has guild MANAGE_CHANNELS + MANAGE_ROLES + VIEW + SEND but **NOT Administrator**; its "Death Board" role is at position 1.

**The trap (cost me the task):** I denied `@everyone` VIEW_CHANNEL first (`PUT /channels/{c}/permissions/{guildId}` type:0 deny `1024` → 204). The bot is itself a member of `@everyone` and its channel access was riding on the guild-default VIEW. The instant `@everyone` VIEW is denied, **the bot loses VIEW on that channel** and every channel-scoped write returns `50001 Missing Access` (403): can't add its own allow overwrite, can't add member overwrites, can't even DELETE the `@everyone` overwrite to undo. Guild-level MANAGE_CHANNELS does **not** bypass a channel-level VIEW deny — only **Administrator** (or being guild owner) does. I locked the bot out of the channel it was supposed to manage.

**Correct order (do this next time):**
1. **First** add the explicit allow overwrite for the bot user/role (VIEW+SEND+READ_HISTORY = `68608`) while it still has access.
2. **Then** deny `@everyone` VIEW. The bot keeps access via its explicit overwrite.
3. Then add member overwrites.
Better still: build the full `permission_overwrites` array and `PATCH /channels/{id}` it in **one** atomic call so there's never an intermediate state where the bot is excluded.

**Recovery once locked out:** the bot can't fix it (no Administrator). Only the **guild owner** (Robert, `346946099560579073` — confirmed `owner_id` == `DISCORD_OWNER_ID`; owners bypass ALL overwrites) can re-grant the bot in channel settings. Note guild-**scoped** reads still work while channel-locked: `GET /guilds/{id}/channels` shows the channel + its overwrites, and `GET /guilds/{id}/members/search?query=` resolves member IDs — that's how I still produced the member list to hand back.

**Two perms the AP bot lacks (flag, don't force):** `CREATE_INSTANT_INVITE` (false in role perms `397553298512`) → `POST /channels/.../invites` = `50013 Missing Permissions`; and no Administrator. For "lock + invite" tasks in this guild, either get Robert to do the owner clicks or have him grant the bot those perms first.

**Member-search caveat:** `/guilds/{id}/members/search` rate-limits fast (~5 quick queries → `429 retry_after ~6s`); space queries with `sleep 3`. URL-encode multi-word queries. Don't fabricate matches — of 6 intended members only 3 resolved confidently (Robert=owner, KM=`ultrakmag`/"KM (Behold.vc)", Mattias=`.wiking`); the rest had no real match and were reported as "needs to join."

## 2026-06-01 — Teams/Exchange Graph connectors now REQUIRE admin consent (MC1163922) — guest self-consent is dead (db-189)
**Learned:** 2026-06-01 | **Project:** Death Board (db-189) | **Category:** API setup / auth / feasibility

**The finding (feasibility gate for the Teams Graph connector):** A guest account CANNOT authorize a third-party Graph app to read a host tenant's Teams chats on its own. Microsoft message-center notice **MC1163922** (rolled out end of Oct 2025 for Graph, end of Nov 2025 for legacy EAS/EWS/IMAP/POP) changed the **default managed consent policy** so third-party apps reading Teams OR Exchange content require **admin consent** — end-user self-consent is no longer sufficient. Swept-in delegated scopes include `Chat.Read`, `Chat.ReadWrite`, `ChannelMessage.Read.All`, `OnlineMeetings.Read/.ReadWrite`, plus the whole `Mail.*`/`Calendars.*`/`EWS/EAS/IMAP/POP.AccessAsUser.All` family. The merill permissions reference now shows even `Chat.Read` as **AdminConsentRequired: Yes** (used to be No).

**Implication:** For ANY Graph connector that reads a *client's* tenant content as Robert-the-guest, the gate is an admin (Global Admin / Privileged Role Admin / Cloud App Admin) **in the client's tenant** granting consent — there is no scope combo that routes around it. The guest membership lets Robert *participate* in chats; it does not let an app read them on his behalf. Build plans for these must stage around that gate: produce a multi-tenant app + admin-consent URL, route it to the client admin, and only build the token capture + MCP after consent lands. The consent URL doubles as the empirical test (it bounces with `AADSTS90094 admin consent required` for a non-admin, confirming the verdict).

**Only theoretical non-admin path:** Resource-Specific Consent (RSC) — a packaged Teams *app* installed into a specific team/chat, granted by a team owner. Wrong shape for the OAuth-refresh-token MCP pattern, still needs tenant RSC/custom-app-upload enabled, chat-scoped RSC is limited. Don't pursue over a one-time admin consent.

**Consumer-Teams trap:** Graph's delegated chat API only sees **org-tenant** (Entra work/school) chats. Any conversation in a **consumer Teams** group chat (`teams.live.com/l/invite/...` links, vs org `teams.microsoft.com`) is invisible to Graph regardless of consent. Before promising coverage, confirm how much of the target comms is org-tenant vs consumer. ## 2026-06-01 — Shared Drive permission mechanics + cross-drive moves (gdrive scripting)

**Källa:** CZP/AP Drive reorg — consolidating all projects into the new `projects` Shared Drive
**Kategori:** tooling
**Taggar:** gdrive, shared_drive, permissions, inheritance, cross_drive_move, consolidation, oauth

Mechanics learned doing a multi-Shared-Drive consolidation via the Drive API (OAuth from `~/.claude/.gdrive-server-credentials.json` refreshed against `gcp-oauth.keys.json`, `supportsAllDrives=true` on every call):

- **A Shared-Drive child can't be more private than its parent.** Subfolders inherit the parent's (and the drive-membership) sharing, and you **cannot delete an inherited permission** (DELETE → 403). To truly privatise an item it must live *outside* the shared subtree. To remove an *elevated* direct grant while an inherited one remains, PATCH the permission's role down (e.g. commenter→reader) rather than DELETE.
- **Detect inherited vs direct:** `GET /files/<id>/permissions?fields=permissions(id,emailAddress,role,permissionDetails)` → each `permissionDetails[]` has `inherited` (bool) + `inheritedFrom` (parent id). Only `inherited:false` perms are removable on the item. A file's `driveId` being present ⇒ it's in a Shared Drive; member role `organizer`/`fileOrganizer` ⇒ Shared-Drive member (vs My Drive `owner`).
- **Moving between Shared Drives** (`PATCH /files/<id>?addParents=<destDriveId>&removeParents=<srcDriveId>&supportsAllDrives=true`): **direct** file/folder shares **travel** with the item; **drive-membership-based** access does **NOT** (moving out of a team drive into a Robert-only drive strips the team unless re-shared). **Doc/file IDs are stable** across moves, so existing links + per-doc shares survive.
- **Grant scoped access without drive membership:** direct-share a folder with a group (`POST /files/<id>/permissions {type:'group', role:'writer', emailAddress:'all@aurorapunks.com'}`). This grants the **subtree only**, not the whole drive — the way to keep a team's access to portfolio folders while CZP-confidential siblings in the same drive stay hidden. (Members of a Shared Drive see everything in it — you cannot hide a subfolder from a member, so confidential content and team-shared content can't coexist in one drive via membership.)
- **Silent share:** add `&sendNotificationEmail=false` so the recipient isn't emailed (e.g. when a separate cover letter is the intended first contact).
- **Consolidation shortcut:** move the **parent group folder** (1 op) instead of N children — all children + their external shares ride along. Renaming on collision (3 folders all named "Projects" → "AP Projects", etc.).
- **Upload→rename:** `gdrive-upload.js --convert --html` leaves the `.md` in the new Gdoc title; rename via `PATCH /files/<id> {name}`. Extract the new id with `grep -oE 'document/d/[A-Za-z0-9_-]+' | sed 's#document/d/##'` — `cut -d/ -f2` grabs the wrong field ("d").

**RAG note:** `wiki/` is a WATCHED root in `assistant/rag-config.js` (glob `**/*.md`) alongside skills/memory/agents/followups — new `.md` under `wiki/` is auto-indexed. Run `node assistant/rag-indexer.js --backfill` to index; it walks all roots but only embeds new/changed chunks (cheap). Run it from the project root (cwd matters — it resolves `assistant/` relative).

**How to apply:** before any cross-drive Drive reorg, check `driveId` + `permissionDetails` on the targets to predict what access survives the move; prefer parent-folder moves; re-share with groups directly to preserve team access; and flag any access-model conflict (team-shared portfolio vs confidential engagement folders) to Robert *before* moving — they can't share one Shared Drive.
