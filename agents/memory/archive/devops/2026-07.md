## db-256 Drive migration - Phase 5 PORTFOLIO consolidation: portfolio = holdings-at-root, and an empty second source (2026-07-15)

**Portfolio-drive structure differs from a company-unit drive: ONE FOLDER PER HOLDING at the drive ROOT, not the standard company template.** The Phase-2 create step had templated the Portfolio drive (`0AF1ubBnsLIXNUk9PVA`) with the same 6-folder standard (`_legals`/`_financials`/`Deliverables`/`Board_Governance`/`Meeting_Notes`/`_archive`). For a portfolio that template is meaningless - holdings are unrelated third parties, each is its own coherent subtree. Correct move: drop each holding folder-intact at the DRIVE ROOT alongside the (harmless) template folders; don't try to slot holdings into `_legals`/`_financials`. Left the template folders in place (no-delete rule) - a portfolio root with 5 empty template folders + N holding folders is the accepted end state. Script: `assistant/drive-phase5-portfolio-consolidate.js` (reuses the Phase-3/4 client: getToken, moveOne addParents/removeParents, listChildren, listPermissions).

**An "empty second source" is a real outcome - verify it two ways, don't force a merge.** The brief expected to dedup two "Portfolio Companies" folders (AP Admin + AP External `EXT Portfolio Companies` `12-r2AFJMwwl5qEno9ybBD5rYhk4lrbOs`). The EXT one turned out EMPTY. Confirmed BOTH live (`files.list '<folder>' in parents` = 0, and this is a *stable* 0 not the freshly-moved-item index-lag, because nothing was moved into/out of it) AND in the 2026-07-13 manifest (0 children walked under it). So there was nothing to dedup and 0 collisions - all 7 holdings came from Admin only. Lesson: when a source is reported empty, corroborate live-list + manifest before concluding; an empty source is legitimately "nothing to do", not a failure to enumerate.

**The external-share footprint is a VISIBILITY report, not a repair queue - state that explicitly.** All 7 holding TOP folders carried only the Robert-organizer baseline (0 external). The real external grants live on DESCENDANTS (WINDSWEPT AB = 206 of 317 descendants shared to WSA accountants + a Behold.vc/Rocketride investor cluster + a few `anyone:with-link`; Pixie Pie = 1 file to 4 investor/advisor readers). Two-part method that scales: (1) live `permissions.list` on each top holding folder for the immediate picture; (2) for descendants, don't crawl live - reuse the manifest's `external_grant_items.json` (id→grants map) intersected with each holding's subtree computed from the per-drive `.ndjson` parent map (BFS by `parents`). Because AP Admin's drive baseline is Robert-organizer-only, per the Phase-3 corrected finding the cross-drive move keeps every direct grant and drops nothing → **NET regrants = 0**; the whole footprint is for the owner's awareness, not action. Say "SURVIVES the move" next to each grantee cluster so nobody reads the list as a to-do.

**Guard the move set by explicit ID allow-list + name-regex belt-and-suspenders.** Mixed source folders hide non-holdings: a bankrupt-estate folder to FREEZE (`WLBS AB`, Phase-7), the acting company's OWN mis-filed company (`RUNATYR AB`, has its own drive), and loose corporate/cap-table files that are NOT holdings. Encode the genuine holdings as an ID Set (`ADMIN_MOVE`) so only those move; everything else falls through to a `skipped[]` array with a reason string; add a name-regex (`/wlbs|konkurs|bankrupt|runatyr/i` + non-folder) as a second guard for any live-enumerated source you couldn't pre-vet by ID (here EXT, which was empty anyway). Never scatter-guess a loose file into a holding.

**Flag public-link leakage you find in passing even when you're leaving the file alone.** One loose cap-table file left in place (`Aurora Punks AB - Aktieinnehav.xlsx`) carried `anyone:reader` + two external readers. Out of Phase-5 scope to move, but a public link on a shareholding register is worth surfacing to Robert in the report/flags regardless.

## 2026-07-15 - Drive migration Phase 6: flatten buckets, collision-first, and a "My Drive folder" that was actually a sync mirror (devops /db-256)

**Learned:** 2026-07-15 | **Project:** db-256 Drive migration | **Category:** gdrive / migration / collision-detection / drive-for-desktop / http-client

**Compute the collision set with a FREQUENCY MAP over the whole namespace BEFORE moving anything - not pairwise against the target.** Flattening N buckets into one flat root is not "for each child, does the root already have this name". Build one `Map<normalizedName, occurrences[]>` spanning (existing root folders, excluding the buckets) + (ALL children of ALL buckets), then treat **any name with count > 1 as a collision and flag every copy**. This one rule catches three distinct classes in a single pass: (1) child-vs-existing-root, (2) child-vs-another-bucket's-child, and (3) **same-bucket duplicates** - two identically-named siblings inside ONE bucket, which pairwise-against-target logic completely misses and which hard-collide the moment they land at root. Phase 6 hit exactly that: `SirWhoopass` ×2 both inside `AP Projects`, unanticipated by the brief. Normalize with `trim().toLowerCase()` - `Vessels Of Decay` vs `Vessels of Decay` differ **only by case** and would have silently double-filed the same project. Flag, never rename/merge: same-named folders under different entities can be genuinely different projects (`Elric` existed under AP, AP-External AND Runatyr).

**A bucket that still holds flagged collisions is NOT empty - say so instead of reporting "flattened, retired".** The instinct is to report buckets as emptied+retired. All 3 Phase-6 buckets retained 1-5 flagged collisions, so none could be retired. Compute `remainingAfter` by re-listing the bucket after the moves and derive `empty: remaining === 0` rather than assuming; report the retained items per bucket.

**"Move Robert's My Drive project folder X" - verify what the folder IS, not just who owns it.** Phase-4's lesson was ownership (a board-notes folder owned by a third party → flag, don't transfer). Phase 6's is a level deeper: **ownership was fine (Robert owned all 3, `canMoveItemOutOfDrive=true`) and the move was still wrong.** All candidates lived under `My Computer/projects` = a **Google Drive for Desktop backup mirror of the masterbrain root `/home/assistant/projects/` itself** (gave itself away instantly: `CLAUDE.md`, `.git`, `node_modules`, `.mcp.json`, `assistant/`, `skills/`, `vault/`, `.secrets` all sitting in "My Drive"). Moving a folder out of a sync mirror **cloud-side is a sync mutation, not a filing action** - if the mirror is ever reconnected it can remove/relocate the local copies, and it hands a Shared Drive ownership of live VPS content when the VPS is the runtime + source of truth. **Cheap tells to check before any My-Drive→Shared-Drive transfer:** (1) walk the parent chain to the top - a `My Computer`-style root means Drive-for-Desktop machine backup, not a Drive-native folder; (2) `ls` the same path on the VPS - if it still exists locally, the Drive copy is a **mirror node of a live working dir**, not an archive (`water_me_and_you` did; `sir_whoopass` didn't = stale remnant, mirror dormant since March); (3) check what the folder actually contains - one `sir_whoopass` was `projects/art/sir_whoopass`, an **art subfolder**, never a project.

**When a brief's premise is disproved by live data, flag the premise - don't execute the literal instruction.** The brief (and the plan's own Phase-6 step 1) said `water_me_and_you` sits "under an `umbrella` folder". **There is no `umbrella` folder in Drive** - exact-name and `name contains 'umbrella'` searches return nothing but an unrelated PNG. `umbrella/` is Robert's **VS Code workspace-root prefix** ([[feedback_workspace_root_no_umbrella_prefix]]), a local path convention that got conflated into a Drive location, and the wrong premise propagated from the plan into the brief. An approval granted over a wrong premise doesn't cover the real situation: report the finding + options, move nothing.

**The inherited Phase-3/4/5 Drive client has NO socket timeout - it hangs forever on a stalled Google response.** The first Phase-6 execute wedged ~72 moves in: process alive, socket open, `utime` frozen for minutes, zero progress, `tail`-buffered stdout showing nothing. `node`'s `https.request` has no default timeout, so a response that never arrives never rejects and the retry/backoff loop never even gets a chance. Fix (add to any script reusing this client): `req.setTimeout(45000, () => req.destroy(new Error('socket timeout')))` + wrap `httpsReq` in try/catch inside `api()` so network errors/timeouts retry with the same backoff as 429s. The resumed run logged 4 such retries and completed instead of hanging. **Diagnosing a stuck Node run:** sample `/proc/<pid>/stat` fields 14/15 (utime/stime) a few seconds apart - frozen CPU + `State: S` + an established socket = hung request, not slow work. Beware `cmd 2>&1 | tail -30`: `tail` buffers everything until the pipeline ends, so a wedged run shows a **0-byte output file** and you learn nothing - run long jobs with `nohup node script.js > log 2>&1 &` and tail the log directly.

**A re-run of a live-surveying move script is safe and idempotent - verify by checking the recomputed decision set, and re-verify the lost readbacks.** Killing a wedged run loses its result JSON, but not the work. Because the script re-enumerates live state on every run, already-moved folders are simply no longer bucket children (nothing re-moves), and - the part worth checking - **the collision set recomputed identically** (same 4 names), because collisions are computed among items *still in the buckets*, which the partial run never touched. Then independently re-verify the killed run's moves: replay the `--enum` JSON's `move=true` list through `files.get` and assert `id` unchanged + single parent == target + `driveId` == target (84/84), and assert every `move=false` item is still parented to a bucket (9/9). Don't trust a result JSON you never got.

**Same-drive flatten ≠ cross-drive move: the baseline-strip risk simply doesn't apply - say so rather than repeating the regrant caveat.** Phases 3-5 needed the "cross-drive moves keep direct grants, only source baseline drops" analysis. Phase 6 was entirely **within** the Projects drive, so nothing at all changes about sharing: NET regrants = 0 by construction, not by lucky baseline. The footprint report is then purely informational. Useful thing it surfaced anyway: `all@aurorapunks.com` had been removed from the AP **drives** back in the 2026-07-13 security step, but survives as an **item-level grant on 81 of 84 Projects folders** - "removed from the drive" and "removed from the content" are different facts; check both.

**Keep flagging public links you find in passing, even mid-migration.** The approved Task-1 fix (`anyone`:reader off the AP cap-table register `Aktieinnehav.xlsx` - deleted the one `anyone` perm, all 3 named grants verified intact **by permission ID** afterwards) was scoped to one file. The enumeration then turned up two more `anyone`:reader links unprompted (`Soul Walker`, `WS - Robot Lord Rising`). Report, don't auto-remove - the approval was per-file. Corollary on counting: the Phase-5 note said "4 loose files"; that count **included the target itself**, so only 1 of 4 was actually public. Re-derive counts from live data instead of inheriting them from a prior note.

**Project:** AP/CZP/Runatyr Drive migration (db-256) | **Category:** gdrive-api, shared-drives, folder-create, re-parent, migration-mutation

First real mutation of the migration (Phases 0 + backup were read-only). Phase 1 = additive `_legals/{_working,_archive}` shells on 5 company folders in the Financial SD (`0AMBeS-GYxphsUk9PVA`) + move the one stranded lånerevers Doc into `Aurora Punks AB/_legals/_working/`. All single-drive, additive, reversible; no sharing/ownership/cross-drive/delete/rename. Reusable bits:

1. **Manifest-first, don't re-walk.** Looked up all 5 company-folder IDs + the revers file ID straight from `/home/assistant/backups/drive/2026-07-13/financial.ndjson` (184-item drive, trivial to grep) instead of re-hitting Drive. Confirmed "no `_legals` exists yet" by name-scanning the manifest before creating — cheaper and safer than a live pre-check (still kept a live `findChild` guard in the script as belt-and-suspenders).

2. **Shared-Drive folder create:** `POST https://www.googleapis.com/drive/v3/files?supportsAllDrives=true&fields=id,name,parents,mimeType` with JSON body `{name, mimeType:'application/vnd.google-apps.folder', parents:[parentId]}`. `supportsAllDrives=true` is mandatory or it 404s/misbehaves on a Shared Drive. Auth = `getToken()` from `assistant/gdrive-read.js` (Robert-user OAuth, same as the manifest walk) — Bearer header, no service account.

3. **Same-drive re-parent (move) = `files.update` with add/removeParents, NOT a copy:** `PATCH /drive/v3/files/{id}?supportsAllDrives=true&addParents=<new>&removeParents=<old>&fields=id,name,parents`. File ID, bytes, version history, and sharing all survive — the ID in the response equals the input ID (verified `idUnchanged=true`). **Shared-Drive items are single-parent**, so `removeParents=<oldRoot>` cleanly replaces the parent (the read-back shows exactly one parent = the new folder, old root gone). Always do a fresh `files.get?fields=id,parents` read-back after the PATCH, and assert the ID is unchanged + the new parent is present + the old parent is absent.

4. **`q` list to find a child by name** (dup-guard) on a Shared Drive needs the drive corpora params: `GET /drive/v3/files?q=<'parent' in parents and name='X' and trashed=false>&supportsAllDrives=true&includeItemsFromAllDrives=true&corpora=drive&driveId=<DRIVE_ID>&fields=files(id,name,parents)`. Omit `corpora=drive`+`driveId` and shared-drive children don't reliably come back.

5. **Scope discipline paid off — flagged, didn't guess.** The AP AB root had TWO loose revers files: the working Google Doc `Lanerevers_CZP_AP_2026-07-06` (the exact-named target, moved) and a sibling `Lanerevers_CZP_AP_2026-07-06_signed.pdf` (the signed/executed PDF, `1szYlDOOl_X3njed0D1GJKAQJ3O4kiNZD`, NOT named in the brief). Moved only the exact-named file and surfaced the signed-PDF sibling to Robert rather than moving an unnamed file on inference. On a "do ONLY this" gated mutation, an exact-name match beats a semantic guess — flag the sibling, don't sweep it.

## 2026-07-14 — Discord: moved ticket-post actions from reactions to button rows (db)
**Learned:** 2026-07-14 | **Project:** Death Board / Discord bot | **Category:** discord-bot, interactions, buttons, ux

Follow-on from the same-day reaction work: Robert flagged that a pre-seeded ✅ reaction always sits at count 1, so a task "reads as done" at a glance. Fix = replace reactions with real Discord **buttons** (message components).

- **customId carries only the action, not the ticket ID.** `dbtask:<action>` (done/closed/trash/in_progress/backlog/obsidian/escalate). The ticket ID is recovered in the handler from `interaction.message.embeds[0]?.title || interaction.message.content` via the same `([a-z]+-\d+-[a-z0-9-]+)` regex the reaction path used. Reason: customId has a 100-char hard limit and ticket slugs get long (`k2c-035-resend-k2c-outsourcing-agreement-to-andreea-chifu-` ~55 chars); encoding the ID would risk overflow. Reading it back off the message is limit-proof and reuses proven extraction.
- **Two button layouts** via `buildTaskButtons(full)`: feed posts (#alerts/#brief, project channels) get one row [Done · Close · Trash]; #tasks embeds get a second row [WIP · Reopen · Obsidian · Escalate]. Max 5 buttons/row, 5 rows/msg — well within.
- **Button interactions route through the EXISTING `interactionCreate`→`onInteraction`.** There was already a slash-command handler that early-returned on `!isChatInputCommand()`. Added a branch at the very top: `if (interaction.isButton() && customId.startsWith('dbtask:'))` → `onButtonAction`, wrapped in try/catch that ephemeral-replies on error only if `!replied && !deferred`. **No new intent needed** — message-component interactions are delivered to any bot in the guild with `GatewayIntentBits.Guilds`; unlike slash commands they need NO registration/deploy.
- **`deferUpdate()` FIRST, then confirm via `channel.send`.** The 3s interaction-ack window is the trap: the `done` path calls `postToDone` which fans out sends across every guild and can exceed 3s → `interaction.reply` would throw `Unknown interaction`. So ack instantly with silent `deferUpdate()` (owner-check + no-ID guard use `interaction.reply({ephemeral})` BEFORE the defer since they're instant), then post confirmations to `msg.channel.send` exactly like the reaction flow. noop (already-in-state) returns silently — no channel noise.
- **Owner-gated.** Buttons live in shared project channels (K2C/AP guilds), so `onButtonAction` rejects non-owner clicks with an ephemeral reply. Reactions were ungated — latent risk a teammate closes Robert's ticket; buttons close that gap.
- **Shared core `applyTicketStatus(id, newStatus, actor)`** returns `{missing}|{noop}|{ok}` and owns the archive rules (done/closed keep mail archived, reopen unarchives). Both the button handler AND the legacy reaction handler call it — single source of truth.
- **Legacy reactions kept working.** `onReaction` + `addStatusReactions`/`addFeedReactions` retained but no longer seeded on new posts (all 4 send sites — postToTasks, cmdDone, postAlert×2 — now pass `components:` instead of calling the seeders). Pre-button posts that still carry reactions keep functioning. The seeder methods are now dead-but-harmless.
- **Verify button components before deploy** without spamming a channel: `node -e` require discord.js, build the rows, `.toJSON()`, assert row/button counts + customIds. Caught nothing this time but cheap insurance against ButtonBuilder API misuse (invalid style/emoji throws at build).

I changed the description/field text (Reactions→Actions, buttons wording) but NOT the title, so old pinned legends won't auto-refresh — cosmetic only; the buttons themselves work regardless. Bump the legend title if a forced refresh is ever needed.

## 2026-07-14 — db-256 Drive migration Phase 2: create Shared Drives + auto-sole-organizer on user OAuth

**Context:** Phase 2 (create-only) of the AP/CZP/Runatyr Drive restructure. Stood up the 3 missing target Shared Drives (Zenland Games AB `0AG5ggAZpSdKLUk9PVA`, APDS unit `0AIxVfcR4Xlm-Uk9PVA`, Portfolio `0AF1ubBnsLIXNUk9PVA`) + built the empty standard template in each. Script: `assistant/drive-phase2-create.js`.

**`drives.create` call shape (Shared Drive):** `POST https://www.googleapis.com/drive/v3/drives?requestId=<UUID>&fields=id,name` with JSON body `{ "name": "<drive name>" }`. **`requestId` is REQUIRED and must be unique per drive** (use `crypto.randomUUID()`) — it's the idempotency key; reusing one returns the same drive instead of creating a new one. Returns `{ id, name }` where `id` is the new driveId (also the root folder ID). Auth = the same `getToken()` from `gdrive-read.js` (Robert user OAuth, `drive` scope) that the read-only manifest walk uses — no separate write client needed; the scope already covers create (proven by gdrive-copy/upload creating files).

**Folder-in-Shared-Drive create:** `POST https://www.googleapis.com/drive/v3/files?supportsAllDrives=true&fields=id,name,parents` body `{ name, mimeType: "application/vnd.google-apps.folder", parents: ["<driveId or parent folder id>"] }`. Parent a top-level folder to the driveId itself. `supportsAllDrives=true` is mandatory or it 404s on shared-drive parents.

**KEY FINDING — membership = creator-only comes FREE on user OAuth.** When you create a Shared Drive with Robert's user OAuth token, the authenticated user (Robert) is automatically added as the sole `organizer` (Manager). Read-back of `.../drives/<id>/permissions` confirmed exactly one permission = `robert@aurorapunks.com` role `organizer`, nobody else. So "membership = Robert only" needs ZERO extra API calls — just don't add anyone. This is why deferring the accountants is trivial: doing nothing = Robert-only. (Robert's call 2026-07-14: never add a 3rd party to an EMPTY drive — it fires a premature "added to a shared drive" email; add accountants/service accounts only in that entity's Phase 3 content batch when content lands.)

## 2026-07-13 — WhatsApp healthz "spam" was just self-heal alerting; the "watchdog gap" was MY misread of lastReadyAt (db-167)

**Learned:** 2026-07-13 | **Project:** Death Board / db-167 | **Category:** infrastructure / healthz-monitor / whatsapp-bridge / diagnosis-discipline / false-positive

Robert asked "looks like spamming?" re Captain Hook #alerts posting alert+recovery pairs (~6m apart). The real fix was small; the cautionary tale is bigger.

1. **The actual bug + fix (monitor over-alerts on normal self-heals).** `healthz-monitor.sh decide_bridge()` alerted after 2 consecutive not-ready checks (~6m at the 3-min cadence), which lands *exactly* on the in-process watchdog's 5m self-heal exit + systemd restart, so every normal transient wedge produced an alert-then-immediate-recovery (watchdog self-heals 2-7×/day). **Fix, live:** non-QR threshold 2→3 so a self-heal (not-ready ~2 checks) stays silent, while a genuinely stuck bridge — not-ready *continuously*, so `cons` keeps climbing — still trips at check 3 and every reminder after. Plus: gate the recovery message on `notified`, else threshold=3 just swaps alert+recovery spam for *lone-recovery* spam (every silenced wedge still creates a transient failing entry that "recovers").

2. **THE TRAP: `lastReadyAt` is last-*connect* time, NOT wedge-start.** `bridge.js` sets `state.lastReadyAt` **only** in the `ready` event handler (L166); it is never refreshed while the bridge stays connected. So `now - lastReadyAt` = how long since it last *transitioned* to ready, which after any long healthy uptime is huge. I misread a probe showing `lastReadyAt=13:57:33` at 14:33 as "stuck 36 min" — but the bridge had been genuinely ready that whole time and only wedged ~14:31 (the monitor's own `firstFailedAt=14:33:01` proved the not-ready episode was minutes old, inside the 5m watchdog grace). **I invented a watchdog gap that wasn't there, restarted the bridge ~when the watchdog would have self-healed anyway, and started a bridge.js "fix" for a phantom bug.** Backed it all out.

3. **The same misread produced a buggy monitor guard — don't gate liveness on a last-known-good timestamp that only stamps on transitions.** I'd briefly added "alert if `now - lastReadyAt ≥ 12m`" as a "flap-proof stuck" check. It would false-alarm on *every* routine disconnect after a long uptime (age always ≥12m then). Removed. **Rule: a flap-proof stuck signal needs a timestamp that marks when the bad state STARTED (firstFailedAt / notReadySince), not one that marks the last good transition. lastReadyAt age ≠ not-ready duration.** For the monitor, sustained-not-ready already climbs `cons` monotonically; a truly stuck bridge is caught by the consecutive count — you don't need a second signal, and the wrong second signal is worse than none.

4. **Diagnosis discipline (the real lesson).** Before declaring a self-healing component "failed," measure the failure's *duration from its start*, not from some convenient last-good marker. Cross-check independent clocks: the monitor's `firstFailedAt`, `journalctl` restart lines (systemd `Started`/`exited` for the service), and process `etimes` — not a single field whose semantics you assumed. `authState='ready'` + `ready:false` is a genuine tell (the getState catch at bridge.js ~L612 flips `ready` without touching `authState`), but it means "a probe failed recently," not "stuck for the age of lastReadyAt." When you catch yourself mid-fix on a discovery that contradicts a *closed, verified* ticket, re-derive before shipping.

**Real hardening (shipped, Robert-approved):** wrapped the watchdog's `await client.getState()` in a 30s `Promise.race` timeout (`.finally(clearTimeout)` so no dangling timer); a timeout rejects into the existing catch → counts toward `WATCHDOG_FAILURE_THRESHOLD` → `process.exit(1)`. Legit defensive practice (a hung puppeteer probe can't stall a tick) independent of today's non-incident. Root trigger for the wedges themselves is memory pressure (db-258).

## 2026-07-13 — db-258 closed: VPS memory is comfortable, no upgrade; linkedin-sd trimmed (per-session, unlike the whatsapp bridge)

**Learned:** 2026-07-13 | **Project:** Death Board / db-258 | **Category:** infrastructure / memory / mcp-sprawl / diagnosis

Closed the long-open memory-pressure ticket. Reusable bits:

1. **"100% swap" ≠ pressure. Measure the right signals.** swappiness=60 parks cold pages in swap, so `free` shows swap near-full on a perfectly healthy box. The real pressure signals are `vmstat` **si/so** (sustained non-zero = active thrash), **load average**, and **confirmed OOM kills**. Here: si/so≈0, load 0.24, zero OOM, avail 2.4Gi → no upgrade needed despite swap at 94%. Don't recommend a paid RAM upgrade off the swap number alone.

2. **False-OOM grep gotcha.** `journalctl | grep -iE "oom"` matched 7 lines — all the substring "oom" inside **"data_room"** in RAG indexer logs (an active project folder). Kernel OOM kills go to the **system** journal / `dmesg` (not readable as the `assistant` user), NOT the user journal. So "N oom hits in the user journal" is never authoritative — inspect the actual lines, and treat unconfirmed-because-unprivileged as "couldn't verify," not "found kills."

3. **Distinguish per-session MCP sprawl from single-bridge fixed cost BEFORE recommending a trim** (the recurring whatsapp trap). Method: trace each server's procs to their PPIDs — many distinct session parents = per-session (trimming `~/.claude.json` reclaims real RAM as sessions cycle); one parent / a systemd service = a shared bridge (trimming reclaims ~nothing). Verified this run: **linkedin-sd is per-session** (config `uvx linkedin-scraper-mcp@latest`, direct stdio, ~83Mi python/session, 6 instances → 6 parents), so trimming it is a real ~500Mi reclaim. **whatsapp is the single bridge** (`whatsapp-bridge.service`, one puppeteer chromium ~2Gi, thin `mcp-whatsapp.js` HTTP shim per session) — trimming from `~/.claude.json` reclaims almost nothing. Config trim governs **new** sessions only; live sessions keep booted servers until they cycle.

4. **Per-session footprint ranking (8Gi Hetzner, ~6 sessions, 2026-07):** atlassian jira+confluence ~1.9Gi/37 procs (biggest, ~320Mi/session, retained — Jira used interactively for PM) · gdrive ~828Mi · linkedin ~782Mi · gmail+personal ~744Mi · rag ~399Mi. ## 2026-07-13 — Drive metadata manifest (264,771 items) for db-256 backup gate: the detached+checkpoint pattern that beat the teardown death

**Project:** AP/CZP/Runatyr Drive migration (db-256) | **Category:** gdrive-api, shared-drives, permissions, detached-checkpoint, rate-limit-retry, backup-manifest

Built the metadata-only manifest that unblocked the db-256 backup go/no-go gate (Robert's chosen backup path over Google Takeout). READ-ONLY walk of all 8 in-scope Shared Drives = **264,771 items** (32,467 folders / 232,304 files; projects drive alone is 168,530, AP-internal 85,117). Tool: `assistant/drive-manifest-walk.js` (walk) + `assistant/drive-manifest-summary.js` (combined manifest + summary). Reusable learnings:

1. **`files.list` does NOT return inline `permissions` for Shared Drive items — verified 2026-07-13.** Requesting `fields=...,permissions(...)` in files.list on a shared drive silently returns items WITHOUT the permissions field (and, oddly, requesting the unsupported subfield can also drop `modifiedTime`/`parents` from the same response). `files.get` with `fields=permissions` also returns nothing for a shared-drive item that only inherits drive-level access. The ONLY reliable read is the per-item `permissions.list` endpoint: `GET /files/{id}/permissions?supportsAllDrives=true&fields=permissions(id,type,role,emailAddress,domain,allowFileDiscovery,deleted)`. That per-item call is exactly the N+1 that killed the first attempt — so don't call it on every item blindly (see #2).

2. **`permissionIds` IS returned inline in `files.list` and is the cheap fingerprint to avoid the N+1.** For each item files.list returns `permissionIds` (the numeric grantee IDs; a Google permission ID is stable per grantee, e.g. robert@aurorapunks = `12199552634137347431` on every item and the drive root). Method: bulk files.list capturing `permissionIds`, then per-drive compute the **baseline** = permIds present on ≥90% of items (drive-wide inherited grants), then run `permissions.list` **only** for items whose permIds fall outside baseline. That collapsed a 264,771-item perms pass to 58,553 expansions (0 errors). Correctness is threshold-independent: anything outside baseline is fully expanded; baseline grants are resolved once per drive from any expanded item and recorded in `baselines.json`. NB: the drive-root `permissions.list` only returns robert, NOT the drive-wide inherited grants that appear on files — so derive baseline empirically from item frequency, not from the drive root.

3. **The detached + per-page-checkpoint pattern is what beat the session-teardown death.** Launch with `setsid nohup node walk.js ... > out 2>&1 < /dev/null &`. Append each page to on-disk NDJSON immediately (never hold the corpus in memory), and write the per-drive `nextPageToken` + counts to an atomic `_state.json` (temp-file + rename) AFTER every page. On restart: `done` drives skip, `error`/`in_progress` drives resume from the saved token WITHOUT truncating their NDJSON. Poll for a `_WALK_COMPLETE` marker (or use a Monitor `until [ -f marker ]` loop) rather than running the multi-thousand-item walk inline. This survived a real mid-run kill and a rate-limit abort, both resuming cleanly.

4. **Drive `403 User rate limit exceeded` is TRANSIENT — retry it, don't treat 403 as fatal.** The big drives (AP-internal, projects) hit `403 reason=userRateLimitExceeded` during pagination. Drive uses 403 for BOTH permission-denied AND quota, so branch on the body: `/rateLimitExceeded|userRateLimitExceeded|User rate limit/i` ⇒ back off (exp, up to ~60s, ≥10 attempts) and retry; other 403 ⇒ real permission error. My first version treated all 403 as fatal and aborted the drive at page 61 — but the checkpoint meant it resumed to completion (page 186, 85,117 items) after the fix. Also: `pageToken:null + status:done + ndjson-lines == state.itemCount` is the completeness proof (null token = API returned the last page = full walk, not an early stop). An empty drive (legals) legitimately returns HTTP 200 with an empty file list = 0 items, distinct from an access failure.

5. **Auth: reuse `assistant/gdrive-read.js` `getToken()`** (Robert-user OAuth refresh-token at `~/.claude/.gdrive-server-credentials.json`, keys at `gcp-oauth.keys.json`, hardened via `creds-store.js`). Call `getToken()` before every page — it returns the cached token and auto-refreshes near expiry, so long runs never lapse. Do NOT invent a new auth flow or use the service account (Shared Drives need the user grant).

6. **Output as a restore aid:** `manifest_combined.ndjson` (one line/item: metadata + effective permissions, `permsSource: expanded|baseline`) + `external_grant_items.json` (the re-grant worklist: 421 distinct external grantees across 56,151 items — anyone-with-link, non-aurorapunks domains, external gmail/user grants). This is the concrete answer to the migration's #1 risk (cross-Shared-Drive move silently strips per-file external shares): after each batch move, re-grant from this list. Note it's a metadata/permissions restore MAP, not a file-content byte backup — Takeout is still the option if byte-level content backup is wanted.

## 2026-07-06 — Atomic creds writes: the 0-byte OAuth truncation class (db-250)

**Project:** Death Board / infra (all Google integrations). **Category:** tooling / durability.

- **Symptom to recognize instantly:** any Google tool failing with `Unexpected end of JSON input` = a **0-byte creds file**, NOT `invalid_grant`. `ls -la ~/.claude/.*-credentials.json` — a 0-byte file is a local write bug (truncation); a non-empty file with `invalid_grant` is Google-side expiry/revocation (db-051/db-177). Two different failure classes, different fixes. Don't reflexively reauth-and-move-on: if it's 0-byte, the write path is broken and will re-truncate.
- **Root cause:** `fs.writeFileSync(FILE, JSON.stringify(creds))` opens the real path with **O_TRUNC** (file → 0 bytes) *then* writes. A process killed in that gap (session teardown, MCP child reaped, an unattended refresh interrupted) leaves 0 bytes. Multiple unrelated files truncating in one time window = a kill event mid-write, not Google.
- **Fix pattern (reusable for ANY credential/state file):** write to `FILE.tmp.<pid>` → `fsync` → `rename` (atomic on POSIX; a reader/kill never sees a partial file). PLUS a **content guard**: refuse to persist a payload missing its critical field (here `refresh_token`) so a bad/empty refresh can't clobber last-good. PLUS read 0-byte/whitespace as `null` (clean "reauth needed" vs cryptic parse crash). Centralized in `assistant/creds-store.js` — reuse it, don't re-hand-roll `writeFileSync` for creds.
- **Google refresh gotcha:** a refresh response omits `refresh_token`. Hand-rolled writers that spread `{...creds, access_token}` are fine (they keep it); but the googleapis lib's `refreshAccessToken()` path (mcp-gdrive-fork) needed an explicit `{...savedCreds, ...response.credentials}` merge or it can drop refresh_token.
- **Forensics:** these writers log to `assistant/logs/*.log` + Claude session transcripts, **not journald** — so `journalctl` won't hold the smoking gun, and volatile user logs are wiped on reboot anyway. mtimes across the creds files are the best timeline evidence.
- **Monitoring gap that let it hide:** healthz-monitor.sh only probed Gmail, only for `invalid_grant`. A 0-byte file (and gcal/personal-gmail entirely) slipped past for days. New `assistant/creds-probe.js` + `creds-probe.timer` (daily 07:00 Stockholm) now probes every creds file: non-empty assertion + a real refresh_token exchange, Discord-alerting on regression. When adding a new creds file, add a row to the `PROBES` table.
- **systemd oneshot probe convention:** exit code = #failures (gives a 2nd signal via `systemctl --user --failed` on top of the Discord ping). Read secrets from `.env` inside the script (small `readEnvVar` helper) rather than a systemd `EnvironmentFile=` — avoids strict-parse failures on unrelated `.env` lines. Timer needs user **linger** (already on for `assistant`) to fire headless.
