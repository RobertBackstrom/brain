## 2026-05-31 — GIN meeting booking failure: past-date + no auto-response = MUST-ASK boundary (eli-031)
**Learned:** 2026-05-31 | **Project:** eli (Elias GIN scheduling) | **Category:** must-ask / email-response / gating / past-date-tickets

**Context:** GIN meeting request for Adam Ritchie (Flotsam Interactive) arrived in the 4am sweep, routed to DevOps as "keyword fallback" (not ideal — should route to BizDev or PM normally). The GIN watcher had attempted auto-booking on Wed May 27 3:00pm but failed (slot already taken). No response or reschedule offer was sent to Adam. By the time the ticket reached DevOps on May 31, the original date was 4 days past.

**Pattern — past-date booking failures are MUST-ASK boundaries:**
1. **Check the facts first:** read GIN watcher state + calendar + Gmail for any manual booking/response that might've happened outside the auto-workflow
2. **If booking failed and no response sent:** the next step is always a *send* (apology + reschedule offer) — which is a MUST-ASK boundary per the autonomous decision framework
3. **Date discrepancy is a red flag:** ticket said "Thu 28 May 12:00" but GIN showed "Wed May 27 3:00pm" — someone manually adjusted the request or the ticket was created from incomplete data. Don't assume.
4. **Use IPC to ask, not needs_input blocking the whole ticket:** the question is narrow ("do we send apology or ignore?") and Robert can answer in one line — IPC is the right tool, so other work can proceed if needed

**What went wrong:** Routing a contact-response task to DevOps instead of BizDev/PM meant the 4am run spawned the wrong agent. The routing keyword ("respond") was too generic. Lesson: BizDev and PM agents should watch for GIN-related tickets; DevOps only if it's a tooling/integration issue.

**Next time:** If a ticket involves "respond" or "send" to a contact, check the project memory and existing epics to route to the right agent (BizDev/PM/Content) *before* DevOps. DevOps is for the watcher script itself, not for handling booking failures.

**Tags:** must-ask, email-response, routing, past-date, gating, gin, elias, eli-031

## 2026-05-29 — Discord channel ingestion into Death Board + RAG: everything's already built, glue it (db-190)
**Learned:** 2026-05-29 | **Project:** Death Board / Discord ingestion (db-190) | **Category:** discord / rag / architecture / reuse

**Context:** Robert wants the AP bokslut group (Robert + Amer + Mattias) and AP Board group tracked against `apb` tickets + RAG-indexed instead of lost in Discord. Scoped + prototyped a read-only stub.

**The big reusability win — almost nothing new needs building:**
1. **Group-DM constraint is the load-bearing gotcha (already in my own learnings, db-088):** Discord bots CANNOT join Group DMs. Any "add the bot to the X group" request is the Group-DM problem in disguise — the answer is always "make it a channel in a guild we control." The AP guild (`616345869490454593`) already exists with the `aurorapunks` profile and the bot is already in it. Don't waste time on SDK options.
2. **Message→event capture already exists:** the community scanner (db-052, `_onCommunityMessage` at discord-bot.js:3323) emits JSONL events to `community-events/discord-YYYY-MM-DD.jsonl` for any channel listed in a project's `community_config.json`. Adding a config block = subscribing a new channel, **no bot code change**. Seed phase + snowflake dedup + keyword filters are all handled.
3. **Event→ticket already exists:** `community-bot-orchestrator.js processEvents()` turns JSONL events into tickets under a parent epic. The only tweak for *conversations* (vs discrete community reports) is an `append-to-ticket` mode instead of create-per-message.
4. **Non-file RAG ingestion already exists:** `rag-indexer.indexContent(db, {source, virtualPath, title, content, meta, mtime})` is the Gmail/GDrive Phase-3 entry point. A new `discord` source needs NO schema migration — `docs.source` is free-text, virtual path `discord:<external_id>`, dedup via `UNIQUE(source,path)` + content-hash + a `sync_cursors` cursor. Same redaction runs automatically.

**Prototype pattern that's safe to ship first:** a standalone reader (`rag-discord-indexer.js`) that consumes the bot's *existing* JSONL output and upserts via `indexContent()`. It never imports or restarts the bot, so it can't break live behavior — the cleanest possible first increment. `--dry-run`/`--stats` verified against live rag.db with zero side effects.

**The one real RAG gap for privacy:** `indexContent()` hardcodes `visibility='public'`. To scope a source to specific agents (`agent:<name>`), it needs a one-line `meta.visibility` passthrough on the INSERT. `search()` already honours visibility; only the writer is missing it. Worth doing generally, not just for discord. Note "public" on this single-tenant VPS = "all Robert's agents", not internet-public.

**Tags:** discord, rag, indexContent, community-scanner, group-dm, db-190, db-088, db-052, reuse, visibility

## 2026-05-29 — Inbox triage: enforce continuously via sweep, don't wait on native Gmail filters (db-186)

**Learning (scope workaround):** Creating native Gmail filters needs `gmail.settings.basic` (re-auth, blocked since db-154). But you DON'T need filters to kill inbox noise — `batchModify` (archive/trash labels) works with the `gmail.modify` scope we already have. A policy-driven sweep cron (`gmail-sweep.js` reading `triage-policy.json`, run daily) achieves the same noise reduction continuously and is *more* flexible than native filters (one JSON, VPS-native, evolvable). Native filters become a nice-to-have for client-side (MacAir) enforcement only. The May one-time cleanup decayed 808 → 1179 precisely because nothing enforced it; continuous enforcement is the fix, not a bigger one-time pass.

**Learning (Gmail query gotcha):** Gmail `from:(a@x.com OR b@y.com)` tokenizes addresses loosely and OVER-MATCHES. Observed: `from:info@gamesindustry.network` pulled in unrelated senders, and the bucket I labelled "trade newsletter" was actually Nordic Game/MeetToMatch matchmaking (Meeting Request, New Connection Request). ALWAYS dump the actual From/Subject of a sender rule against the live mailbox before trusting a label or profiling-by-domain. A wrong archive rule on legit event/networking mail is a real cost.

**Learning (single source of truth pattern):** Noise rules had drifted across 3 places (Gmail filter spec, server.js hard-coded skip-list, scan-query category excludes). Consolidated into `triage-policy.json` consumed by sweep + digest + `server.js checkEmails()` (which now reads `routine_ignore_senders`/`routine_skip_subjects`). When the same policy is duplicated in code + data, collapse to the data file and have code read it.

**Learning (Gemini notes sender):** Gemini meeting-note emails arrive from `gemini-notes@google.com`, not just `meetings-noreply@google.com`. The Routine's `isGeminiNote` detector missed them, so ~35 piled up un-routed. Fixed. Worth re-profiling sender addresses periodically — Google changes them.

**Learning (newsletter digest UX):** Robert prefers newsletters (Substack, trade posts) DIGESTED not silently archived: read → 2-3 sentence summary + link to original post → one grouped email → THEN archive. Archive-after-send means each post is digested exactly once, so a daily cron never re-sends. Unwrap `click.kit-mail*` tracking links by base64-decoding the last path segment to recover the real URL. Chunk the summarizer (8/call, retry once) — a single big batched `claude -p` call returned empty intermittently.

**Source:** db-186 inbox management overhaul Part 1. **Tags:** gmail, inbox, triage, oauth-scope, cron, single-source-of-truth, gemini.

## 2026-05-29 — Unsubscribe at source: one-click (RFC 8058) only, don't click spam (db-186)

**Learning (tooling):** `gmail-unsubscribe.js` does RFC 8058 one-click: POST to the `List-Unsubscribe` https URL with body `List-Unsubscribe=One-Click` and `Content-Type: application/x-www-form-urlencoded`, ONLY when `List-Unsubscribe-Post: List-Unsubscribe=One-Click` is present. All 9 legit senders returned 2xx. Senders with http-only links (no one-click) are NOT auto-clicked — clicking arbitrary unsubscribe pages is fragile and Playwright-tier. Route those to a sweep trash backstop instead.

**Learning (don't unsubscribe spam):** For cold/spam outreach, clicking unsubscribe CONFIRMS the address is live and invites more. Filter-and-trash those (policy rule) rather than unsubscribe. Distinguish legit marketing (Google Cloud, Nintendo consumer, ESL) from cold spam (random "pre-IPO invest", cold hotel/masterclass outreach) before acting.

**Learning (Google Group delivery trap):** IGDA Insider's List-Unsubscribe pointed at `groups.google.com/a/aurorapunks.com/group/community...` + `googlegroups-manage+...@googlegroups.com` — i.e. it's redistributed via an Aurora Punks Google Group. Unsubscribing would leave the WHOLE group (broader than the one newsletter). Always read where an unsubscribe link actually goes before firing; flag group-delivered lists to Robert.

**Learning (Robert's promo policy):** He does NOT want games-industry orgs/newsletters unsubscribed even when he auto-trashes their marketing - he wants them KEPT, switched to auto-archive, and folded into the daily digest (Nordic Game, DevGAMM, Develop, Courage, Konvoy VC, A MAZE). Consumer/SaaS junk + cold spam = remove. Platform/dev mail (PlayStation/Sony/Nintendo-dev/MS/Apple/Steam) + receipts + booking confirms = never touch. Nintendo *consumer* (mail.nintendo-europe.com) is distinct from the dev portal and IS unsubscribable.

**Learning (no restart for cron-run policy):** `gmail-sweep.js` and `gmail-newsletter-digest.js` are standalone scripts the daily cron invokes; they read `triage-policy.json` fresh each run. Policy edits to sweep/digest rules need NO Death Board restart - only `server.js checkEmails()` skip-lists (also policy-driven) require a restart since the server loads them in-process.

## 2026-05-25 — Scope-specific OAuth refresh-token revocation; healthz auth-probe pattern (db-177)
**Learned:** 2026-05-25 | **Project:** db (Gmail OAuth incident) | **Category:** oauth / healthz / diagnostics

**Context:** Captain Hook posted a 68h 30m Healthz reminder on `auth://gmail.modify` (Gmail OAuth refresh-token 401 since 2026-05-22 10:30 UTC). Direct probe via `gmail-api.checkAuth()` returned `Token has been expired or revoked` from `oauth2.googleapis.com/token`. Same OAuth client (`446018956587-phujr539...`) was fully healthy for Drive (`.gdrive-server-credentials.json`) and Calendar (`.gcal-credentials.json`), both refreshed minutes earlier. Fix: re-consent via `oauth-helper.js exchange gmail "<callback-url>"`, fresh tokens saved, probe + listMessages confirmed recovery, healthz auto-detected.

**Scope-specific revocation is a real failure mode — don't assume "one healthy refresh on this client means the client is fine."** Google can revoke a refresh_token for a single scope while leaving sibling-scope tokens from the same (client_id, user_id) alive. So when a healthz auth probe screams about one scope, the diagnostic isn't "is the OAuth client healthy" — it's "is this *specific scope's* refresh_token alive." Compare creds-file mtimes across all scopes for the same client_id: if one is stuck at the failure timestamp and others are fresh, you have scope-specific revocation, not a client-wide problem. That rules out test-mode-7-day-expiry, 50-token rotation, and IdP-wide revoke in one glance.

**Diagnostic recipe for OAuth healthz failures (replicate for any auth-probe alert):**
1. `stat -c '%y - %n' ~/.claude/.<scope>-credentials.json` for the failing scope AND every sibling scope on the same client. Match mtimes against `assistant/logs/healthz-state.json:firstFailedAt`.
2. Run the actual healthz probe directly (`node -e "require('./gmail-api').checkAuth().then(console.log)"`) to capture Google's exact error string — the healthz monitor only stores HTTP code (200/401).
3. Inspect the file shape (no values): `expiry_date`, `scope`, `refresh_token` length. `expiry_date: 0` is a known harmless artifact — `rag-external-indexer.js:117` writes it deliberately to force-refresh after a 401 (file mtime updates even though the refresh itself failed). Don't read mtime as "token last worked"; read it as "we last tried to refresh."
4. Only then go to re-consent. The flow is `oauth-helper.js url <scope> → user opens URL → pastes back full callback URL → exchange <scope> "<url>"`. The dummy redirect (`http://localhost:53682`) lets the browser fail to load while the code lands in the address bar — no SSH tunnel needed (which db-051 originally required when gws CLI was in the path).

**`auth://<scope>` pseudo-URL is a portable healthz pattern.** `healthz-monitor.sh` checks `auth://gmail.modify` by `node --eval`'ing `checkAuth()` and feeding the boolean into the same state-machine that handles HTTP sites (dedupe, reminder cadence, recovery message). It scales trivially to every refresh-token-bearing credential — gdrive, gcal, slack cookies, whatsapp bridge, linkedin session, etc. The next durable-fix tier is a multi-creds probe that exercises every refresh token daily so silent rot is caught at 24h, not 3 days. Current healthz only probes Gmail; everything else is flying blind until something downstream noticeably breaks.

**`feedback_oauth_sync` was a no-op here in the literal sense (no other dependents needed updating because the credential file path is the same and downstream code re-reads it on each spawn), but the *spirit* of the rule applies:** before re-auth, grep `client_id` and `<scope>-credentials.json` to confirm what you're about to swap is the single shared source-of-truth. In this case, 14 files reference `~/.claude/.gmail-archive-credentials.json` directly (every Gmail helper + the MCP wrapper + RAG indexer), all reading from the same file with auto-refresh — so one re-consent fixes all 14. If a downstream caller had stashed an access_token in its own cache, that cache would need invalidation. None did.

**`prompt=consent` in the auth URL forces fresh refresh_token issuance.** Without it, Google may return only an access_token if a recent consent already covers the scope, leaving the (now-revoked) refresh_token in place. `oauth-helper.js` already passes this — keep it. ## 2026-05-21 — GIN → Erik calendar mirror watcher: build-dormant + supervised-activation pattern (Elias NGC)
**Learned:** 2026-05-21 | **Project:** Elias NGC GIN scheduling (gin-erik-watcher) | **Category:** infrastructure / browser-automation / activation

## 2026-05-20 — Making a read-only renderer read-write: the write-path is a SEPARATE default-deny boundary (db-168)
**Learned:** 2026-05-20 | **Project:** db-168 (editable client tracker) | **Category:** security-boundary / write-path / untrusted-input / cloudflare-access / atomic-writes

**Context:** db-163 shipped `clients-server.js` as a read-only field-stripped renderer of the deal-wiki (token-gated, external clients). db-168 made it read-write — a per-deal client comment box (Phase A) + a CF-Access-gated admin edit surface for Robert (Phase B). A leaked token previously only *read* a sanitized page; once writes exist, the write path needs its own lock-down.

**Core lesson — the read sanitizer does NOT protect the write path; build a second boundary.** db-163's `deal-sanitize.js` decides what a client *sees*. It does nothing for what a client *writes*. The write path got its own module, `lib/deal-write.js`, with the same default-deny discipline aimed the other direction.

**Comment sanitization = strip ALL structure, don't "allow safe markdown".** The client comment is the only untrusted free-text. The mistake would be a markdown allowlist. Instead `sanitizeComment()` removes everything structural and collapses ALL whitespace so the stored comment is physically a single line — it then *cannot* open a markdown block, a frontmatter `---` delimiter, a heading, a table, a fence. What it strips: HTML tags + stray `<>`, `[[wikilinks]]` + `[md](links)` (keep the label), per-line heading/list/blockquote/table/fence prefixes, `---`/`***`/`___` delimiter lines, emphasis markers, control chars. Length-cap AFTER neutralisation (so you measure real content). The renderer also escapes — but never rely on one layer; the comment must be inert even if the renderer changed. Test it with the actual injection vectors (heading, frontmatter, HTML, wikilink, code fence, table, control chars, oversized) — 12 vectors in `test-deal-write.js`.

**The narrow read-side exception, done safely.** Phase A needs the client to see their own comments back, but the `## Activity Log` section is denied wholesale by the read sanitizer. The exception: `extractTrackerComments()` reads the *raw* Activity Log but emits ONLY lines matching the EXACT structured shape `- [YYYY-MM-DD HH:MM] **<label> (via tracker)**:` — and then *still* re-scrubs each matched line through `stripCitations` + the internal-phrase denylist. Result: a forged internal line that merely contains the substring "(via tracker)" can't smuggle a `Source:` citation back to the client (verified by test). Key the exception on structure, re-scrub anyway.

**Atomic append-only writes — temp + rename.** `/ingest-deal-email` agents write the same `wiki/deals/*.md` files. Every write goes through `atomicWrite()` (write to a sibling `.tmp-<rand>` file, fsync, `rename()` over the target — rename is atomic on one fs). Comments are append-only (new line inserted as the first `## Activity Log` entry, reverse-chron; existing lines never touched). A concurrent writer never sees a half-written file.

**Admin surface = a SEPARATE server on a SEPARATE auth boundary.** Robert's edit surface is `clients-admin-server.js` (own port 3781, own systemd unit), gated by **CF Access** — NOT the client token. The client read route stays token-only and must NOT go behind CF Access (the token IS its gate; CF Access would block the client). This is the db-163 rule restated: different auth boundary → different server. The admin server verifies the `Cf-Access-Jwt-Assertion` JWT at the origin itself (defense in depth, same `jose.jwtVerify` path as `server.js`), with a documented local-127.0.0.1-no-cf-connecting-ip bypass for VPS scripts/tests. Only JWT *rejection* paths are testable without Robert's real SSO identity — note that gap explicitly.

**Allowlist the admin writes too — trusted ≠ unconstrained.** Even though Robert is trusted with free text, `applyEdit()` allowlists which frontmatter keys (`status`/`priority` only, each enum-validated against the canonical list) and which body sections (`Key People`, `What They Bring/We Bring`, project `Key Dates`) may be written. A non-allowlisted field/section is rejected, not written. Admin section bodies still get heading-demote (`##`→`###`) + `---`-defang so even an admin edit can't inject page structure. Keeps the blast radius of any bug (or a mis-scoped request) minimal.

**Control bytes can't round-trip through tooling.** Authoring a regex with literal control-char class members (`/[\x00-\x08...]/`) — the bytes get mangled or break the shell when you later `node -e` against the file. Fix: write a `stripControlChars()` helper that filters by `charCodeAt`, so the source file carries zero literal control bytes. Same lesson for test fixtures — build control-char test strings with `String.fromCharCode()` in the test file, never inline them in a shell heredoc.

## 2026-05-20 — Per-client doc renderer: field-stripping is allowlist-of-structure, not regex-of-content (db-163, db-164)
**Learned:** 2026-05-20 | **Project:** db-163 (per-client prospect tracker) + db-164 (rendered wiki view) | **Category:** security-boundary / static-hosting / markdown-rendering / cloudflare

**Context:** Two render layers over the deal-wiki — an internal full-fidelity wiki browser (db-164) and an externally-shareable per-client tracker (db-163). Shared a zero-dep markdown→HTML renderer (`assistant/lib/md-render.js`).

**The big one — where the security boundary actually lives.** The plan said "strip internal frontmatter fields (owner, routed_agent…)". That framing is a trap: it implies a *field denylist*. The real leaks were almost never in frontmatter — the deal-wiki frontmatter is clean. The leaks were in **free-prose body sections**:
- `## Snapshot` / `## Current State` carry internal coaching verbatim ("do not name-drop X in outreach", "banned as proof points") and name *other clients* by name.
- `## Pipeline Status` carries internal workflow IDs — Gmail draft IDs (`r-7400345798352457856`), calendar event IDs, send-tracking ticket refs.
- `## Activity Log` is citation-dense (`Source: [[raw/gmail/...]]`).
- Bare prose paths: "Named in `umbrella/blue_scarab_bizdev/README.md`" — not a `[[wikilink]]`, so a wikilink-target check misses it entirely.

**The fix that works: allowlist STRUCTURE, not content.** Default-deny by section heading. For the client tracker only `Key People` + `What They Bring / What We Bring` (deal pages) and `Key Dates` (project page) survived — everything free-prose got dropped wholesale. Content-level regex scrubbing (citation tails, ID patterns, internal-phrase denylist) is the *second* belt, defense-in-depth, never the primary boundary. If you find yourself writing ever-more regexes to clean a section, the section itself is the wrong abstraction — drop it.

It caught two real leaks on first run (`name-drop` coaching text, the word "elias" in the Blue Scarab view) that visual review would likely have missed. Critical test shapes: (1) denylist — assert internal strings are ABSENT; (2) cross-tenant — render client B, assert ZERO of client A's data; (3) the inverse direction too; (4) positive content — assert the deliverable didn't get gutted by over-stripping; (5) adversarial fixture — a synthetic page with mismatched frontmatter must be rejected by the gate.

**Multi-tenant isolation = a hard frontmatter gate, checked per page.** `sanitizeDeal(md, project)` rejects any page whose frontmatter `project` != requested slug *before* rendering. Don't rely on "we only loaded this project's pages" — verify each page's own frontmatter. Candidate deal slugs are harvested from the project page's `[[...]]` links, but each linked page is independently re-gated.

**Token gate pattern (clone of the webhook HMAC idea, simpler):** opaque `crypto.randomBytes(18).toString('base64url')` tokens in a JSON map, `crypto.timingSafeEqual` compare against every known token in constant time (loop doesn't early-exit), charset+length pre-validation, unknown→404 (never 403 — don't confirm the path exists). `fs.watch` the token file for hot-reload so adding a client needs no restart.

**`pitches-server.js` is the canonical clone target** for any new public-at-edge static/dynamic host: zero-dep, `http` built-in, bind `127.0.0.1`, healthz route, systemd user unit modeled on `pitches.service`. New service here = `clients-server.js` on port 3780, `clients.service`.

Rule of thumb: if it shares the existing auth boundary, add a route; if it needs a *different* auth boundary, new server + new tunnel route.

**Restarting `deathboard.service` for additive routes is fine** — it's a single Node process with no route hot-reload. Verify the change is purely additive (no existing route/handler touched), then `systemctl --user restart deathboard.service`. Confirm an existing route still 200s afterward.

DevOps cannot add `clients.runatyr.games → localhost:3780`; document it for Robert: Zero Trust → Networks → Tunnels → deathboard → Published application routes. The DNS CNAME half (`cloudflared tunnel route dns`) IS CLI-doable from the VPS.

## 2026-05-20 — WhatsApp bridge 13-day silent outage: watchdog dead-state gap + Plane-webhook status-corruption loop (db-166, whatsapp-bridge, plane-bridge)
**Learned:** 2026-05-20 | **Project:** Death Board / db-166 | **Category:** infrastructure / puppeteer / watchdog / plane-bridge / webhook

Two distinct bugs, surfaced by one ticket.

### Bug 1 — WhatsApp bridge watchdog has no escape from an already-`ready:false` state
**Symptom:** `whatsapp-bridge.service` showed `active (running)` for 13 days (since 2026-05-07), but `whatsapp_status` returned `ready:false` with `detached Frame`. Process up, port 4501 up, `/health` 200, but **zero Chromium child processes** and only 10.9M RSS (a live bridge is ~130-440M). Classic db-117 liveness-zombie — but this time it never self-healed.

**Root cause:** `bridge.js` watchdog (~line 477). First line of the interval handler:
```js
if (!state.ready) { watchdogConsecutiveFailures = 0; return; }
```
The db-117 status probe correctly *caught* the dead context and set `state.ready=false`. But from that point every watchdog tick hit this branch, reset the failure counter to 0, and returned — so it **never reached `WATCHDOG_FAILURE_THRESHOLD` (3) → `process.exit(1)`** that would let systemd `Restart=always` recover it. The watchdog can escape a live `CONNECTED → not-connected` transition, but has no path out of a state that is *already* `ready:false`. Result: dead-but-not-exiting for 13 days.

**Fix applied (this ticket):** `systemctl --user restart whatsapp-bridge` — re-paired from intact LocalAuth (`.wwebjs_auth/session`) in ~42s, **no QR needed**. `authState:connected` + populated `me` in `state.json` is the tell that a restart will re-pair without a phone scan; only an *expired* session (`qrPresent:true` / auth_failure) needs the QR.

**Fix recommended (separate ticket — not built):** in the `!state.ready` branch, instead of always zeroing the counter, track *how long* the bridge has been not-ready; if it persists past a grace window (~5 min, longer than a normal reconnect) call `process.exit(1)`. Converts a 13-day outage into a ~5-min self-heal. Defense-in-depth: add a `/health`-parsing check to `healthz-monitor.sh` (already runs every 3 min, posts to Discord `#alerts`) — the endpoint already exposes `ready` + `watchdog`.

**Generalization:** the db-117 5-layer pattern is necessary but not sufficient. A watchdog that only fires on a *transition* is blind to a *steady* dead state. Any restart-on-failure watchdog must be able to trigger from "currently broken", not just "just broke" — otherwise the first probe that flips the flag also permanently disarms the watchdog.

### Bug 2 — Plane inbound webhook silently stamps `status: backlog` on every `issue.updated`
**Symptom:** Could not mark db-166 `done`. Every `PUT /api/followups/:id/status {done}` succeeded, but ~30s later the file reverted to `backlog`. `deathboard` log showed `[webhook/plane] Updated db-166-...: {"status":"backlog"}` on a loop.

**Root cause:** `server.js` `/webhook/plane` handler built `statesById` **only if `issue.state_detail` was present** in the payload. Plane CE's `issue.updated` webhook sends `state` as a bare UUID and omits `state_detail`. With an empty `statesById`, `plane-mapper.planeStateToDbStatus(uuid, {})` can't resolve the UUID and **silently defaults to `'backlog'`** (see `planeStateToDbStatus`: missing state → `return 'backlog'`). So every webhook stamped `backlog` regardless of the real Plane state. The Plane issue itself was correctly in the `Done`/`completed` state the whole time — the *mapper default* was the corruption source.

**Fix applied:** when `state_detail` is absent, fetch the project's states via `plane-client.listStates()` and build `statesById` from that. Plus an anti-corruption guard: if the issue's state still can't be resolved to a group, **drop `status` from the update set entirely** (`delete updates.status`) rather than letting it default to `backlog`. Logs `unresolved state ... status update suppressed`. Restarted `deathboard`; db-166 then held `done` across many webhook cycles.

**Generalization — silent-default = data corruption.** `planeStateToDbStatus` returning `'backlog'` for an *unresolvable* state is indistinguishable from a real backlog state. A mapper that can't resolve its input must signal "unknown" (return null / omit the field), never a plausible-looking default. Any bridge field-mapper: on unresolved input, **omit the field so the existing value is preserved** — don't guess. Check `plane-mapper.js` priority/owner mappers for the same `|| 'none'` / `|| default` pattern.

## 2026-05-20 — Plane bridge mapper anti-corruption audit + webhook hardening (db-165)
**Learned:** 2026-05-20 | **Project:** Death Board / db-165 | **Category:** plane-bridge / silent-default-corruption / webhook / hmac

Followed up the db-166 silent-default warning across the whole `plane-mapper.js`. The `|| default` pattern was in 4 places, not 1.

### The full silent-default sweep — `plane-mapper.js`
A mapper that returns a *plausible-but-wrong* value on unresolvable input corrupts the write-back path. On the inbound (Plane→`.md`) direction this is data corruption of the source of truth. The fix everywhere is the same: **return `null` / omit the field, let the caller preserve the existing value, never guess.**
1. `planeStateToDbStatus()` — `return 'backlog'` for null/unknown → now `return null`. (db-166 root cause; was latent in the mapper even after the server.js handler was patched — any other caller would still corrupt.)
2. `planeToDb()` priority — `PLANE_PRIORITY_TO_DB[x] || 'none'` silently overwrote a real DB priority with `none` for an unrecognised Plane value → now omits the field.
3. `dbStatusToPlaneState()` — `DB_STATUS_TO_GROUP[x] || 'backlog'` mapped unknown DB statuses to backlog *group* outbound → now `null`, `dbToPlane()` omits `state`.
4. `dbToPlane()` assignee — `else → membersMap['robert']` silently assigned every agent-owned ticket to Robert in Plane → now leaves unassigned.

**Diagnostic-flag pattern for bridge mappers.** Rather than silently dropping a field, surface *why* on non-API meta keys (`_priorityUnresolved`, `_ownerUnresolved`, `_stateUnresolved`). Callers (import / watch daemon) log them so data-quality issues in the `.md` files are visible, then a `stripMapperMeta()` helper removes the `_`-prefixed keys before the payload hits the API. Distinguish a *genuine* unresolved (status not in the mapping table = data bug) from a benign empty lookup (empty `statesMap` in dry-run) — flag only the former.

### Webhook HMAC: `crypto.timingSafeEqual` THROWS on length mismatch
`/webhook/plane` signature check did `timingSafeEqual(Buffer.from(sig,'hex'), Buffer.from(expected,'hex'))`. A missing / malformed / odd-length `x-plane-signature` header produces a short Buffer; `timingSafeEqual` throws `Input buffers must have the same byte length`, which fell through to the catch block as a **`500`** — wrong status, and it leaks that the endpoint behaves specially. **Always compare `.length` first and fail closed with `401` before the constant-time compare.** Applies to every HMAC webhook handler (`/webhook/atlassian`, `/webhook/docuseal` — check those too).

### Bridge state was further along than its own docs claimed
`plane_bridge.md` said "Phase 1 complete, no live API calls yet" — but the bridge was fully live: all `PLANE_*` env vars set, `PLANE_WEBHOOK_ENABLED=true`, bulk import done (605 created / 1617 updated in the sync log), `plane-sync-watch.service` running, CF Access Bypass for `/webhook/plane` in place, webhook registered + firing. **Don't trust a design doc's stated phase — verify against `.env`, `systemctl --user list-units`, the sync log, and an external `curl` of the webhook path.** The 361 sync-log errors looked alarming but were all one-off import-time 429 rate-limits from 2026-05-13; cross-referencing db_ids showed every affected ticket re-synced — `node` one-liner to diff errored-vs-succeeded ids is the quick check.

### Verifying a bidirectional webhook bridge locally without touching the live API
You can prove the whole inbound round-trip with self-signed POSTs to `localhost:PORT/webhook/plane`: HMAC the body with the secret from `.env`, embed the `[external_id: db-NNN]` footer in the payload's `description_html`, and for `issue.updated` embed `state_detail` so the handler doesn't need a live `listStates()` call. Test the corruption case explicitly: an unresolvable state UUID must leave `status` unchanged, not stamp `backlog`. Back up the test ticket file first, revert after. The `listStates()` call IS a live API hit — the auto-mode classifier correctly blocks it under a "don't touch Plane's API" instruction; embed `state_detail` to route around it cleanly.

## 2026-05-20 — Design-doc event name ≠ real Plane CE event name; simulate with the REAL payload (plane-bridge)
**Learned:** 2026-05-20 | **Project:** plane-bridge | **Category:** integration / plane / webhook / testing

**Context:** Robert ran the db-165 kill-gate UI test (wrote a comment on a Plane issue). The `/webhook/plane` handler logged `Unhandled event: issue_comment.created` and dropped it — the comment never reached the `.md` activity log. The prior db-165 round-trip "self-test" had passed because it was simulated with the *design doc's* payload, not a real one.

### The lesson: a simulated webhook test is only as good as the payload you feed it
`plane_bridge.md` named the comment event `comment.created`. The handler matched that name. The simulated test POSTed a body using that name → passed. **Plane CE actually emits `issue_comment.created`** — `event` = the *model name* (`issue_comment`), `action` = `created`, joined by the handler into `issue_comment.created`. Sim passed, real UI failed. **When writing a webhook test fixture, derive the payload from the integration's SOURCE (serializer + the task that builds the payload), not from your own design doc.** A design doc is a guess until a real event proves it.

### Plane CE `issue_comment.created` payload — confirmed shape (verified against source)
Source of truth: `plane.api.serializers.IssueCommentSerializer` (used by `bgtasks/webhook_task.py` via `SERIALIZER_MAPPER["issue_comment"]`) + the payload builder in `webhook_task.py` (`payload = {event, action, data, activity}`).
- `payload.event` = `"issue_comment"` (model name), `payload.action` = `"created"`.
- `payload.data` = the comment object. **The comment lives at `data`, NOT `payload.comment`.**
  - `comment_html` is the ONLY text field — the API serializer `exclude`s `comment_stripped` and `comment_json`, and there is no plain `comment` field. Strip HTML tags from `comment_html`.
  - `data.issue` = a **bare issue UUID** — no description, no `[external_id: ...]` footer. You CANNOT `extractExternalId()` from a comment payload.
  - `data.actor` = a bare actor UUID (no `actor_detail` in the API serializer). The resolved user object is at `payload.activity.actor` (`{display_name, ...}`).
- `data.id` is the COMMENT uuid, not the issue uuid — easy to mis-log.

### Resolving a bare issue UUID → db-id (no description to grep)
For `issue_comment.created` the only issue reference is a bare UUID. Two-step resolution: (1) **primary** — scan `plane-sync-log.jsonl` newest-first for a record whose `plane_id` matches the issue UUID, take its `db_id` (cheap, no API call, last-write-wins); (2) **fallback** — `plane-client.getIssue(projectId, issueUuid)` then `extractExternalId()` on the description. Note: ticket `.md` frontmatter does NOT carry a `plane_id` field for imported tickets, so the sync log is the canonical UUID↔db-id map.

### General rule for any model-keyed webhook integration
Plane keys webhooks by Django model name, so the event prefix is the *model* (`issue`, `issue_comment`, `cycle`, `module`), not a human verb. When you add handling for a new event type, check `SERIALIZER_MAPPER` / `MODEL_MAPPER` in `bgtasks/webhook_task.py` for the real model name, and read the matching `*Serializer` `Meta` (`fields` / `exclude`) for the actual field set before writing extraction code.

- Requires Claude Code restart to pick up the new MCP entry. Plan the work so the restart isn't mid-flow.

- The existing `oauth-helper.js` had a single hardcoded `KEYS_FILE` path. Changed to a per-profile `keysFile` field on each scope profile, defaulting to the legacy path when unset:

## 2026-05-19 — Personal Gmail multi-account ingest + 38k-message cleanup (Death Board, db-158)
**Category:** integration / Gmail API / Voyage / cleanup patterns
**Project:** Death Board (db-158)

Wired Robert's personal Gmail (`johanrobert.backstrom@gmail.com`) into both the MCP toolset (`mcp__gmail-personal__*`) and the RAG indexer (`source=gmail-personal`). Approach for any similar future "absorb a large mailbox" job:

**1. Cleanup-then-index, not the other way around.** Personal mailbox was 59,459 messages. Trashed 37,858 (~64%) of promo/social/no-reply junk BEFORE RAG ingest. Saved ~50% of Voyage tokens and kept the corpus signal-dense. Pattern: Robert chose this explicitly when I proposed parallel cleanup+ingest. Always offer it first when ingesting a non-curated mailbox.

**2. Label-then-trash safety pattern for bulk Gmail ops.** Created a `cleanup-candidate` user label. Step 1 = bulk-label matching messages (reversible). Step 2 = Robert skims the label folder in Gmail UI. Step 3 = trash on his nod. Removes "fat-finger destruction" risk entirely. Tooling: `assistant/personal-gmail-cleanup.js` with `count/create-label/label/trash/list-senders` subcommands.

**3. Google returns 403 for per-minute quota hits, NOT 429.** Body contains `reason=rateLimitExceeded` or `Quota exceeded`. Existing `authFetch` only retried 429/5xx, so the initial full-mailbox backfill dropped ~525 messages. Fix: peek the body on 403 and treat as retryable if `/rateLimitExceeded|userRateLimitExceeded|Quota exceeded/i` matches. Applied to `rag-external-indexer.js authFetch`.

**4. Gmail messages.get format=full is ~5 quota units; per-user-per-minute cap is 15,000.** That's 50 calls/sec max sustained. Voyage embedding stalls during indexContent let calls bunch up, blowing past the spread limit. Added `RAG_GMAIL_MAILBOX_THROTTLE_MS` env (default 35ms ≈ 28/sec) to keep us well clear.

**5. Voyage's 120k tokens/batch limit + approxTokens (chars/4) underestimates real tokens ~2x for non-English.** Swedish text inflates significantly. Batch budget of 100k *estimated* tokens consistently produced 150-200k *real* tokens → 400 errors. Lowered to 50k estimated for `backfillEmbeddings` and split batches by token budget, not chunk count. The same chars/4 estimator drives `getBudgetRemaining` daily-cap accounting, which is OK because we want to under-count and let real usage be the constraint.

**6. Daily Voyage budget cap (`RAG_MAX_EMBED_TOKENS_PER_DAY=5M`) is enforced at `indexContent` time, not `backfillEmbeddings`.** When initial ingest exhausts the cap, docs+chunks are written but `chunk_vecs` rows are skipped. Result: FTS5 search works, vector/rerank scoring is missing. Recovery: run `node rag-indexer.js --embed` after budget resets (next UTC day). `backfillEmbeddings` only *records* budget, doesn't enforce — by design, so explicit recovery doesn't double-block.

**7. Systemd timer race during long initial backfills.** The `rag-external-sync.timer` (hourly) fired while my manual backfill was still running. Cursor wasn't yet set, so the timer-triggered run started a SECOND full enumeration in parallel. Both competed for the same Gmail per-minute quota, both hit 403s. Net result was actually beneficial here (the 525 originally-errored were caught by the second pass), but for cleanliness consider either an flock-style lock on the script, or set the cursor early (with a "partial" flag) to make subsequent runs go incremental. For now, idempotent reads + hash-skip make the race forgiving.

**8. Multi-account Gmail config pattern.** Refactored `rag-config.js` to export `GMAIL_ACCOUNTS` array. Each entry: `{name, source, keysFile, credsFile, mode: 'labels'|'mailbox', labels?, query?}`. The indexer iterates accounts and dispatches per `mode`. Keeps the original work-account behavior untouched (first array entry preserves the old hardcoded paths/labels). Same pattern would work for adding more accounts later.

**9. Sender-report sampling for cleanup planning.** Listing all senders in a 16k subset hits the per-minute quota in seconds. Instead: enumerate all message IDs (cheap — one messages.list page = 500 IDs), then evenly *sample* N (e.g., 1500), fetch only those metadata-only, project to full counts via `scaleFactor = totalIDs / sample`. Gave a clear top-50-senders picture in ~60 seconds vs 12+ minutes.

**Final state:** 21,604 docs / 37,818 chunks indexed under `source=gmail-personal`. Hourly systemd timer continues incremental sync via the multi-account loop with zero service-file changes.

## 2026-05-13 — Plane Phase 2: live two-way sync wired (plane-bridge, plane-sync-watch)
**Learned:** 2026-05-13 | **Project:** plane-bridge | **Category:** integration / plane / sync / chokidar / webhook

### What was done
Wired Phase 2 live bidirectional sync between `followups/*.md` and Plane. All 6 tasks executed; 3/3 smoke tests passed.

### chokidar + debounce + .env bootstrap pattern (reuse for any file-watch daemon)
- chokidar was already in `package.json` and `node_modules` — always check before `npm install`.
- The watcher must bootstrap `.env` itself before requiring any module that reads `process.env` at call time. Pattern: copy the same .env loader block from server.js at the top of the file, before any `require()` that uses env vars.
- `awaitWriteFinish: { stabilityThreshold: 200, pollInterval: 100 }` — prevents partial-write events when agents write large files. Essential for followup files.
- `ignoreInitial: true` — critical: without this, chokidar fires "add" for every existing file on startup, spamming 549 Plane API calls.
- Debounce map pattern: `Map<filepath, NodeJS.Timeout>`. Cancel existing timer on new event; only sync after 500ms quiet period.

### Webhook-watcher cooldown to prevent feedback loops
- Problem: webhook handler writes `.md` → chokidar detects change → watcher re-pushes to Plane → Plane fires webhook again → infinite loop.
- Solution: cross-process cooldown file at `/tmp/plane-cooldown.json`. Webhook handler writes `{filepath: timestamp_ms}` after every `fs.writeFileSync`. Watcher reads this file on each event; skips the file if `Date.now() - ts < 2000`.
- Key constraint: when watcher and webhook handler are in **different** processes (they are here — deathboard.service vs plane-sync-watch.service), you CANNOT use shared in-memory state. Must use the filesystem IPC file.
- 2-second window is generous enough for chokidar debounce (500ms) + write stabilization (200ms) + event processing overhead.
- The cooldown file check is in `isInCooldown()`, the mark is in `markCooldown()` — both in server.js (inline, not imported from plane-sync-watch.js to avoid circular dependency).

### Plane webhook API: not available in Plane CE stable (2026-05-13)
- `/api/v1/workspaces/<slug>/webhooks/` → 404. Both workspace-level and project-level paths return 404.
- Plane CE stable (APP_RELEASE=stable as of 2026-05-13) does NOT expose a webhooks management REST API. Webhooks must be registered via Plane UI: Workspace Settings → Webhooks → Add.
- The webhook endpoint in server.js (`/webhook/plane`) is fully implemented and tested; it just needs to be registered manually.
- If/when Plane CE adds a webhooks API, the endpoint pattern will likely be `/api/v1/workspaces/<slug>/webhooks/` (POST with `{url, secret, events[]}` body) — try that first on future versions.

### CF Access bypass: dashboard-only for remote-managed tunnels
- Adding `/webhook/plane` to `CF_JWT_BYPASS_PATHS` in server.js bypasses the *server-side* JWT check — but CF Access intercepts at the edge, before the request reaches origin.
- For remote-managed tunnels, bypass rules must be added in CF Zero Trust dashboard: Access → Applications → find the board.runatyr.games app → add a "Bypass" policy scoped to the `/webhook/plane` path. Cannot be done via CLI without a CF API token scoped to Zero Trust.
- Mirror of how `/webhook/atlassian` and `/webhook/docuseal` are configured — Robert has done this before and knows the flow.

### .env inline comments break server.js parser
- server.js .env loader regex: `^([A-Z_][A-Z0-9_]*)=(.*)$` captures everything after `=` including inline comments.
- `PLANE_WEBHOOK_ENABLED=true   # comment` → value = `'true   # comment'` which != `'true'`.
- Rule: never put inline comments on active env var lines in .env. Put the comment on a separate `# comment` line above the var.
- Same applies to any .env file parsed with a naive `line.split('=', 2)` or similar non-shell parser.

### systemd PartOf= for satellite services
- `PartOf=deathboard.service` means plane-sync-watch will stop when deathboard stops. Good for dev (stop everything with one command) but means the watcher goes down if deathboard crashes.

## 2026-05-13 — Plane CE Pages API: auth wall, no webhooks, one-way push only (plane-pages-spike)
**Learned:** 2026-05-13 | **Project:** plane-pages-spike | **Category:** integration / plane / pages / auth

**Context:** Spiked Plane CE Pages API to evaluate feasibility of bidirectional wiki/skills filesystem ↔ Plane Pages sync (187 .md files). Full report at `assistant/plane_pages_spike.md`.

### Critical finding: Pages is NOT in the v1 API key namespace
- Plane CE has two API namespaces: `/api/` (web app, session cookie auth) and `/api/v1/` (API key auth via `X-Api-Key` header).
- Pages (`PageViewSet`) is registered under `/api/workspaces/<slug>/projects/<id>/pages/` — the session-auth namespace.
- The `/api/v1/` namespace (API key, used by the ticket bridge) has: issues, cycles, modules, stickies, states, members — **no pages**.
- Calling Pages endpoints with `X-Api-Key` returns 401. There is no workaround within the current CE release.
- Source: `plane.urls` routes `api/` → `plane.app.urls` (session) and `api/v1/` → `plane.api.urls` (API key). `plane.api.urls.__init__` has no page import.

### No page webhook events
- `Webhook` DB model has boolean flags: `project`, `issue`, `module`, `cycle`, `issue_comment`. No `page` flag.
- `webhook_activity` task routes on these flags — pages trigger nothing.
- Source: `apps/api/plane/bgtasks/webhook_task.py` and `apps/api/plane/db/models/webhook.py`.
- **Conclusion: no outbound events when pages change. Bidirectional is impossible without polling.**

### Session cookie impersonation workaround
- `/api/` namespace disables CSRF (`BaseSessionAuthentication.enforce_csrf` is a no-op).
- If you POST to `/auth/sign-in/` with email + password, you get a `sessionid` cookie that works for all `/api/` calls.
- This enables one-way push (filesystem → Plane) but: sessions expire, cookie must be refreshed (daily systemd timer), and it's tied to a real user account rather than a service token.

### Delete requires archive first
- `PageViewSet.destroy` checks `archived_at is None` and returns 400 if not archived first.
- Two-step: `POST .../archive/` then `DELETE .../`. Both are session-auth only.

### Hierarchy: parent_id works but list is root-only
- DB model has `parent` FK to self; `partial_update` accepts `parent` UUID.
- `list` view filters `.filter(parent__isnull=True)` — child pages are invisible to list. Must use `GET /pages/<page_id>/` to fetch children.
- For sync purposes: you can build hierarchy with parent_id, but list-based sync won't see children. Need to track page IDs in a local sync log.

### Content format
- `description_html` is the primary writable field — plain HTML string, no Prosemirror tooling needed.
- `description_binary` is Prosemirror binary (base64), used by Tiptap editor for live editing — ignore for sync.
- `access`: `0` = public (all project members), `1` = private (owner only). Default to `0` for wiki sync.

### external_id field exists on model but not serializer
- `Page` DB model has `external_id` and `external_source` fields — purpose-built for sync dedup.
- Neither field is in `PageSerializer` or `PageDetailSerializer` — not accessible via API.
- Use description footer `[external_id: wiki/deals/elias_ngc.md]` as dedup key instead (same pattern as ticket bridge).

- Pattern mirrors the docuseal webhook's "fail closed on missing secret" approach. Add both: the feature flag (enable the surface) AND the HMAC check (authenticate callers). Two separate concerns.
- Don't forget to add new webhook paths to `CF_JWT_BYPASS_PATHS` so CF Access doesn't redirect incoming webhook calls to the auth page.

- Batch in groups of 10 with 200ms inter-batch delay. Self-hosted Plane with Gunicorn workers=1 is easily saturated by parallel requests. Start conservative (200ms), tune down if fast.

## 2026-05-12 — Multi-site Atlassian via wrapper-script MCPs (Death Board / db-141)
**Learned:** 2026-05-12 | **Project:** Death Board (db-141) | **Category:** mcp / secrets / multi-tenant

### Problem
Claude.ai's Atlassian Rovo connector is **single-site by design** — one OAuth grant = one Atlassian site (`<sub>.atlassian.net`), and the claude.ai UI has one connector slot per service. Toggling Rovo from `badass-studios` → `aurorapunks` mid-session to process K2C standups kills the badass-studios surface. Two parallel sites = needs two parallel MCP surfaces.

### Pattern: parallel local MCPs alongside Rovo, wrapper-script secret loading
1. **Site allocation:** Rovo → heavier-traffic / richer-feature site (badass-studios). Local `@aashari/mcp-server-atlassian-jira` + `-confluence` MCPs → the other site (aurorapunks).
2. **Secret loading:** Do NOT put `ATLASSIAN_API_TOKEN` directly in `~/.claude.json` `env` blocks — that file is plaintext config (versionable, surfaceable in logs). Instead:
   - Keep the credential in a dedicated chmod-0600 file (`~/.claude/.atlassian-credentials.json`, single source of truth, same file other tools like `discord-bot.js` already read).
   - Write a thin wrapper at `assistant/bin/mcp-atlassian-<service>.sh` — reads token via `node -p "require('$CREDS').apiToken"` (no jq dependency, node is always present), exports env vars, then `exec npx -y @aashari/...`.
   - Point `~/.claude.json` `command` at the wrapper, leave `args: []` and `env: {}`. The JSON only references the path; the secret never lands in it.
3. **Permission gating:** Editing `~/.claude.json` is flagged as self-modification of agent config. Edits that write a secret to it get blocked even with user confirmation; edits that only change `command`/`args`/`env` (no secret payload) pass cleanly. Design the change to not require the secret in config and the gate becomes a non-issue.

### Two non-obvious gotchas
1. **Claude Code caches the MCP spawn config in-memory at session start.** After editing `~/.claude.json` + killing stale `npm exec` processes, Claude Code respawns them — but with the **old** cached command/env, not the new one on disk. Confirmed via `/proc/<pid>/environ`: token still empty, process tree still `npm exec @aashari/...` instead of going via the wrapper. **The user must restart Claude Code** for the new spawn config to take effect. Killing processes alone is insufficient.
2. **`pkill` exit code 144 ≠ failure.** When chained with other commands, the high exit code from pkill (matches killed) can propagate as a non-zero shell exit. Verify the actual outcome with a follow-up `ps`, not by the exit code.

### Verification path before "ship"
Don't wait for the Claude Code restart to confirm the token works. Do a direct curl smoke test:
```bash
EMAIL=$(node -p "require('/home/assistant/.claude/.atlassian-credentials.json').email")
TOKEN=$(node -p "require('/home/assistant/.claude/.atlassian-credentials.json').apiToken")
curl -s -u "$EMAIL:$TOKEN" "https://aurorapunks.atlassian.net/rest/api/3/project/KAN" | node -e '...'
```
Confirms token is valid + scopes are right before you ask Robert to restart anything. If curl fails, you debug now; if it succeeds, restart is the only remaining variable.

### Reusable beyond Atlassian
Same pattern fits any npx MCP that takes static secrets via env — GitHub API tokens, paid-tier API keys, anything where the credential should outlive the Claude Code session but not pollute `~/.claude.json`. Convention: wrapper at `assistant/bin/mcp-<provider>.sh`, secret file at `~/.claude/.<provider>-credentials.json` (chmod 0600), registry entry under `<provider>.<purpose>`. Cross-references db-116 (parallel registrations beat upstream fork for multi-tenant MCPs).

## 2026-05-12 — Cloudflare tunnel: remote-managed vs locally-managed (Plane deploy)
**Learned:** 2026-05-12 | **Project:** Plane deploy / plane.runatyr.games | **Category:** infra / cloudflare-tunnel

### Problem
Added `plane.runatyr.games → http://localhost:3779` to `/home/assistant/.cloudflared/config.yml`, ran `cloudflared tunnel route dns deathboard plane.runatyr.games` (DNS CNAME created cleanly), restarted `cloudflared` via systemd user service. Public requests still 404'd from Cloudflare's edge. `journalctl --user -u cloudflared` showed the loaded ingress did NOT include `plane.runatyr.games` even after restart — only the original four hostnames (board / hive / code / pitch). The file edit was a **silent no-op**.

### Root cause
The `deathboard` tunnel is **remote-managed**. Its ingress is owned by the Cloudflare Zero Trust dashboard (Networks → Tunnels → deathboard → Public Hostnames), not by the local `config.yml`. When cloudflared runs, it fetches the ingress config from Cloudflare's edge and ignores the `ingress:` block in `config.yml`. The local file's `tunnel:` and `credentials-file:` directives are still honored — that's why the tunnel comes up at all — but the routing list is ignored.

### How to tell which mode you're in (pre-flight check)
Don't trust the local file. Always verify against the live config cloudflared actually loaded:
```bash
journalctl --user -u cloudflared --no-pager | grep "Updated to new configuration" | tail -1
```
The JSON in that log line is the authoritative ingress. If a hostname is missing there, your local edit didn't take.

### Fix path
**Remote-managed tunnel:** add ingress via Cloudflare Zero Trust dashboard:
1. https://one.dash.cloudflare.com/ → Networks → Tunnels → click tunnel name
2. Configure → Public Hostnames tab → Add a public hostname
3. Subdomain + Domain + Service Type (HTTP) + URL (e.g. `localhost:3779`)
4. Save. Propagates to running connectors within ~10s — no cloudflared restart needed.

**Locally-managed tunnel:** edit `~/.cloudflared/config.yml`, then `systemctl --user restart cloudflared`.

### Trap for future agents
`cloudflared tunnel route dns` creates the DNS CNAME but does NOT register the hostname in the tunnel's ingress — these are two separate operations on Cloudflare's side. A successful `route dns` + edited `config.yml` + restarted cloudflared can all succeed while the public endpoint still 404s, because the actual routing decision lives in the dashboard.

## 2026-05-12 — Plane CE: SITE_ADDRESS is the *internal* Caddy bind port
**Learned:** 2026-05-12 | **Project:** Plane deploy / plane.runatyr.games | **Category:** infra / docker-compose / caddy

### Problem
After the tunnel was correctly routed, public requests reached the origin but got `502 Bad Gateway` (host = Error in Cloudflare's diagnostic page). Local `curl http://127.0.0.1:3779/` returned `Recv failure: Connection reset by peer`. The proxy container was running and healthy; Caddy logs showed `server running` on `:3779` but no incoming request logs.

### Root cause
Two ports were involved and they didn't match:
- Plane's `docker-compose.yaml` maps host `127.0.0.1:3779 → container:80` (hard-coded port 80 inside).
- `SITE_ADDRESS` in `plane.env` configures Caddy's *internal* bind. We had set it to `:3779` thinking it was the external/public port.
- Result: nothing listening on container `:80`, every connection RST'd.

### Fix
Set `SITE_ADDRESS=:80` in `plane.env`. The host-side port (3779) is controlled by the docker-compose `ports:` mapping, not by Caddy's env.

### Subtle second gotcha — env changes need *recreate*, not *restart*
`docker compose restart <svc>` keeps the existing container and only restarts the process — environment from `.env` is NOT re-read. To pick up env-file changes, use `docker compose up -d <svc>` which recreates the container with the new env. Cost us ~3 minutes wondering why `SITE_ADDRESS=:80` didn't take effect.

### Pre-flight checklist when wiring a new Plane-like compose stack behind Cloudflare
1. `docker port <container>` — confirm host:container port mapping
2. `docker exec <container> netstat -tln` — confirm the app inside is bound to the *container* port from step 1
3. Local `curl -sI -H "Host: <public>" http://127.0.0.1:<host-port>/` — confirms origin works before adding Cloudflare into the loop
4. Public `curl -sI https://<public>/` — confirms tunnel + edge

If step 3 fails but the container is up, the issue is internal-bind-port mismatch (this learning). If step 3 works but step 4 fails, the issue is the tunnel (the cloudflare-tunnel learning above).

## 2026-04-24 — /schedule (remote agents) ≠ scheduled VPS work; use systemd user timers + Claude CLI for hybrid (ops-security-automation)

**Learned:** 2026-04-24 | **Project:** ops / security-automation | **Category:** scheduling architecture / remote-vs-local agents

**Context:** Robert asked to schedule a recurring weekly security screening of the VPS, Claude directory, and git repos. First instinct was to invoke the `/schedule` skill which is meant for "scheduling background agents." Hit a fundamental mismatch in the skill flow that's worth capturing — the design split between *remote* (Anthropic-cloud sandboxes) and *local* (VPS-side cron/systemd) routines is critical and easy to confuse.

**The distinction:**
- **`/schedule` = REMOTE agents.** Run in Anthropic's CCR cloud sandbox via the `RemoteTrigger` API. Each fire spawns a fresh isolated session with its own git checkout + tools + MCP. CANNOT access the VPS filesystem, `systemctl`, `journalctl`, local services, or `~/.claude/`. Right tool for: GitHub-PR-driven work, periodic refactors against a public/private repo, anything that lives in a git remote.
- **systemd user timer + bash + `claude -p` (or just bash) = LOCAL.** Runs on the VPS as user `assistant`. Full access to the filesystem, services, and OAuth-stored credentials. Right tool for: anything that audits, triggers, or modifies VPS state — security screening, log triage, cron jobs replacing crontab, periodic data collection from local sources.

**Symptom that surfaces the confusion:** if the prompt mentions paths under `/home/assistant/`, references `journalctl --user`, runs `gitleaks` against local repos, calls `ss -tlnp`, or hits `localhost:3777` — it's NOT a remote-routine candidate. Stop the `/schedule` flow before creating anything; remote agents would just fail on the first local syscall and you'd burn one routine slot per failure.

**Hybrid pattern that works (T1/T2 security screening, this session):**
1. `~/.config/systemd/user/<job>.timer` with `OnCalendar=Sun *-*-* 05:00:00 Europe/Stockholm` — systemd handles DST automatically when an inline timezone is given.
2. `<job>.service` is `Type=oneshot`, calls a bash script in `/home/assistant/projects/.security/`.
3. Bash collector dumps mechanical data (gitleaks, ss, perms, journalctl greps) to a timestamped raw file in seconds.
4. Bash then invokes `claude --model sonnet -p "$(cat prompt-X.md)\nREPORT_PATH: $REPORT" --allowedTools Bash,Read,Write,Edit` to synthesize + write a DB ticket. LLM is invoked exactly once per run, not in a polling loop.
5. Baselines (systemd units, /etc/passwd, authorized_keys, last-run timestamp) live in the same dir; the script auto-creates them on first run, so the timer is self-bootstrapping. No "manual setup" step.

**Why hybrid not pure-bash or pure-LLM:**
- Pure bash: cheap, but priority tiering, narrative summaries, redacted gitleaks output, and conditional Discord pings are all judgment-heavy. Encoding all of those rules in bash + jq is brittle and unreadable.
- Pure LLM: works but burns tokens on cheap mechanical things (running ss, parsing /etc/passwd) the model is not faster at than bash. Also slower per run, which matters for monthly deep audits.

**Other systemd timer details that are easy to miss:**
- `RandomizedDelaySec=5min` on the timer prevents thundering-herd at 05:00 — gives a few minutes of natural jitter without needing a cron-like `0,3,6 * * *` mess.
- `Persistent=true` means if the VPS was off at the scheduled time, run it as soon as possible after boot. Cheap insurance.
- For one-shot: `OnCalendar=2026-05-08 09:00:00 Europe/Stockholm` is sufficient — the timer just won't refire because the calendar event is in the past after it runs. No `RemainAfterExit` or self-disable trickery needed.
- Linger MUST be on for the user (`loginctl show-user assistant -p Linger` should say `Linger=yes`) or user timers won't fire when the user isn't logged in. On this VPS it's already enabled because deathboard.service is a user unit. New VPS deployments need `loginctl enable-linger <user>` before user timers will work.

**Ticket-ID regex constraint (from server.js, also good to remember):** `^[a-z]{2,6}-\d{3}(-[a-z0-9-]+)?$`. Date-based slugs like `sec-NNN-weekly-20260503` work because the slug part accepts digits. Do NOT use `sec-20260503-weekly` — fails the regex (the digits-after-prefix segment must be exactly 3 chars). The script picks `NNN` by enumerating `sec-*.md` and incrementing the max.

## 2026-05-08 — Discord NEW-alert spam loop: catch-block ate the snapshot mark (Death Board)

**Symptom:** `apb-003` Discord notification "🆕 NEW: …" reposted every 15 minutes for hours (07:58 → 09:13 visible to Robert). Same ticket, same payload, no underlying state change.

**Root cause** in [server.js:3686-3813](assistant/server.js#L3686-L3813):
1. Routine builds `currentSnapshot`, diffs against `discordBot._lastSnapshot`, pushes `{type:'new', fu}` for any id missing from prev.
2. Inside the `for (const change of immediateChanges)` loop, `await discordBot.postAlert(fu, 'NEW')` runs **first**, then the next line marks `_lastSnapshot[fu.id] = currentSnapshot[fu.id]`.
3. The whole 5b block is wrapped in one outer `try { … } catch (err) { console.log('[Discord] Alert posting error: …') }`. When `postAlert` threw `Missing Access` (one of the channels in the multi-channel send had revoked perms), the throw bypassed the snapshot-mark line.
4. Next routine run: `prev[fu.id]` still missing → diff still says `{type:'new'}` → fires again → throws again → snapshot still not marked → infinite loop.

journalctl confirmed every 15-min run logged `[Discord] Alert posting error: Missing Access`. The project-channel send succeeded (so Robert saw spam) while the alerts/tasks-channel send failed (so the catch tripped).

**Fix shipped:** wrapped each `postAlert`/`postToDone` call in its own try/catch, with the `_lastSnapshot[fu.id] = currentSnapshot[fu.id]` mark moved outside the try so it always runs. Same pattern applied to the alert-changes loop ([server.js:3777-3801](assistant/server.js#L3777-L3801)). Restart reseeded the snapshot (`Seeded snapshot with 506 follow-ups`), spam stopped.

**Underlying perms problem still open** at db-124 — bot needs to figure out which channel/guild throws "Missing Access" so future NEW/OVERDUE alerts actually deliver everywhere they're supposed to.

### Cross-project lesson: "post + mark posted" must be all-or-nothing per-item, not per-loop

Whenever you have a `for (item of items) { await side_effect(item); markDone(item); }` pattern wrapped in one outer try/catch, a partial failure on item N skips `markDone(item N)` AND every subsequent item. For state-change broadcasters (Discord alerts, Slack posts, email send, kanban auto-action triggers) the failure mode is the same: one bad delivery → infinite retry on every subsequent run. Defaults to apply:

1. **Per-item try/catch.** A bad post for ticket X must not break the loop for ticket Y, and must not block the snapshot/marker update for X itself. Choose a policy: mark-on-failure (best for spam-prone broadcasters — accept the rare lost notification) or stay-unmarked-on-failure (best for transactional sends with idempotent retry semantics + a backoff).
2. **Multi-channel sends should not throw monolithically.** `postAlert` calls `postToTasks` + alerts channel + project channel. If any one throws, the rest are skipped AND no marker fires. Each `channel.send` should be its own try/catch with channel-id logged on failure, so a single revoked perm doesn't poison the others.
3. **Log enough to bisect.** "Alert posting error: Missing Access" with no ticket id, no channel id, no severity is useless — Robert lost hours to a recurring alert before the symptom was visible enough. New log line includes `fu.id (change.type)` minimum; db-124 will add channel id once we add per-`channel.send` wrapping.
4. **Liveness-vs-readiness still applies.** Same shape as the WhatsApp zombie (above): the system reported `success` at one layer (project-channel send went through) while another layer was silently broken (alerts-channel perm revoked). Default: any multi-target broadcast should expose per-target health, not a single boolean.

## 2026-05-07 — Puppeteer daemon state tracking: status probes must actually probe, recovery wrappers must wait for ready (db-117, whatsapp-bridge)
**Learned:** 2026-05-07 | **Project:** Death Board / db-117 | **Category:** infrastructure / puppeteer / state-tracking / error-recovery

**Context:** WhatsApp bridge silently entered a stale state where `state.ready=true` but all Puppeteer calls failed with "detached Frame" errors. Root cause: the bridge's `ready` flag was set once on first `ready` event and never invalidated, even when Chromium disposed the underlying page during a reconnect. Status endpoint returned stale state, MCP calls failed silently.

**Five-layer fix pattern for persistent Puppeteer daemons:**

1. **Status probe must actually probe.** Don't just return cached state — call a cheap Puppeteer method (`client.getState()` or `page.evaluate(()=>1)`) on each `/status` request, cache result for 5s, and flip `state.ready=false` if probe fails. Without this, status endpoints lie after Chromium crashes.

2. **Drive state from lifecycle events.** Hook the client's state-change events (e.g., `change_state` in whatsapp-web.js) to write state.json. On disconnected states (`OPENING`/`PAIRING`/`UNPAIRED`), set `ready=false` immediately. On `CONNECTED`, verify via probe before trusting it.

3. **Detached-frame auto-recovery.** Wrap every Puppeteer-backed endpoint with a recovery wrapper that catches `detached Frame`, `Target closed`, `Protocol error`. On detection: `client.destroy()` → wait for `ready` event (not just `initialize()` return) → retry original request once. Cap to 1 recovery per 5 min to prevent thrash. **Critical:** must wait for the 'ready' event, not just `await client.initialize()` — the initialize promise resolves before auth completes.

4. **Watchdog with process.exit.** Every 60s, probe `client.getState()`. On 3 consecutive failures, `process.exit(1)` so systemd restarts the service. Belt-and-braces with #3 — catches cases where recovery wrapper doesn't fire (no request traffic during failure window).

5. **Liveness probe reflects watchdog.** `/health` endpoint (unauthenticated, used by monitoring) returns 503 if watchdog flagged unhealthy. Death Board / Prometheus can surface this without parsing logs.

**Anti-pattern:** First version of the recovery wrapper called `await client.destroy(); await client.initialize();` then immediately retried. The retry failed with "Cannot read properties of undefined (reading 'getChats')" because `initialize()` hadn't reached `ready` yet. Fix: wrap `initialize()` in a Promise that listens for the `ready` event (30s timeout, also listens for `auth_failure` to fail fast).

**Verification test:** Kill the Chromium renderer PID (`kill -9 $(pgrep -f 'chrome.*renderer' | head -1)`). Next MCP call should either (a) succeed after ~4s (auto-recovery), or (b) fail cleanly with a recovery error (if on cooldown). If it fails with "detached Frame" leak, the wrapper isn't wired. If it fails with "undefined" errors, the wrapper isn't waiting for ready.

**Generalization:** This pattern applies to any long-lived daemon wrapping a browser automation library (Puppeteer, Playwright, Selenium). The common trap: trusting lifecycle hooks alone. Always (1) probe on status check, (2) drive state from events, (3) wrap calls with recovery, (4) watchdog with exit, (5) surface health via unauthenticated endpoint.

**How to apply:** When building a persistent Puppeteer/Playwright daemon (MCP bridge, scraper service, automation worker), ship all 5 layers from day 1. Don't wait for the first "it stopped working and I didn't notice" incident. The recovery wrapper (~40 LOC) and watchdog (~20 LOC) are the cheapest insurance.

## 2026-05-06 — Multi-tenant MCP servers: parallel registrations beat fork (db-116, slack)
**Learned:** 2026-05-06 | **Project:** Death Board / db-116 | **Category:** mcp / architecture

When an MCP server reads creds from a single env or file but Robert needs N tenants (workspaces, accounts, orgs), the instinct is to fork upstream and add multi-tenant support. **That's usually wrong.** Claude Code prefixes tools with the registration name (e.g., `mcp__slack-rawfury__conversations_history`), so N parallel entries in `~/.claude.json` each get their own tool namespace — no collision. db-116's original ticket recommended a fork on the false assumption tools would collide; DevOps overrode with parallel registrations and shipped in one session.

**Why:** Fewer moving parts: no fork to maintain, no upstream-merge work, no API change in the binary. Disk caches namespace cleanly when the server's keyed by tenant ID (Slack uses `~/.cache/slack-mcp-server/<TEAM_ID>_*`). Per-tenant disable is trivial — comment out one entry. Tool count multiplies but ToolSearch defers schemas, so only names live in context.

**How to apply:** Pattern is: cred file becomes an array, launcher script takes a `<key>` arg and picks the entry, `~/.claude.json` gets N entries each invoking `launcher.sh <key>`. Reach for a fork only when (a) the upstream binary genuinely can't be re-invoked per tenant (rare) or (b) the disk-cache layout doesn't namespace and would corrupt across tenants. Likely candidates beyond Slack: Linear, Atlassian (across sites), GitHub (across orgs), any per-workspace SaaS.

## 2026-05-06 — Shell field-splitting: never use whitespace delimiters with possibly-empty fields (db-116, mcp-slack-launcher.sh)
**Learned:** 2026-05-06 | **Project:** Death Board / db-116 | **Category:** shell / parsing

First implementation of `mcp-slack-launcher.sh` used `\t` as the JSON-pick delimiter and `IFS=$'\t' read -r ws_key ws_name xoxc xoxd team_id`. Tab is **IFS-whitespace**, so consecutive empty fields collapse and shift later fields into earlier slots — placeholder workspaces (empty xoxc + empty xoxd) printed as `unknown` instead of `Raw Fury`, because `team_id` slid two slots forward. Switched to `|` (non-IFS-whitespace, cannot appear in xoxc/xoxd/team-id tokens) and the bug vanished.

**Why:** `IFS` whitespace is *flexible* — multiple consecutive whitespace chars collapse to one separator, and leading/trailing whitespace is ignored. Non-whitespace IFS is *strict* — exactly one separator per field, empty fields preserved. Anyone parsing JSON-derived data through `read` will hit this if any field can be empty.

**How to apply:** For shell field-splitting on JSON-derived data (jq output, node `-e` output, etc.) where any field may be empty, **never use `\t`, space, or newline as the delimiter.** Use `|`, `:`, `\x1f` (unit separator), or `\x01` — characters that won't appear in tokens and aren't IFS-whitespace. If ambiguous, prefer `\x1f` (literally designed for this).

Wired into `submitAnswer()` first; should be wired into other PUT/POST handlers too (composer, status changes, plan, etc.) — followup db ticket potential. Wrapped, not replaced, so genuine non-auth network errors still show a useful toast when /api/health succeeds.

Wasted ~3 minutes inspecting routes before checking journalctl for the actual request. Rule: **for any "form submit failed in the UI" report, the FIRST diagnostic is always `journalctl --user -u deathboard.service --since 'Nm ago' | grep <method>`. If the request isn't in the log, the server didn't see it — stop looking inside the server.**

That landed as a real answer in the YAML AND added an activity log entry "Robert: Answered ... → test". ## 2026-05-06 — Daily briefing double-fire: flock catches simultaneous, not sequential — defend in 3 layers (db, daily-briefing.sh)
**Learned:** 2026-05-06 | **Project:** Death Board / daily-briefing | **Category:** infrastructure / cron / idempotency

**Context:** On 2026-05-06 at 07:00 UTC, two briefing instances ran in parallel. Cron's claude (per `daily-briefing.sh`) created surviving tickets at 07:03:54 (swa-003, dbl-003, db-109/110/111). A SECOND claude session created 5 dup tickets at 07:06:36 (db-112/113/114, dbl-004, db-115), self-noticed via reading `daily_briefing.md`, and cleaned up its dups by 07:10:14. The deprecated cloud `/schedule` routine `trig_01XiRJyL9PvKVECDqdNscLRc` was already disabled (since 2026-04-29), so it wasn't the cloud-routine bug from db-002 redux. Most likely source of the second instance: Robert's morning manual Claude Code session firing the same briefing prompt at the same hour as cron — or any other invocation path that bypasses the wrapper's flock.

**Why flock alone wasn't enough:** the existing `flock -n 200` on `/tmp/daily-briefing.lock` in `daily-briefing.sh` only catches *simultaneous* invocations of the **same wrapper script**. It does nothing against (a) sequential reruns minutes later, (b) any other code path that shells out to claude with the briefing prompt, or (c) cloud-routine WebFetch POSTs to `/api/briefing/save`. Need defense in depth.

**Three guard layers I shipped (ordered cheap → expensive failure):**

1. **Wrapper script `daily-briefing.sh`** — early-abort if `head -1 daily_briefing.md` already contains today's UTC date. Bypass with `--force` or `--smoke`. Catches the cron path before spawning claude (saves ~$0.50/run + zero LLM-side risk of dups). Verified by re-running the wrapper today: exits in 0s with "briefing already done for 2026-05-06 — skipping". `--smoke` exemption preserves smoke-test flow.

2. **Briefing prompt Phase 0** — same `head -1` check via Bash inside the prompt. Catches *any* invocation method (Robert's manual session, accidental retries, future cloud routines) before phase 1 runs gmail/calendar tools. Critical line: "Do NOT proceed to Phase 1, do NOT call gmail/calendar tools, do NOT create tickets." Without this, a manual-session run that bypassed the wrapper would still create dups.

3. **Server.js `/api/briefing/save` and `/api/briefing/start-session`** — both endpoints reject 409 if today's daily-briefing already exists / start-session already fired. `save` checks `head -200 chars` of `daily_briefing.md` for today's UTC date string; `start-session` writes a per-day marker file `assistant/.briefing-session-YYYY-MM-DD.marker` and rejects subsequent calls. Includes a sweep that deletes yesterday's markers on each call so the dir doesn't accumulate. `force: true` body flag bypasses save.

**Bonus fix (the bug Robert noticed in the screenshot):** `start-session` was calling `execFile('code', ...)` and `execFile('claude', ...)` with no PATH. Systemd-spawned deathboard.service has a stripped PATH — neither `code` (which doesn't exist; the box uses `code-server`) nor `claude` (which lives at `/home/assistant/.local/bin/claude`) resolved → silent ENOENT. Fixed by hardcoding absolute paths (`CODE_BIN=/usr/bin/code-server`, `CLAUDE_BIN=/home/assistant/.local/bin/claude`) and passing an explicit `PATH` in the child env.

**How to apply:** Any time you build a "run once a day" task that can be invoked from multiple paths (cron + manual session + cloud routine + UI button), don't rely on a single guard. The pattern:
- Wrapper: cheap idempotency check (file-mtime / header string) — bail before spawning the LLM.
- Prompt: Phase 0 self-check — bail before writing/calling tools.
- Server endpoint: 409 on duplicate per-day write — last line of defense for HTTP callers.

**Anti-pattern I almost shipped:** "just delete the old cloud routine" — the cloud routine was already disabled. The actual race was another claude session entirely. If I'd stopped at "kill the cloud routine," the next dup would have happened tomorrow morning when Robert opened his session.

**Cross-cutting note for future cron design:** when a system-spawned process needs to exec arbitrary user-installed binaries (claude, code, gh, etc), always pass absolute paths AND an explicit `PATH` env. Systemd's default service-level PATH is minimal (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`) — anything in `~/.local/bin` is invisible.

## 2026-05-06 — Scope-narrow official API > proxy-spending on cloud-IP-blocked services (db-113)
**Learned:** 2026-05-06 | **Project:** Death Board (db-112 → db-113) | **Category:** architecture

**Context:** db-112 surfaced that LinkedIn fingerprint-blocks Hetzner AS24940 on auth-strict endpoints (`ERR_TOO_MANY_REDIRECTS` on `/messaging/`). The default reflex was "buy a residential proxy ($50-200/mo)". Robert pulled the conversation toward a fourth option: don't pay to evade the block, scope-narrow the official API surface to cover the critical path and accept downtime on the rest.

**Learned:** When a platform (LinkedIn, similar) blocks your VPS IP on auth-strict endpoints, check whether the OFFICIAL API surface covers the critical-path slice as the *member themselves* before paying for evasion. LinkedIn `w_member_social` is self-serve OAuth (no Partner Program approval); covers post-as-self + own-profile + own-analytics. Combine with the platform's official Data Export + email-notification side-channel (via Gmail) to cover own-history and incoming-message awareness. Reserve scraping for the genuinely unavailable surfaces (other people's profiles, search) and accept its downtime by removing it from the critical path.

**Why this is durable:** The same pattern almost certainly applies to Twitter (member-as-self via OAuth + paid tier for scraping replaces blocked IPs), Instagram (Graph API for own posts/insights + scraping for competitor research), Reddit (PRAW for own activity + scraping for cross-sub research). When designing any new platform integration where the default community pattern is scraping, write the use-case-vs-API-scope matrix BEFORE picking the auth strategy. If the official API covers ≥60% of the critical path, never start with scraping.

**How to apply:** Two-column matrix at the start of any platform integration ticket:
- Left column: each use-case (post, read own DMs, read other profiles, search, analytics, etc.)

## 2026-05-06 — Multi-workspace MCP via parallel instances + distinct names beats forking when the upstream is single-tenant (db-116, slack)

**Project:** Death Board / db-116
**Category:** MCP architecture, namespace, fork-vs-instance trade-off

**Context:** db-108 installed `korotovsky/slack-mcp-server` for one Slack workspace (Aurora Punks). Six more workspaces (Raw Fury, Deconstructor of Fun, Upstream Arcade, Overwolf, Behold, Bright Gambit) were needed for BD + PM agent surfaces. The ticket presented three options: (A) parallel MCP instances per workspace, (B) fork upstream to add multi-workspace support, (C) PR upstream. Ticket recommended B citing "tool namespace collision" as A's killer con.

**The con was wrong.** "Tool namespace collision" only applies if all instances register under the same key in `~/.claude.json`. Registering them as `slack-aurora`, `slack-rawfury`, `slack-dof`, etc. produces distinct tool prefixes (`mcp__slack-aurora__channels_list`, `mcp__slack-rawfury__channels_list`, …). Claude Code's MCP runtime keys tools by server registration name — distinct names = distinct namespaces, automatically.

**The other concern is real but defanged:** tool surface multiplies 7× (~12 tools per workspace × 7 = ~84 tools). But MCP tools are deferred via ToolSearch on this VPS — the cost is name-only context, fetched on demand. Verified by checking the deferred tools list in an active session: every `mcp__slack__*` tool was deferred. Multi-workspace expansion changes the count but not the runtime cost shape.

**Cache file collision is also a non-issue for this binary specifically:** `slack-mcp-server` writes `~/.cache/slack-mcp-server/T<team_id>_users_cache.json` and `T<team_id>_channels_cache_v2.json` — auto-namespaced by team ID. Different workspaces = different team IDs = different files. Verified by inspecting strings in the binary.

**Forking would have been worse:** `slack-mcp-server` is a Go binary distributed as a precompiled npm package (linux-amd64 prebuilt). Forking to accept multiple `(workspace, xoxc, xoxd)` triples means setting up a Go toolchain on the VPS (currently nonexistent), building per-platform, and tracking upstream releases. Plus every tool call in the agent prompt would need an explicit `workspace` parameter — more friction at call time, not less. Not worth it for ≤10 workspaces.

**The pattern that worked:**
- One launcher script taking a workspace key arg (`mcp-slack-launcher.sh aurora`).
- One creds JSON array file (one entry per workspace, keyed by `workspace_key`).
- N entries in `~/.claude.json` under different names, each invoking the launcher with its key.
- Per-workspace cred-set helper for atomic token writes (no hand-editing JSON).

**How to apply:** When asked to add multi-tenant support to a single-tenant MCP, the order of consideration should be:
1. Can we run N parallel instances with distinct registration names? Default yes.
2. Are the binary's per-process side effects (caches, locks, ports, sockets) namespaced or namespaceable via env vars? Almost always — modern binaries respect `XDG_CACHE_HOME` or include tenant IDs in cache filenames.
3. Is the tool surface multiplication a runtime problem? On VPSes with ToolSearch deferred loading, no. On hosts that load all MCP tools eagerly, possibly — but that's an Anthropic-side concern, not a forking justification.
4. Only if 1-3 fail, fork. And even then, prefer JS/TS forks over Go/Rust forks (lower toolchain overhead).

The mental model: **MCP server name IS the workspace dimension.** You don't need to invent a `workspace` parameter inside the protocol — you put the dimension in the server registration name and let the runtime route. Same as how `mcp__gmail__*` and `mcp__claude_ai_Gmail__*` coexist — different "instances" of Gmail by registration name.

**Tags:** mcp, multi-workspace, namespace, fork-vs-instance, slack, korotovsky, parallel-instances, deferred-tools, single-tenant-binary, db-116

## 2026-05-06 — Bash IFS-whitespace trap: tab-delimited fields collapse when fields are empty (db-116, mcp-slack-launcher)

**Project:** Death Board / db-116
**Category:** shell scripting, parsing, JSON-from-shell

**The bug:** Wrote a launcher that piped JSON-array-pick output through `IFS=$'\t' read -r XOXC XOXD WS_NAME TEAM_ID <<< "$PICK"`, where the node program emitted tab-separated values. For populated workspaces it worked. For placeholder workspaces (empty xoxc, empty xoxd, populated workspace_name, empty team_id), the workspace name printed as "unknown" instead of "Raw Fury". Output was `\t\tRaw Fury\t\n`, but read assigned `XOXC=Raw`, `XOXD=Fury`, `WS_NAME=""`, `TEAM_ID=""`.

**Root cause:** Bash treats space, tab, and newline as **IFS whitespace** when they appear in `$IFS`. IFS-whitespace runs are collapsed to a single delimiter and stripped from the start/end of the input, ON TOP of being used as a delimiter. So `\t\tRaw Fury\t` is parsed as the fields `Raw`, `Fury`, ``, `` — not what you'd expect from "tab-separated."

This only matters when fields can be empty AND adjacent. With non-empty fields the collapse is a no-op.

**Fix:** Switch to a non-whitespace delimiter (`|`, `:`, or any byte that won't appear in your data). Tokens never contain `|`, so the fix was a one-character change. Re-tested: empty fields preserved, named workspace surfaces correctly in error messages.

**How to apply:**
1. **Default to non-whitespace IFS for structured shell parsing.** `\t` feels natural but is a footgun the moment any field can be empty. `|` or `\x1f` (US separator, ASCII 0x1f) is safer.
2. **If you must use `\t`:** read into a single var and split with parameter expansion (`${PICK%%$'\t'*}`, `${PICK#*$'\t'}`) — those don't collapse runs.
3. **Quick smoke test:** before trusting your `read` parser, throw an empty-field case at it. If your code path can produce `\t\tx\t`, test that exact string.

This is generic enough to bite anywhere shell consumes tab-separated output (`cut`, `awk`, `read`). The fix is always: pick a delimiter that's not in IFS-whitespace.

## 2026-05-06 — Triangulate to verify a side-effect cron is alive (db-115, Death Board)

**Source project:** Death Board (db-115, Pleo receipt-forward closeout)
**Category:** monitoring / verification pattern

**Problem:** A scheduled cron's "is it actually firing?" question is annoyingly hard to answer when the cron is conditional (only fires when input X exists). The 2026-04-30 one-shot verifier for the Pleo receipt-forward path returned **INCONCLUSIVE** — not because the path was broken, but because no Pleo-eligible receipts arrived in the verifier's window. Single-signal verifiers can't distinguish "broken" from "nothing to do."

**Pattern: triangulate three independent signals before declaring a verdict.** For any side-effect-producing routine (forwards, posts, archives, syncs), pick signals that fail independently:

1. **External authoritative source** — for an outbound action, query the destination. (Here: Gmail Sent search `to:forward@fetch.pleo.io newer_than:7d`.) This is the strongest signal because it bypasses your code entirely.
2. **Local ledger file** — most "did I do X?" routines write a dedupe ledger. Check the ledger's *modtime* AND *content tail*. Modtime alone can be misleading (file touched without write). Content tail gives you per-action timestamps.
3. **Journal / structured log** — `journalctl --user -u <service> | grep <signal>` for routine-emitted lines like `Receipts: N`. This catches the "ran but did nothing" case.

**Decision rule:**
- ≥2 signals positive → path verified alive.
- All 3 negative AND input-side has data → real bug, file new ticket.
- All 3 negative AND input-side empty → still inconclusive; trigger a synthetic input rather than wait for nature.

**Anti-pattern:** don't schedule a one-shot verifier with a date-based cron line (`0 9 30 4 *`). It self-deletes only on PASS, so an inconclusive verdict leaves it sitting in crontab for a year. If you need ongoing visibility, schedule a *recurring* sanity-check that alerts on prolonged silence (e.g. weekly Pleo check: alert if zero Sent forwards in 7 days while inbox shows receipts). The recurring version doubles as monitoring.

## 2026-05-06 — Approve & execute has no per-ticket debounce — parallel-click spawns multiple agents (db-115, Death Board)

**Source project:** Death Board (db-115 closeout, observed in activity log)
**Category:** platform / UX gap

**Symptom:** db-115 activity log showed three closeout sessions firing within 10 minutes (18:42, 18:45, 18:52) plus a fourth resumed VS Code session. All four did the same Pleo verification, cron cleanup, and file-deletion work. The first to acquire each side-effect "won"; the rest were no-ops on already-clean state.

**Root cause (refined after reading server.js):** Server.js DOES have a per-ticket lock — `findActiveSession(id)` at line 421, called from `/plan`, `/start-session`, `/execute-now`, `/execute-plan`. The lock works correctly **while the process is alive**. The hole is the *gap between exit and second click*: idempotent closeout work finished in seconds, so by the time the user re-clicked, `findActiveSession` returned null and a fresh agent spawned. UX side: the button doesn't latch into "running…" state immediately, so a user re-clicks expecting feedback.

**Fix shipped 2026-05-06 (db-115):** Added `findRecentCompletion(fullId, cooldownMs)` that searches `completedProcesses` (the recent-completed log) for a matching entry within `cooldownMs`. Wired into all four spawn endpoints after the `findActiveSession` check: 30s cooldown for `/plan` and `/start-session` (planning is iterative), 60s for `/execute-now` and `/execute-plan` (execute paths have side effects). Bypassable with `{force:true}` body opt, mirroring the existing `findActiveSession` force-restart contract. Returns `409 { error: 'recently_completed', completed_at, hint }`.

**Why it matters:** Most agent work is idempotent (re-running the closeout was harmless), but for non-idempotent actions (sending an email, creating a ticket, posting to social), parallel spawns will produce duplicates. Robert's existing [[feedback_ticket_number_collision]] memory documents the same failure mode for ticket creation — same root cause, different surface.

**How to apply:**
1. **Active-session locks alone aren't enough.** A liveness probe (`process.kill(pid, 0)`) only catches in-flight work. For idempotent or fast-finishing routes, you also need a *post-completion* cooldown — query the recent-completed log, refuse re-spawn within N seconds. Cheap to add, catches the entire class of double-click races.
2. **Recognize the pattern in any spawn-on-click endpoint.** Email-send, ticket-create, draft-publish, agent-spawn — all need both layers (live lock + post-completion cooldown), or a client-side debounced button. Server-side is preferable because it survives multi-tab/multi-device use.
3. **Better fix** (UX, future work): kanban button enters a "running…" disabled state on click, polls `/api/followups/:id` for `routed_agent` change, latches green when the agent completes. Removes the user-side ambiguity that drives re-clicks in the first place. Belongs in UIbot's queue.
4. **Cross-project lesson:** when adding any "fire this once on click" endpoint, audit for both windows: in-flight collision AND post-completion bounce. The cooldown is one helper + one if-block per endpoint — small enough that there's no excuse to skip it.

## 2026-05-05 — Discord bot multimodal vision shipped via stream-json (db-107)

**Learned:** 2026-05-05 | **Project:** Death Board (db-107) | **Category:** discord, vision, claude-cli, stream-json, system-prompt

**Stream-json input format that works (verified end-to-end):**

```json
{"type":"user","message":{"role":"user","content":[
  {"type":"text","text":"<the prompt>"},
  {"type":"image","source":{"type":"base64","media_type":"image/png","data":"<base64>"}}
]}}
```

One JSON object per line, written to stdin, then `stdin.end()`. Output is NDJSON; the final `{"type":"result", ...}` line carries the same `result`, `usage`, `total_cost_usd`, `session_id`, `stop_reason` shape as the text-mode envelope — meaning the existing parser-fallback (`for line in lines.reverse(): if line.includes('"type":"result"')`) just works for both modes. 1. `--input-format stream-json` REQUIRES `--output-format stream-json` (CLI errors out otherwise). They're paired — can't use json output with stream-json input.
2. `--verbose` is needed alongside `--output-format stream-json --print` for the result line to actually contain the assistant's text. Without it I got partial messages but no terminal `result` envelope.

Discord CDN URLs are signed but valid for the bot's request lifetime. Cap total image bytes at 5 MB across attachments per turn — Haiku 4.5 with a ~370 KB PNG was ~$0.08 cold / ~$0.009 warm (1h cache hit).

**System-prompt patterns that fix interrogative intake:**
- Explicit "draft-first, confirm-once" rule with the literal embed shape baked in. Without this, Haiku defaults to turn-by-turn slot-filling on ticket creation intents — three round-trips instead of one.
- Single-match project default rule: "if exactly one prefix matches case-insensitive substring or known alias, default to it silently — only ask on genuine ambiguity." Haiku is otherwise too cautious and asks "which Elias project?" when there's only one Elias prefix.
- "Reading attached images" rule: tells Claude to extract image content as primary context, not ask "what's in the image?"

**How to apply on future intake-flow work:**
- When a CLI helper bakes a giant text prompt and you need to add multimodal: the smallest diff is a sibling stream-json branch keyed off "any image block in messages." Keep the text path identical so non-multimodal traffic doesn't regress.
- Test both branches with a tiny smoke harness (instantiate the bot class, stub `discord.js`, call `callClaudeWithTools` directly with synthetic messages) — much faster than restart-and-DM-the-bot.
- When an LLM is asking too many questions, the fix is usually system-prompt explicitness, not new tools or new code paths. Show it the exact shape of the response you want.

## 2026-05-05 — WhatsApp-on-VPS bridge (db-086) + Slack parity ticket (db-108)

**Project:** Death Board / shared tooling
**Category:** integration architecture, MCP, systemd, browser-automation services

### What shipped

1. **Persistent WA Web bridge daemon** at [`assistant/whatsapp/bridge.js`](../../../projects/assistant/whatsapp/bridge.js) — owns one whatsapp-web.js client + Puppeteer Chromium, exposes a small HTTP API on `127.0.0.1:4501` with bearer-token auth (token auto-generated to `~/.claude/.whatsapp-bridge-credentials.json` 0600). LocalAuth session in `assistant/whatsapp/.wwebjs_auth/`.
2. **Stdio MCP shim** at [`assistant/whatsapp/mcp-whatsapp.js`](../../../projects/assistant/whatsapp/mcp-whatsapp.js) — 6 tools: status / list_chats / search_chats / read_thread / send_message / get_qr. Reads bridge token on every call, calls bridge HTTP API. Registered in `~/.claude.json` as `whatsapp`.
3. **Systemd user service** at `~/.config/systemd/user/whatsapp-bridge.service` — `Restart=always`, logs to `bridge.systemd.log`. Enabled + running.
4. **QR pairing surface** — bridge writes ASCII to `qr.txt`, PNG to `qr.png`, dataURL to `qr.dataurl`. Robert scans via WhatsApp Linked Devices.
5. **Slack ticket** scaffolded as `db-108` (cookie-based xoxc + xoxd MCP, sequenced after db-086).

### Architecture decision: bridge daemon, not in-process MCP client

The natural temptation is to make the MCP server itself instantiate the WA client. Don't. Three reasons:

1. **One WA session per phone number, ever.** WhatsApp Web detects multiple active sessions and disconnects all but one. If the MCP is invoked from multiple Claude sessions / cron jobs / agents simultaneously, each spawn would re-init Chromium and try to claim the LocalAuth dir → constant disconnect/reconnect churn or ban risk.
2. **Chromium boot is heavy** (~3s on this box for the Puppeteer-bundled chrome at 146.0.7680.31, ~130MB resident). MCPs spawn-and-die per session; WA sessions need to stay alive across sessions.
3. **LocalAuth directory locking.** whatsapp-web.js LocalAuth uses a Chrome user-data dir. Two processes pointing at the same dir corrupts state instantly.

Solution: one long-running daemon (systemd, `Restart=always`), ephemeral MCP shims that call the daemon over loopback HTTP. **This is the durable shape for any browser-automation-backed integration** — apply same pattern to anything else that needs Puppeteer/Playwright + persistent auth (e.g. if Slack ever needs to fall back from API to web-scrape).

### Defense-in-depth on a loopback service

Even though the bridge listens only on `127.0.0.1`, I added a bearer token check on all non-`/health` endpoints. Reason: any process running as user `assistant` (other agents, future scripts, contractors with shell access) can hit loopback. The token gates write access (sending messages) to "code that can read `~/.claude/.whatsapp-bridge-credentials.json`" — which is the same trust boundary as Stack-A creds. Cheap to add, real boundary.

`/health` is unauthenticated by design: lets external monitors (Death Board, future healthz cron) check liveness without owning the bridge token.

### State file as a Death Board signal

Bridge writes `assistant/whatsapp/state.json` on every state change: `{ready, authState, qrPresent, lastReadyAt, lastError, me}`. ## 2026-05-05 — Drive ACL cleanup: revoke at the highest level (Shared Drive > folder > file)

**Project:** k2c-004 (filing dead-SA folder access on `k2c_legals`)
**Category:** tooling, Drive permissions, dead-config cleanup

**Context:** Old gcp project `claude-code-mcp-489713` had a service account (`service-account@claude-code-mcp-489713.iam.gserviceaccount.com`) that was added to Robert's Drive ecosystem before the OAuth migration on 2026-04-20. After that migration the gdrive MCP runs as Robert's personal OAuth and the SA does nothing — but its ACL entries persisted everywhere. Cleanup task: revoke from "all places in AP Gdrive."

**Key learning — blast-radius surprise:** A naive `'X' in readers` query returned **69,100+ files and was still paging** when killed. That's not direct shares — it's **inheritance from Shared Drive membership**. The SA was a `fileOrganizer` member on 6 Shared Drives (Aurora Punks, Aurora Punks Admin, Aurora Punks External, CZP, Platform Sales, Public), and every file in those drives matches `'X' in readers` via inheritance.

**The right algorithm — top-down, level-aware:**
1. **Pass A — Shared Drive membership.** `drives.list` → for each, `permissions.list(fileId=driveId, useDomainAdminAccess=false)` → find SA → `permissions.delete(driveId, permId, supportsAllDrives=true)`. **One API call per drive, kills inheritance for every descendant.** Robert needs to be `organizer` (Manager) on the drive — the API will 403 otherwise.
2. **Pass B — direct file shares.** Re-query `'X' in readers and trashed=false` globally. Whatever remains is a **direct share** (My Drive, or per-file shares within drives we don't own). Iterate, lookup permId per file, revoke.
3. **Re-run pass B until residual = 0.** A folder-level direct share will inflate Pass B's count via inheritance from that folder; revoking the folder permission is one call but produces N "phantom" matches in the next enumeration. Re-running collapses them — a permission that's *only* inherited returns from `permissions.list` but `permissions.delete` says "Permission not found" (you can't delete an inherited permission at the descendant — only at its source).

**Concrete numbers from this run:**
- Pass A revoked: 6/6 drive memberships in <2s
- Pass B first run: 244 hits enumerated, only 5 revocable directly (4 folders + 1 transient failure), but
- Pass B second run: 0 hits — inheritance from the 4 folder revocations had cleared every descendant

**Safety guard worth keeping in any cleanup script:** abort Pass B if it exceeds a threshold (5000 hits). That's the unmistakable signal that Pass A missed a Shared Drive membership and you'd otherwise spend hours iterating phantom matches. Better to bail and audit.

**Auth gotcha:** the gdrive MCP fork's `auth.js` declares scope `drive.readonly`, but the saved `.gdrive-server-credentials.json` retains whatever scopes were last consented (Robert's token has full `auth/drive`). For write/delete operations, reuse the existing creds file directly — don't trust the source-code declared scope. Construct `OAuth2(client_id, client_secret)` from `gcp-oauth.keys.json.installed` so refresh works; without those, refresh fails with `invalid_request: Could not determine client ID`.

**Don't pipe through `tail` when watching long-running scripts.** `node X | tail -80` buffers everything until the pipeline closes, so you see nothing for the entire run. Either redirect to a file and `tail -F` it, or use `stdbuf -oL -eL` to force line buffering on the producer.

**Logs:** `assistant/logs/revoke-stale-sa-2026-05-05T14-*.json` (apply runs)

- creds in `~/.claude/.<name>-credentials.json` (0600)

- `initialize` → grab serverInfo
- `notifications/initialized`

## 2026-05-04 — Per-ticket Discord thread lifecycle: file watcher + msg.startThread + inbox/outbox reuse (db-088 step 3)

**Learned:** 2026-05-04 | **Project:** Death Board (db-088) | **Category:** discord / threads / file-watcher / inbox-outbox

**The pattern that worked:** Hooking the *existing* file watcher (`assistant/server.js startWatcher`) for ticket lifecycle events, rather than building a separate event bus. Two new branches inside the same debounced handler:
1. `oldHash === undefined` → new file → `discordBot.ensureTicketThread(id)` (idempotent — bot returns null for non-AP-routed prefixes, so the call is a no-op for everything outside `[apb, aurora, toa, swa, bem, kng, gff, dbl]`).
2. `prevStatusMap.get(filename) !== 'done' && newMeta.status === 'done'` → `discordBot.archiveTicketThread(id)`.

For status transitions you need a `prevStatusMap` because hashes are one-way — populate it inside `initFileHashes()` from `parseFrontmatter(content).meta.status` so the *first* status change after restart is detected against the real previous value, not undefined.

**`channel.threads.create` vs `msg.startThread`:** Use `msg.startThread({name, autoArchiveDuration})` when the originating event is a user message (parent-channel post → ticket+thread) — the user's message becomes the thread's parent, which feels natural. Use `channel.threads.create` when the originating event is filesystem/API (watcher → new ticket → standalone thread). Both are stored the same way in the bot's `ticketThreadMap`.

**Thread name pattern:** `<ticket-id> — <title>` truncated to Discord's 100-char limit. The leading ticket ID lets `getTicketIdFromThread` reverse-lookup from `msg.channel.name` if the in-memory map is missing — useful for recovery when `ticket-threads.json` is wiped or out of sync.

**Inbox/outbox reuse:** Don't invent a parallel queue for thread replies. The existing `.assistant-inbox.jsonl` / `.assistant-outbox.jsonl` plumbing (db-014) is exactly right — same JSON shape (`id, ticket_id, source, question, ts, status, ...`), same 120s outbox poll, same fallback message ("Assistant is working on this"). Only the `source` field changes (`discord-agent-relay` vs `discord`), and the response writes to `thread.send` instead of `msg.reply`. Extracted into `_enqueueAgentRelayInbox(thread, ticketId, text, username)` so both parent-post-with-message and thread-reply paths share it.

**Idempotency on `ensureTicketThread`:** Always cheap to call. (a) Returns the existing thread info from `ticketThreadMap` if present and the thread still exists in Discord (validate via `client.channels.fetch`); (b) recreates if Discord deleted the thread; (c) returns null cleanly when the prefix isn't claimed by any prefix-only profile. This means callers (file watcher, slash commands, CLI) don't need to track state.

**Prefix detection heuristic for parent posts:** Two-pass match against `Object.keys(projectPrefixes)`:
1. First try `\b([a-z]{2,8})-\d+/i` (e.g. "create a follow-up for toa-016") — if match is a known prefix, use it.
2. Fall back to bare-word match `\b(toa|swa|...)\b` — covers casual mentions ("looks like a toa thing").
3. Default to `db` (Death Board internal) when nothing matches.

This is good-enough for v1; if it gets noisy, swap in an LLM classifier (Haiku tier) that reads the body + project list and returns the prefix.

**Known limitation (intentional):** Existing pre-watcher tickets don't get retroactive threads. `initFileHashes` populates hashes for everything at startup, so all subsequent edits look like updates (oldHash defined). No threads created retroactively. If retroactive backfill is needed, add a `/thread <id>` slash command or a one-shot script that calls `ensureTicketThread` for every active follow-up.

- `assistant/discord-bot.js` — `TICKET_THREAD_MAP_FILE` const, `_loadThreadMap`/`_saveThreadMap`/`getTicketThread`/`setTicketThread`/`getTicketIdFromThread`/`_getAgentRelayChannel`/`ensureTicketThread`/`archiveTicketThread`/`_handleAgentRelayPost`/`_handleAgentRelayThreadMessage`/`_enqueueAgentRelayInbox` methods. - Reuse the file-watcher-as-event-bus pattern any time you need to react to ticket lifecycle. Don't bolt on event emitters when the watcher already runs.

## Claude Code hooks fire for ALL concurrent sessions on the VPS — design accordingly (2026-05-04, db-076)

**Project:** Death Board (db-076 RAG Phase 4)
**Category:** tooling, hook-design

### What I learned

Hooks configured in `/home/assistant/projects/.claude/settings.json` apply to **every** Claude Code session running in that project — foreground IDE sessions, background autonomous agents (4am sweep, queue runners, scheduled cron jobs), sub-shells from slash commands, anything that reads the project's settings.json. On the VPS that's typically 3–10 concurrent sessions with distinct `session_id`s.

I discovered this when wiring `PostToolUse` + `SessionEnd` for trace capture. Within minutes I had 5 different session-id trace files: my main session plus 4 others (one editing pb-* tickets, one reading agent memory, two editing server.js — all background work). Each one fires hooks independently.

### Implications for hook design

1. **Per-session state isolation matters.** Sidecar files keyed by session_id (`assistant/session-traces/.<sid>.last`) are essential to avoid sessions racing on shared files.
2. **"Recently touched" heuristics across the global followups dir are unsafe.** A heuristic that says "find the most-recently-touched X" will pick up another session's work, not yours. Per-session signals (current-ticket marker, ticket IDs inside this trace's events) are the only safe basis for attribution.
3. **Hook scripts run unattended in many contexts.** They MUST swallow errors (`set +e`, `2>>errors.log`), MUST timeout (`timeout 2s`/`timeout 10s`), MUST never block tool dispatch. Outer hook timeout (in settings.json) > inner shell timeout — gives margin without letting Claude Code kill the wrapper before it can clean up.
4. **`$CLAUDE_PROJECT_DIR` is the right path anchor**, not absolute paths — survives if the project moves.
5. **`.claude/settings.json` watcher activates new hooks live.** No restart needed if the file existed at session start. If it didn't (creating it for the first time), users must open `/hooks` once or restart.

### How to apply

When designing any hook that needs to attribute work back to the right "owner" (ticket, agent, project), do not rely on filesystem mtime or "what's been touched recently" — those signals leak across concurrent sessions. Require explicit per-session state: a current-* marker file, in-trace metadata, or a session-id-keyed sidecar. When in doubt, orphan to a review queue rather than guess.

## 2026-05-03 — Healthz monitor: CF Access 302 is not "site healthy" — use localhost instead (db-097)
**Learned:** 2026-05-03 | **Project:** Death Board (db-097) | **Category:** monitoring / cloudflare-access / coverage

**Context:** Captain Hook reminded for 242h+ that Death Board + cc-hive were "still failing (code 302)". Browser worked fine — Robert was confused. Root cause: 2026-04-23 security audit moved both behind Cloudflare Access. Unauthenticated curl from the VPS hits the CF Access edge gate, which serves a 302 to `runatyr.cloudflareaccess.com/cdn-cgi/access/login/...` *before reaching origin*. The healthz script's expected `200` was now structurally unreachable for these hosts.

**The trap to avoid: "just expect 302."** It's a one-line "fix" that silently weakens monitoring to the point of uselessness. CF Access serves 302 whether origin is up, down, or on fire — origin is never hit. Treating 302 as healthy means we'd stop alerting when the actual app dies. The `code-server` line uses `expected=302` legitimately because that endpoint exists *only* to be CF-Access-gated; for our own services where we want app-liveness signal, 302 conveys zero information.

**The right fix for this class of monitor:** localhost. The healthz monitor and the apps share the VPS — `http://localhost:3777` (Death Board) and `http://localhost:3000` (cc-hive) bypass CF Access entirely and actually verify the node process is alive and responsive. Trade-off: lose edge/tunnel coverage from this single check; mitigated by `db-035-cf-connector-count-healthz` which already monitors connector count separately. The two checks now do orthogonal jobs (app liveness vs tunnel liveness) instead of overlapping uselessly.

**The "real" fix if you want end-to-end coverage:** CF Access service token. Create a service token in the CF dashboard, add `CF-Access-Client-Id` + `CF-Access-Client-Secret` headers to the curl call, register both in `secrets_registry.md`. ## 2026-05-02 — Round-trip verify before swapping a parser globally (db-098)
**Learned:** 2026-05-02 | **Project:** Death Board (db-098) | **Category:** tooling / data-migration / safety

**Context:** Replacing a low-level utility (parser, serializer, codec) used across many files is a common-but-risky kind of change. Whenever I'm about to swap one, I should first run an exhaustive round-trip verification across every existing file/record so I know nothing semantically drifts.

When swapping the Death Board's hand-rolled YAML parser to `js-yaml`, the verification script (`assistant/verify-frontmatter-roundtrip.js`) caught 5 ticket files with pathological escape-pile-up in `context:` fields — strings like `"\\\\\\\"Dark Dungeon Days\\\\\\\""` accumulated over many round-trips of the buggy old parser. The old line-based parser silently tolerated them; strict YAML 1.2 rejects them. Without the pre-flight scan, the swap would have failed live on those 5 tickets after the first write attempt — and possibly silently corrupted others.

**The script shape that worked:** for every file, parse with the new parser, re-serialize with the new serializer, parse again, and compare. Track three outcomes separately: parse failures (hard error), semantic deltas (data lost between round-trips — must be 0), formatting deltas (informational; expected to be non-zero on first pass since the new serializer reformats). On the second pass, formatting deltas should drop to 0 — that confirms the new pipeline is fixed-point.

**How to apply:**
1. Before swapping any module-level parser/serializer/codec, write `verify-X-roundtrip.js` that runs every existing file through the new pipeline.
2. Skip files that fall outside the parsed type (here: skip files with no frontmatter — they're not tickets).
3. Surface broken-input files (parse failures); fix them by hand BEFORE the swap.
4. Verify second-pass byte-stability — confirms one-time format-settle, no thrashing.
5. Only after all three counters look right, replace the production parser.

### 2026-05-01 — Pre-fire validation pattern for systemd-timer + slash-command jobs

**Project:** gen-213 (deal wiki digest timer)

**Learning:** When a systemd user timer triggers a slash command via `claude -p "/foo"`, three failure modes catch you on the first scheduled fire if you don't validate ahead of time:
1. `claude` CLI not on the systemd user's PATH (fix in script: `export PATH="$HOME/.local/bin:$PATH"` before invoking)
2. Slash command file moves or gets renamed → silent failure
3. `cwd` of the script differs from the project root → slash command not found (commands resolve relative to cwd's `.claude/commands/`)

Pre-fire checklist for a new timer: `bash -n <script>` for syntax, `command -v claude` from the script's PATH, `ls .claude/commands/<name>.md`, `systemctl --user list-timers` to confirm next-fire timestamp, `systemctl --user status <name>.service` to see if Type=oneshot is set + ExecStart resolves.

Mirrors security-t1.timer / digest.sh pattern. Skip the pre-fire check at your own peril — the first failure is silent and Robert won't notice for a week.

**How to apply:** Any new systemd-user-timer wired to a Claude slash command, the DevOps agent does the four-line pre-fire check before declaring it shipped. Add it to the timer-creation skill if one exists; if not, this learning IS the pattern.
