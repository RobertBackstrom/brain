## 2026-07-17 — RAG "indexed but not searchable": scanned-PDF stubs + OCR gated to one drive; a two-bug fix (deal history / avtal / kontoutdrag)
**Learned:** 2026-07-17 | **Project:** RAG indexer (Death Board), triggered by Robert "agenter hittar inte kontoutdrag/avtal på Drive/mail" | **Category:** rag / gdrive / ocr / pdf-extraction / diagnosis

**Symptom → diagnosis: "we indexed everything" was true for *files*, false for *content*.** `rag-indexer.js --stats` looked healthy (gdrive 21,397 docs, gmail 61,573 back to 2021, gmail-personal 23,545 back to 2014, all re-synced same-day). Mail is genuinely fine. But ~1,100 gdrive rows are **stubs** — indexed by filename/title, **no searchable body** — and they skew hard toward exactly the high-value docs Robert meant: signed contracts, förhandlingsprotokoll, bank statements. `20240123_Loan Bright Gambit.pdf`, `Förhandlingsprotokoll Aurora Punks Development 20250314.pdf` = title-only. Lesson: doc-count stats hide a content-coverage hole. To size it, bucket `length(content)` per mime, don't trust totals.

**Root cause A — OCR was gated to ONE Shared Drive.** `gdriveFetchContent(..., allowOcr)` only passed `allowOcr=isFinancial` (`file.driveId === FINANCIAL_DRIVE_ID`, `0AMBeS-GYxphsUk9PVA`). A scanned PDF with no text layer on ANY other drive (Aurora Punks Admin, Aurora Punks, CZP, Platform Sales…) fell through to a stub. Fix: added `CFG.OCR_DRIVE_IDS` (env-overridable `RAG_OCR_DRIVE_IDS`) = financials + AP Admin + AP + CZP + Platform Sales + legals + Runatyr; `isOcrDrive = OCR_DRIVE_IDS.has(file.driveId)` now drives BOTH `allowOcr` and the higher 25MB size cap (scans exceed the 5MB default). Kept `isFinancial` for the per-company `project` tag only (that folder-map logic is specific to the Financial drive's structure).

**Root cause B — a latent OCR-trigger bug that would have starved even the Financial drive.** pdf-parse emits page separators `-- 1 of 3 --` for scanned pages with NO text. The old check `pdfText.replace(/\s/g,'').length < 100` counted those markers as "text", so: (1) a multi-page scan's markers push past 100 → OCR never fires even where allowed; (2) marker-only junk (`"-- 1 of 1 --"`, 16 chars) got stored as if it were content — which is why these rows had **no `pdf_no_text_layer` sentinel** and my first retry (targeting that sentinel) matched **zero** rows. Fix: strip `/--\s*\d+\s*of\s*\d+\s*--/g` BEFORE measuring; if the stripped body is empty, return the `pdf_no_text_layer` sentinel instead of storing markers. So the retry selector must catch BOTH the sentinel AND legacy marker-only bodies (`content.startsWith('[OCR via')` excludes already-done rows; stripped-length < 100 catches the rest).

**Verify the extraction chain on ONE real file before a 181-file batch — and don't trust your own throwaway auth.** My first smoke test downloaded "507 bytes" and I nearly concluded the files were shortcuts/undownloadable. It was **my test script's bug**: `.gdrive-server-credentials.json` holds only `{access_token, refresh_token, scope,…}` — **client_id/client_secret live in `~/.claude/gcp-oauth.keys.json`** (`.installed`/`.web`). My refresh sent `client_id=undefined` → 200 with an invalid token → every Drive call 401'd with a 507-byte error body that *looks* like a tiny file. Load creds like the indexer does. With correct auth: file = 134,933 bytes `%PDF-1.3`, pdf-parse got 8 non-space chars (confirming scanned), tesseract `swe+eng` got 588 chars of real Swedish ("REVERS… tvåhundratusen (200 000)… två (2) procents årlig ränta"). Binaries present: `/usr/bin/tesseract` (+swe,eng), `/usr/bin/pdftoppm`.

**No restart, no cron change needed — the indexer is a fresh process per run.** `rag-external-sync.timer` runs `node rag-external-indexer.js --gmail --gdrive --incremental` every 30 min, so code+config edits are picked up on the next tick automatically, and new scanned PDFs on the OCR drives OCR going forward via the normal incremental path. One-time backfill of the existing 181 stubs via new CLI flag `--retry-ocr` (targeted re-fetch by file ID, no Drive walk; refactored the retry loop into `reindexGdriveRows()` + a `reindexScannedPdfs()` selector). NOTE: `retryFailedExtractions` re-fetches file metadata but originally omitted `driveId` from `fields=` — without it the OCR gate `OCR_DRIVE_IDS.has(file.driveId)` silently never fires on the retry path. Any retry that depends on driveId MUST request it.

## 2026-07-16 — LinkedIn MCP down = stale cookie this time ("No valid LinkedIn session"), NOT the IP block (devops /LinkedIn, db-275)

**Learned:** 2026-07-16 | **Project:** Death Board / LinkedIn MCP (db-275) | **Category:** tooling / MCP / linkedin / debugging

**Two distinct "LinkedIn MCP is down" signatures — don't conflate them:**
- `ERR_TOO_MANY_REDIRECTS` on strict endpoints (SEO/famous profiles still work) = **Hetzner AS24940 IP fingerprint block** (db-112/db-048). Structural, cookie is fine, no re-export fixes it.
- **"No valid LinkedIn session is available"** on `get_my_profile` (own profile, least-strict call) = **cookie is dead / server-side-invalidated**. Fix = re-export `li_at`.

**Diagnostic gotcha (changed since db-112):** the documented "check trace-runs server.log first" shortcut is now unreliable — the latest `~/.linkedin-mcp/trace-runs/run-*/server.log` is **0-byte** (not logging). The authoritative probe now is a **live MCP call** (`get_my_profile`) — read the error string, not the trace log. `ps aux | grep linkedin` showed processes up (one uvx+python pair per interactive session) — "processes up" says nothing about session validity.

**This incident:** `cookies.json` was 20 days old (written 06-26), contained **only `li_at`** (no JSESSIONID). Client-side `expirationDate: 2031` is meaningless — LinkedIn invalidates server-side (re-login on Robert's side, or ~30-day session rotation). Fix is Robert-side only: Cookie-Editor export → `node assistant/linkedin-restore-cookie.js --stdin` (li_at line 1, JSESSIONID line 2). **Recommend including JSESSIONID** — without it write-actions (send_message, connect) fail even after reads recover. No service restart needed; MCP reads cookies.json on next call.

**Robert asked "vore det enklare via Playwright?"** — no, and the reason is canonical, so it lives in [[reference_mcp_tools]] (LinkedIn entry), not just here: `linkedin-scraper-mcp` **is already Patchright/Playwright**. Both failure modes are auth/IP-layer, so any driver inherits them identically; a bespoke script also re-implements cookie import/validation and loses the tool surface. The durable lever is a freshness probe (db-275), not a library swap.

## 2026-07-16 — gmail.settings.basic scope prep; the superseded-spec trap; Gmail default search excludes Spam (db-154 / apb-026)
**Learned:** 2026-07-16 | **Project:** db-154, apb-026 | **Category:** oauth-scopes / gmail / reconciliation / steam-guard

**Context:** Google-Group relay was spam-filing the Steam Guard codes for `aurorapunks_user` (they arrive at sales@aurorapunks.com). Cost a live login attempt. Task: add `gmail.settings.basic` so the durable filter spec could apply itself, and close the code-fetch blind spot.

**`gmail.modify` READS filters but cannot CREATE them — probe, don't assume.** Per the standing "just try the API call before assuming you're blocked" rule (which correctly predicted `drive` covers Docs writes, 2026-06-08), I probed both halves. Result splits: `GET /users/me/settings/filters` -> **200**, `POST /users/me/settings/filters` -> **403 `ACCESS_TOKEN_SCOPE_INSUFFICIENT`**. So filter *inspection/reconciliation* needs no re-auth and can be done any time; only creation is gated. Probe each VERB, not the resource — a 200 on GET says nothing about POST. (The probe POST used a nonsense `@invalid.aurorapunks.test` criteria + delete-on-success cleanup; it 403'd so there was nothing to clean.)

**A superseded artifact will happily let you regress the system — check `_meta.supersedes` BEFORE applying any spec.** The brief said to apply `gmail-filters-spec.json` (2026-05-18). But `triage-policy.json` (2026-05-29) declares `"supersedes": "gmail-filters-spec.json (reconciled into sweep_rules)"`, and db-154's own 2026-05-29 update says the same. Applying the old spec would have **trashed** `community@nordicgame.com` / `noreply@nordicgame.news` / `mallayeva@devgamm.com` / `hello@news.tandemevents.co.uk` / `info@courage.events` — senders the current policy deliberately reclassified to **archive** ("Games-industry event & VC news (keep + digest)"), while Robert has live NGC work (Elias NGC Mixer, GIN scheduling, eli-015). The stale spec wasn't merely redundant, it was **actively wrong**, and "apply the spec" sounded harmless. Two cheap tells that catch this: grep `_meta` for `supersedes`/`superseded_by`, and read the ticket's LATEST update before its original body. Marked the spec `STATUS: SUPERSEDED — DO NOT APPLY` in its own `_meta` so the next agent can't repeat it.

**Gmail's default search scope EXCLUDES Spam and Trash — `in:anywhere` is mandatory for any unattended code/OTP fetch.** The failure is *silent and worse than empty*: with a code sitting in Spam, a plain query doesn't return nothing, it returns the newest **inbox** message = a **stale code**, which the form accepts and Steam then rejects. Proven live: default query returned 3 messages, `in:anywhere` returned those plus two SPAM ones (19:08, 08:38 on 2026-07-16). Pair it with a hard timestamp gate — **Steam reuses the same code across resends**, so validity = `internalDate > loginStartTime`, not "most recent".

**Group relay rewrites the From — never match a Google-Group-relayed sender by its origin domain.** A group re-sends with the original From but from Google's infra (breaks SPF/DKIM alignment -> reads as spoofing -> spam). The From becomes `"'Steam Support' via 1st party registration" <sales@aurorapunks.com>`, so **`from:steampowered.com` returns literally ZERO**. Match on `subject:` (or the group address). This also explains the spam-filing itself. Robert's hand-made never-spam filter (`from:(sales@ OR arkisland@ OR qa@ OR aws@)` -> `removeLabelIds:[SPAM]`) works *because* it matches the rewritten address. Note `removeLabelIds:[INBOX]` (archive) and `removeLabelIds:[SPAM]` (never-spam) are completely different actions — an existing archive rule is not spam protection.

**Built `assistant/steam-guard-code.js`** — module + CLI (`getCode({since})`, `waitForCode({since})`, `--list`). Reuses `gmail-api.js` (`listMessages`/`getMessage`/`extractTextBody`) rather than re-hand-rolling the raw refresh+base64url recipe. `since` is a REQUIRED arg that **throws** if absent — an ungated lookup silently returns stale codes, so the API refuses to make the dangerous call easy. Verified 3 ways: fresh code found, `since=newest+1s` correctly returns null, missing `since` throws. There was **no existing code path to patch** — the watchers only Discord-ping Robert; the "proven recipe" lived in a session transcript. Recipes that live only in transcripts get re-derived (and re-broken); land them in a module.

**Scope additions are additive-safe, but verify the specific way they could bite: exact-match on the stored `scope` string.** Grepped all 16 dependents of `.gmail-archive-credentials.json` — none compare the scope string (the only `.scope.includes('drive')` check is in `gdrive-upload.js`, a different file). `creds-store.js` guards on `refresh_token` only. So widening cannot regress consumers. Per-profile `credsFile` in `oauth-helper.js` means re-authing `gmail` touches ONLY that file — siblings verified unchanged by scope+mtime after the edit. Took a `.bak-<date>-prescope` snapshot anyway: consent is interactive and Robert-blocking, so a bad exchange is expensive to undo.

**The work Gmail token had NO secrets_registry entry despite 16 dependents** — `google.oauth.aurora-workspace` (drive) and the personal one existed, work Gmail didn't. Registered as `google.oauth.aurora-gmail`. When you touch a credential, check it's actually *registered* before updating its entry; absence is the more common defect.

**Least privilege beats round-trip convenience — but surface the tradeoff.** db-154 also wants `https://mail.google.com/` (full mailbox) for `batchDelete` quota reclaim. Today's authorization named only `settings.basic`, so I did NOT add it — but flagged that consent is interactive and expensive, so if he wants both it must go in BEFORE the click or it's a second round. Don't silently widen a sensitive grant to save yourself a trip.

## 2026-07-15 — OOM debugging: `ps` RSS lies, cgroup memory.current is truth; OOM victim ≠ culprit (infra)

**Context:** VPS (ubuntu-8gb-hel1-1, 89.167.23.168, 8 GB) hit Cloudflare 1033; Hetzner console showed OOM-killer repeatedly killing chrome. Initial hypothesis (Robert's + mine): runaway headless-Chrome/Puppeteer spawning until RAM dies. **That was wrong on every count.** Real chain took 4 diagnostic rounds to nail.

**The traps, in order:**
1. **`ps aux` RSS massively overcounts chrome.** WhatsApp bridge chrome tree showed ~1.6 GB RSS in `ps` (VSZ 1.4 TB). Its **actual cgroup `memory.current` was 203 MB** (anon 178 MB, peak 376 MB). Chrome maps huge shared/file-backed executable pages that `ps` RSS counts per-process but the kernel accounts once and can reclaim. **For any memory-limit or "who's the hog" decision, read cgroup accounting, never `ps` RSS.**
   - True per-service memory: `cat /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/<...>/<unit>/memory.current` (and `memory.peak`, `memory.swap.current`, `memory.stat`). Or `systemctl [--user] show <unit> -p MemoryCurrent,MemoryPeak`.
   - Per-service breakdown loop over `user@1000.service/*/memory.current` instantly ranks the real hogs.
2. **The OOM victim is not the culprit.** Kernel picks the largest-RSS process to kill → chrome (inflated RSS) dies every time → looks like "chrome is the problem" on the console. Actual memory consumer was **`code-server.service` (2.4 GB now, user-slice peaked 6.9 GB)** — VS Code server + stacked Claude Code sessions + per-session MCP servers (mcp-gdrive-fork ~120 MB, mcp-whatsapp shim ~62 MB) + extensionHosts + language servers + filewatchers. Each open VS Code/Claude session stacks ~0.7–1 GB. Docker (Plane 16 containers + OpenSign 4) sits **outside** user@1000 (~0.7 GB idle). user-slice 6.9 GB peak + docker + kernel ≈ 7.6 GB → box-wide OOM.
3. **Bridge restarts looked like OOM but weren't.** whatsapp-bridge.service had `NRestarts=27`, all `status=1/FAILURE` = its own watchdog `process.exit(1)`, **not** `signal=KILL`. Its bridge.systemd.log showed every exit = `"bridge stuck not-ready past grace window","notReadyForMs":~300000,"authState":"connected"` — a whatsapp-web.js **authenticated-but-never-ready** bug (self-heals via systemd Restart=always, cgroup-clean, unrelated to memory). Don't conflate a service's self-restart loop with OOM; check exit code (exited/1 vs killed/9) and the service's own log.
4. **cgroup containment already worked.** chrome runs *inside* the bridge's cgroup; systemd default `KillMode=control-group` reaps the whole tree on restart → exactly one tree ever present, no orphan accumulation. My "orphaned trees stack up" hypothesis was disproved by there being exactly one tree.

**Fix applied:** soft memory cap, no process touched, no restart:
- `systemctl --user set-property code-server.service MemoryHigh=4.5G` — works **without root** (user manager owns user units, memory controller delegated on Ubuntu 24.04 cgroup v2). Persists as `~/.config/systemd/user.control/code-server.service.d/50-MemoryHigh.conf`. **`MemoryHigh` = soft** (kernel reclaims/swaps within the cgroup before global OOM) so it can **never kill Robert's live editor session** — critical when the box you're debugging hosts your own session. Reserve hard `MemoryMax` for things you're willing to see killed.
- Slice-level belt (`user-1000.slice MemoryHigh=6G`) needs **root** — user-*.slice is owned by system systemd, not the user manager. Hand it to Robert as a sudo command.

**Access gap:** `sudo -n` needs a password on this VPS → I **cannot** read kernel OOM logs (`dmesg`, `journalctl -k`) autonomously. Kernel OOM confirmation must be handed to Robert as sudo commands, or set up a minimal passwordless sudoers drop-in for read-only `dmesg`/`journalctl -k` if we want autonomous kernel-log debugging going forward.

**Method learning:** a memory-exhaustion diagnosis isn't done until you've (a) read cgroup `memory.current`/`memory.peak` per service, not `ps`; (b) checked the suspected culprit's exit *code* (exited vs killed); (c) confirmed whether the "runaway" is cgroup-contained. Present the correction honestly even after committing to a wrong hypothesis mid-investigation — I flipped culprit twice and said so each time.

**Kernel-log confirmation (added after Robert ran sudo dmesg):** two OOM events, both `systemd invoked oom-killer` (global allocation failure, not a single runaway proc): Jul 14 12:02 killed chrome anon-rss **422 MB** oom_score_adj=0; Jul 14 17:25 killed chrome anon-rss **392 MB** oom_score_adj=**300**. Confirms (a) chrome's real anon footprint was ~400 MB not 1.6 GB — the `ps` RSS inflation, proven by the kernel itself; (b) **why chrome is *always* the OOM victim even though code-server is the consumer: Chrome self-sets positive `oom_score_adj` (+300) on its renderer children so they're sacrificed first.** Big RSS + self-inflicted positive oom_score_adj ⇒ kernel always picks a chrome renderer; code-server's node procs sit at adj=0 and are never chosen. So "OOM keeps killing chrome" on the console is a *red herring* pointing away from the real consumer. (c) The Jul 14 17:25 OOM timestamp exactly matches a whatsapp-bridge `status=1/FAILURE` restart → some bridge restarts ARE OOM-triggered (OOM kills a renderer → bridge sees broken chrome context → exit(1)), while the others are the independent not-ready watchdog. Both mechanisms coexist; don't assume all restarts share one cause. **General rule: when the OOM victim is a chrome/Electron child, suspect it's a decoy — chrome biases the kernel toward its own renderers; find the real consumer via cgroup `memory.peak` per service.**

## 2026-07-15 (same incident, follow-up) — reaper timer + WA bridge not-ready ROOT CAUSE (db-086)

Two follow-up fixes after the OOM diagnosis (Robert: "kör alla tre"):

**#2 Session-hygiene reaper (durable, VPS-native).** Built `assistant/reap-orphaned-vscode.sh` + `reap-orphaned-vscode.{service,timer}` (user timer, every 20 min, logs to `assistant/logs/`). Kills ONLY per-session helpers (claude native-binary, mcp-gdrive-fork, mcp-whatsapp shim, VS Code extension/language hosts) that have been reparented to PID 1 OR to systemd --user (PID 915) — the definitive "owning session is gone" signal — with a >600s age guard. None of those patterns is ever a legit systemd service, so PPID∈{1,915} is unambiguous; the live session traces up through the running code-server entry so it's never touched. Dry-run (`DRY_RUN=1`) found nothing to reap (no orphans at the time) and proved it targets nothing live. Under systemd user@.service the manager (915) is the subreaper, so orphans land on 915, not always 1 — check both.

**#3 WA bridge "authenticated-but-never-ready" — real root cause was NOT version drift.** I initially assumed whatsapp-web.js webVersion drift (LocalWebCache falling back to latest). Wrong. Evidence disproved it: startup reaches `ready` in <1s every restart; the library already defaults webVersion `2.3000.1017054665`; the wa-version repo 404s on that exact file; and the cache had 38 versions yet still worked. **Actual cause:** whatsapp-web.js emits the `ready` event ONLY ONCE on initial load. On a mid-session WA reconnect (`change_state` OPENING→PAIRING→CONNECTED), the bridge's disconnectedStates branch sets `state.ready=false`, but the CONNECTED branch only set `authState='connected'` with a comment "the 'ready' event will fire and handle this" — it never re-fires, so `state.ready` stuck false → the db-166/167 5-min not-ready watchdog `process.exit(1)` restart-looped on EVERY reconnect. **49 restarts logged**, ~15/day. The systemd restart was the de-facto (working, ~5s) recovery. **Fix** (bridge.js CONNECTED branch): when `getState() === 'CONNECTED'` (authoritative — round-trips the live puppeteer page), set `state.ready=true; authState='ready'; lastReadyAt`. False-ready is backstopped by the existing 60s getState liveness watchdog. Backed up to `bridge.js.bak-2026-07-15-oom`, `node --check` passed, restarted (user unit, no root), verified ready in 5s + NRestarts=0. **CAVEAT:** clean startup does NOT exercise the fix (that uses the one-time `ready` event); the reconnect path only triggers on the next spontaneous WA reconnect (~2h). True confirmation = next `change_state CONNECTED` produces NO "stuck not-ready" restart. Watch `bridge.systemd.log` for `grep -c "stuck not-ready"` staying flat.

**Method:** for the 3rd time this incident, the first hypothesis (version drift) was wrong and cheap inspection (log timeline + state.json + cache dir) disproved it before I touched anything. Reading the actual failure timeline (was-ready → change_state cycle → stuck) beat the plausible-sounding theory. Don't blind-pin versions on a working live comms integration; find the state-machine bug.

## 2026-07-15 — RAG auto-indexes memory/skills/agents; no manual --backfill for watched dirs (platform)

`memory/`, `skills/`, `agents/` are all in `rag-config.js` `WATCHED`, and a live chokidar watcher runs inside `deathboard.service` (`server.js` calls `ragLib.startWatcher(ragDb)` at listen time) with ~30s debounce. So anything written to those dirs is RAG-searchable by every agent within half a minute — **no `node rag-indexer.js --backfill` needed** for them. Only reach for `--backfill --sources <x>` if the watcher is confirmed down, or for non-watched content. Corollary for knowledge design: the lever for cross-agent knowledge sharing is **placement** (which shared dir a fact lands in), not triggering indexing. Discovered while adding the /close promotion-step.

**Tags:** db-076, rag, chokidar-watcher, watched-roots, no-manual-backfill, placement-not-indexing, close-ritual, feedback_promote_canonical_facts
