## 2026-06-11 — "You can't access this board based on its filter" = private backing filter, not a project-access problem (BADASS)  [Tooling]
Nancy reported she couldn't open a CUST board (Jira lock screen: "You don't have permission to access this board based on its filter"). Root cause was NOT missing project access — she was an active, CUST-assignable user. Every Jira board is backed by a saved filter, and 4 of the 5 CUST boards were backed by filters **owned by Robert with zero share permissions** (private). Only the auto-created default board's filter (11052, shared `project=CUST`) was visible — which is the tell: if one board works and the others don't for the same user, the broken boards' filters are private/under-shared, not a project-role issue. Diagnosis path (all read-only): `GET /rest/agile/1.0/board?projectKeyOrId=<KEY>` → per board `GET /rest/agile/1.0/board/{id}/configuration` for `filter.id` → `GET /rest/api/3/filter/{fid}?expand=owner,sharePermissions` → look for empty `sharePermissions`. Fix (client-system write = MUST-ASK gate, got approval first): `POST /rest/api/3/filter/{fid}/permission {"type":"project","projectId":"<numeric id>"}` per filter — share with the **project** (mirrors the one working filter) rather than the single complaining user, so the next teammate doesn't hit the same wall. Returns HTTP 201; verify with the same GET. Don't reach for "change the filter owner" (Jira's own suggested fix) — adding a project share is less destructive and keeps Robert as owner. Source: BADASS.

## 2026-06-11 — Archived Jira projects are invisible to JQL (return 0), and their issues can't be bulk-moved until unarchived (BADASS)  [Tooling]
`project = PFL` (and RU/WSX/K26 — all archived) returned `count = 0` from `/rest/api/3/search/approximate-count`, even though the projects hold real history. Archived-project issues are **excluded from all JQL search, boards, and Plans** in Jira Cloud — a 0 here means "archived/invisible," not "empty." Consequence for any consolidation/migration: you cannot count, read, or bulk-move an archived project's issues while it's archived; the only path is unarchive → bulk-move wizard (UI-only, no REST) → re-archive. So "migrate the archived clients into CUST" is inherently UI/Playwright work, not scriptable, and you can't even scope it via JQL first. (This is also why Plan 34's archived sources contribute nothing to the timeline.) Source: BADASS.

## 2026-06-11 — A client reporting a self-serve workflow "doesn't work" - check whether the automation ever ran at all, and audit the guide JQL for unquoted smart values (BADASS)  [Tooling]
Nancy (CUST Chief of Staff) couldn't get the Monaco template checklist to clone when spinning up a new Location Epic, and guessed "filter issue again?" (her prior problem had been filter permissions). It was not. ## 2026-06-11 — CUST location tagging is DUAL: the Location custom field AND a matching label - the label is what's sortable (BADASS)  [Tooling]
After spawning the Monaco epics, Nancy said "you forgot the label and I can't sort by location." The CUST convention tags every location issue **twice**: the `Location` custom field (cf10231) AND a **label equal to the venue name** ("Dubrovnik" label on 94 issues, "Como" 105, "Jeddah", etc.). The spawn script only set the field, not the label. Why it matters: Jira boards/quick-filters/swimlanes sort and group cleanly on **labels**, not on a single-select custom field, so the Per-Location board's "sort by venue" runs off the label - field-only issues are invisible to that sort. Fix: backfilled label "Monaco" on all 55 issues (`PUT /rest/api/3/issue/{key} {"update":{"labels":[{"add":"Monaco"}]}}`), and patched the engine to set `labels=[location]` on epic + stories. **How to apply:** when cloning/creating location-scoped CUST issues, ALWAYS set both the Location field and a venue label (label = location value, spaces stripped). More broadly: if a client says "I can't sort/group by X," check whether X exists as a **label** vs only as a custom field - boards group by label far more readily, and a convention that uses both means the label is the load-bearing one. Source: BADASS.

## 2026-06-05 — Cheapest auto-integratable e-signature = self-host an OSS tool whose FREE tier includes the API (K2C / db-046)  [Tooling]
When a signing solution is needed and cost + auto-integration both matter, the cheapest path is self-hosting an open-source e-sign tool on the existing VPS. **The trap:** DocuSeal's free/Community self-host has **no API** (API is Pro, ~$20/user/mo + $0.20/doc) — so "free DocuSeal" and "auto-integrate" are mutually exclusive (exactly why db-046 sat blocked). Free OSS self-hosts that DO ship an API: **OpenSign** (chosen — Parse-based, runs on the VPS, $0) and **Documenso**. For no-hosting / no-monthly, the cheapest pay-as-you-go APIs are **Zoho Sign $0.20/doc** and eSignatures.io (~$0.49/doc). All produce standard electronic signatures (SES), valid for Swedish B2B contracts under eIDAS — no QES needed. General principle, aligned with "VPS is the runtime": prefer self-hosting an OSS tool that has a free API over a paid SaaS API whenever one exists. Source: K2C / db-046.

## 2026-06-05 — Editing followup-ticket frontmatter triggers a normalizer that strips fields on malformed YAML (Death Board)  [Tooling]
The Death Board runs a frontmatter normalizer whenever an `assistant/followups/*.md` file is saved. If an edit produces **malformed YAML** — e.g. a DUPLICATE key from *adding* `updated:` instead of changing the existing one — the normalizer chokes and **strips most frontmatter fields** (lost project/status/owner/routed_agent on db-046 this session; had to reconstruct by hand). It also silently appends fields like `due: null`. **How to apply:** when updating a ticket's frontmatter, **change the existing key in place** (never add a second `updated:`/`priority:`); the file is modified by the normalizer on every save, so **re-Read before each subsequent Edit**; and to *add activity* prefer the HTTP `POST /api/followups/:id/activity` endpoint (body `{text, link}` — but note it **hardcodes author to "Robert"** as an anti-spoof measure) or the in-process `appendActivity()`, over hand-editing the markdown when authorship/format matters. Source: Death Board.

## 2026-06-03 — `gsheets_update_cell` MCP writes RAW text — it silently breaks SUM/formula cells; use gsheet-set-cell.js (K2C)  [Tooling]
The `mcp__gdrive__gsheets_update_cell` tool writes values in **RAW** input mode, so a numeric value like `13500` lands as the *text string* "13500" (not a number) and a formula like `=B14*0.225` lands as *literal text*. Text cells evaluate to **0 inside SUM/arithmetic formulas**, so updating a numeric input cell silently corrupts every total that references it — with no error. Symptom I hit: set Lost Hive's P&L row to 60k-based milestone amounts, and the row total dropped from 270,000 to 189,000 (the two edited cells counted as 0) while the column SUMs fell by the old values; a read-back showed the cell holding the literal formula string `=B14*0.225` instead of a number, which is the tell. The MCP read returns computed values for real cells, so a formula string coming back = the cell is text.
**Fix / how to apply:** for any **numeric or formula** input cell in a hand-maintained sheet (P&L, trackers, budgets), do NOT use `gsheets_update_cell`. Use **`node assistant/gsheet-set-cell.js <file-id> "'<tab>'!A1=<value>" ...`** (built this run) — it calls Sheets `values:batchUpdate` with `valueInputOption=USER_ENTERED` (auth via the same `~/.claude/.gdrive-server-credentials.json` refresh-token flow as gdrive-replace-sheet.js), so numbers become numbers and `=...` becomes a formula, exactly like typing in the UI. The MCP tool is only safe for plain **text labels**. Always read back the dependent total (not just the edited cell) to confirm formulas recomputed. This refines [[feedback_preserve_formulas_in_sheets]]: "update input cells via gsheets_update_cell" holds for text, but numeric inputs need USER_ENTERED. Source: K2C.

## 2026-06-02 — Adding statuses to a company-managed Jira workflow via the new workflows API — the UUID gotcha (BADASS)  [Tooling]
Company-managed software projects use an auto-generated "Software Simplified Workflow for Project <KEY>" (one workflow for ALL issue types; `issueTypeMappings: {}` on the scheme = everything uses the default). It's flagged "Do not manually modify" but reads `isEditable: true` and IS editable via REST. Path that works (all read-only steps are safe; the writes are a client-system MUST-ASK gate — get explicit approval, the auto-mode classifier WILL block otherwise even after a verbal "go"):
1. Find scheme/workflow: `GET /rest/api/3/workflowscheme/project?projectId=<id>` → `defaultWorkflow` name; old `GET /rest/api/3/workflow/search?workflowName=...&expand=statuses,transitions` gives the simple view (numeric ids).
2. Reuse before creating: `GET /rest/api/3/statuses/search?searchString=...` — status NAMES must be unique within scope, so a duplicate-name create is rejected. "In Review"/"Blocked" often already exist GLOBAL; reuse their ids. Create only the genuinely missing one via `POST /rest/api/3/statuses` (`{scope:{type:GLOBAL}, statuses:[{name, statusCategory, description}]}`). A GLOBAL-scope workflow can only reference GLOBAL statuses.
3. Read current def in new format: `POST /rest/api/3/workflows` body `{"workflowIds":["<entityId>"]}`.
4. **THE GOTCHA:** in the `/workflows/update` payload, every `statusReference` must be a freshly **generated UUID**, NOT the numeric status id. The real id goes in the `id` field of each `WorkflowStatusUpdate`. Build a `{numeric_id: uuid}` map, emit top-level `statuses` as `{id, statusReference:uuid, name, statusCategory, description}`, set `workflows[0].statuses[]` + every transition's `toStatusReference` (incl. the existing ones AND the initial Create transition) to the UUIDs. Sending numeric refs → `STATUS_REFERENCE_NOT_UUID`, plus cascade errors (`NON_UNIQUE_STATUS_NAME` because it thinks you're re-creating "To Do", and `INCORRECT_PROJECT_IDS_IN_STATUS_MAPPING`). `statusMappings: []` is fine when only ADDING (no issue migration needed). Include the workflow's `version` (optimistic lock).
5. ALWAYS `POST /rest/api/3/workflows/update/validation` first (returns `errors:[]` when clean), then `POST /rest/api/3/workflows/update`. Re-read to confirm.
New mid-flow statuses → `statusCategory: IN_PROGRESS` (yellow); mirror the In Progress transition's `system:update-field` resolution-clear action. Simplified workflows use GLOBAL (any→any) transitions — keep that pattern. The Rovo MCP does NOT expose workflow editing, so this must go through the badass REST token (`~/.claude/.atlassian-credentials-badass.json`). Source project: BADASS.

## 2026-06-01 — Positioning AP vs a client-built Jira-entry agent: own the rules, not the tool (BADASS)  [Tooling]
Alex built a GitHub repo (`BADASS-Studios/Jira`) with an `AGENTS.md` so the team uses Copilot to create Jira tickets "correctly." When a client builds an issue-entry assistant on top of a taxonomy AP owns (CUST: client/type components, Location dropdown, templates, spawn automation), the two are **complementary layers, not competitors**: AP owns the *structure*, the client's agent is a *consumer* of it. The one real conflict is **drift** — if the agent lets users invent components/locations or its rules fall out of sync, it silently re-breaks the clean-input guarantee CUST exists to enforce, and the breakage surfaces on AP's side (boards + spawn automation) while the entry rules live on the client's. That asymmetry is the argument *for* co-owning. Recommendation pattern: **co-own the routing rules with a clean seam** — client owns the tool (repo, Copilot/IDE plugin, auto-assign, edit-perms = their dev-ergonomics lane); AP owns the routing-rules section of `AGENTS.md` as a downstream artifact of the Admin Guide it already wrote (the CUST §4 "new component/location goes through the PM" rule makes AP the natural keeper of the entry rules too). Converts a one-off restructure into recurring system-of-record stewardship; marginal effort is keeping one doc in sync. Don't offer to own their repo/tooling — that steps on their lane and reads as a takeover. Source project: BADASS.
