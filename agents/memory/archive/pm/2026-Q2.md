## 2026-06-17 — Auditing a client's Copilot/IDE agent: you can't run it, but you CAN verify its rules against the live board (BADASS)  [Tooling]
Alex asked the team to test his "Jira Manager" Copilot custom agent (`BADASS-Studios/Jira`: `AGENTS.md` + `.github/agents/jira-manager.agent.md`, driven by Atlassian Rovo MCP + VS Code's `vscode_askQuestions`). The orchestrating session **cannot drive that agent** (no `vscode_askQuestions` tool; it's an interactive IDE flow — only the user in their VS Code can run the live create). But the high-value PM contribution is auditing its rule-set against the live CUST structure, which is where drift bugs hide. Method that worked: clone the repo (`gh repo clone`), read AGENTS.md, then validate each live API step the agent depends on against real issues. Found: (a) component table left Game Client / Mobile AR App as "(confirm in Jira)" when real components `Steam-Console`/`AR App` exist — doc drift; (b) epic list filtered strictly by Location custom field — fine because epics are location-tagged, but cross-cutting/no-location epics would be hidden; (c) anti-Epic-creation rules were genuinely robust. **Empirically settled the parenting question** by creating one TEST Task with `customfield_10014` (legacy Epic Link) only — it auto-populated `parent`, proving CUST mirrors Epic Link → parent, so the agent parents correctly even though it uses the deprecated field. Deleted the test via badass REST token (`DELETE /rest/api/3/issue/{key}` → 204; 404 confirms gone) — cleanup of a self-made test artifact that the user pre-authorized. **How to apply:** when asked to "test" a client's agent you can't execute, audit its prompt/rules vs the live system and verify the load-bearing API behaviors with one disposable test artifact, then report concrete fixes. Note: `BADASS-Studios/Jira` is now readable by the VPS `gh` (`RobertBackstrom`, active org member) — the long-standing 404 is resolved. Source: BADASS.

## 2026-06-15 — Writing Story Points across a CUST-like project: the field is Story-only + off-screen by default (BADASS)  [Tooling]
Setting `customfield_10033` "Story Points" on CUST issues failed two ways before working, and both are generic Jira-company-managed gotchas: (1) **not on the screen** — the field must be added to every screen the project's issue-type screen scheme maps (trace `GET /issuetypescreenscheme/project?projectId=` → `/issuetypescreenscheme/mapping` → `/screenscheme?id=` → each screen's tab, then `POST /screens/{id}/tabs/{tab}/fields {"fieldId":"customfield_10033"}`); (2) **context is issue-type-restricted** — the default Story Points context has `isAnyIssueType:false` (Story/Epic only), so Task/Sub-task/Bug reject the write with the SAME "cannot be set, not on the appropriate screen" 400 even after the screen fix. The tell: only Stories take, everything else 400s. Fix without touching the site-wide global context (broad blast radius): `POST /field/customfield_10033/context {"projectIds":["<id>"],"issueTypeIds":[]}` creates a **project-scoped, all-issue-type** context (empty issueTypeIds = all). Also: an atomic PUT combining `update.labels` + `fields.customfield_10033` fails ENTIRELY if the points field errors — so the label silently doesn't write either. **Decouple label writes from points writes** so a points failure doesn't lose the label. Story Points is the right Plans estimation source; T-shirt Size (cf10232, options XS–XL) is a separate option field. Source: BADASS.

## 2026-06-15 — Before "set up the missing data," confirm the data is derivable — not just absent (BADASS)  [Tooling]

Reinforces the "verify the premise" learnings. Source: BADASS.

### Team-managed KAN: status rename + subtask sprint-add gotchas (2026-06-15, K2C)
Two confirmed facts when scripting sprint builds on the aurorapunks team-managed KAN board: (1) **Status NAME rename works via REST** — `PUT /rest/api/3/statuses {statuses:[{id,name,statusCategory}]}` renamed "To Do This Sprint" (id 10000) → "To Do" cleanly on a team-managed project. This contradicts the older blanket assumption that team-managed status config is UI-only (that limit holds for *notification schemes* and *quick filters*, not status names). (2) **The Agile sprint-add API rejects subtask keys** — `POST /rest/agile/1.0/sprint/{id}/issue` errors or no-ops on subtasks because they inherit the parent's sprint. Exclude subtasks from sprint-move lists; add the PARENT task instead and the subtask follows. Build sprint-assignment helpers to fall back from batch (max 50/call) to per-issue on failure so one bad key can't sink the whole batch. Reusable build script: `assistant/k2c_s3_build_2026-06-15.js` (dry-run by default, `--execute` to apply; creates issues, comments traceability, assigns sprints, renames status). Source: K2C.

### Sprint-build pattern after a playtest/standup sweep: split net-new vs in-flight, don't fragment every observation (2026-06-15, K2C)
After reading ~6 weeks of K2C playtests + sprint reviews + standups, the high-value Jira output is NOT a ticket per playtest line. The discipline that worked: (a) populate the active sprint with existing in-flight work first (query `status = "In Progress"` + the closed sprint's not-Done rollovers); (b) create net-new tickets ONLY for work with no home — new units/features/systems (Merchant, Javelin Hut, mount buff systems, boss prototyping), prominent distinct bugs (banner save/reload), and process/staffing items (art-approval workflow, sound-designer hire); (c) fold recurring tweaks into existing in-progress tasks via comment, not new tickets (e.g. javelin projectile fix → existing javelinist code task). Net result for K2C: 19 new issues, not 50. The confirmed scope split (MS2 finish vs MS3 new) is what decides target sprint per ticket — get that decision from Robert BEFORE building so each new ticket's fixVersion + sprint is unambiguous. Source: K2C.

## 2026-06-14 — Jira Advanced Roadmaps "Plans": slice a timeline by client/venue via saved views + label/component filters (BADASS)  [Tooling]
On the CUST Portfolio Board (Plan 34), the per-client timeline was achieved with a clever trick: a saved view filtered to `Label is client-engagement`, where only one "ENGAGEMENT: <client>" epic per client carries that label - so the timeline shows exactly one bar per client (the engagement length, not the tasks). Venue views are the same pattern: Filter → Label row → set to the venue (`Monaco`), then **Save as** a new view (`Venue - Monaco`). Per-single-client drill-down = **Add filter → Component → is → <client>** (clients are Jira *components*, not labels; venues are labels). Key mechanics: plain **Save overwrites** the current view - always use **Save as** for a new one; the Plan filter panel offers Details/Status/Assignee/Label out of the box and Component via "Add filter"; views are **UI-only** (no API) but shared with everyone on the plan. Caveat to set expectations: spawned location epics show as rows-without-bars until they have Start (`customfield_10015`) + Due dates, and a sparse venue (Bahamas = 1 epic) showing little is a real "barely planned" signal, not a bug. The engagement-epic-per-client model (one dated parent epic per client, labelled `client-engagement`) is the durable way to give a client a single timeline bar. Source: BADASS.

## 2026-06-14 — A Jira board named "Per <X>" may have no <X> filter at all - verify the backing JQL before trusting the name (BADASS)  [Tooling]
Board 956 "CUST - Per Location (Dubrovnik pilot)" had the filter `project = CUST AND component != TEMPLATES` - **identical** to board 954 "CUST - All", with no location dimension whatsoever. The "Per Location" name described the *intended use* (slice by venue label via swimlanes/quick-filters), not an actual filter; "(Dubrovnik pilot)" was a stale trial tag. It was a pure redundant duplicate, safe to delete (board + its filter 11055, via `DELETE /rest/agile/1.0/board/{id}` then `DELETE /rest/api/3/filter/{id}`). **How to apply:** when rationalising/auditing Jira boards, pull each board's backing filter (`GET /rest/agile/1.0/board/{id}/configuration` → `filter.id` → `GET /rest/api/3/filter/{id}`) and compare the JQLs before trusting board names - boards named for a dimension usually deliver that dimension via swimlanes/quick-filters/labels, not the filter. Confirm a board isn't a Plan issue-source before deleting it. Source: BADASS.

## 2026-06-12 — Building a Jira "Flows" automation that clones a template checklist (BADASS)  [Tooling]
Built CUST's location-spawn automation live in Jira's **newer "Flows" UI** (it renamed "rules"→"flows", "Create rule"→"Create flow → Create from scratch"). The robust design to clone a template Epic's child stories onto a newly-created Epic: Trigger **Work item created** → conditions (Work type=Epic, the template-source field not empty, Summary !contains "TEMPLATE:") → **Edit work item** to tag the trigger Epic → **Branch flow / related work items with Type=JQL** (NOT a separate "Lookup work items" action - the JQL branch both finds AND loops, making the lookup redundant) → inside the branch, **Create work item**. Two silent-failure gotchas that produce "epic saves, no children appear": (1) the branch/lookup JQL must **quote** any smart value with spaces - `"Template Source" = "{{triggerIssue.Field}}"` not bare - or it's invalid JQL matching nothing; (2) **uncheck "Only include work items that have changed since the last time this flow executed"** on the branch, or it returns the (never-changing) template stories only on the first run. Smart-value scope rule inside a JQL branch: `{{issue.*}}` = the current branched (template) item, `{{triggerIssue.*}}` = the Epic that fired the flow. Direct URL to a company-managed project's automation (skips the menu maze): `https://<site>/jira/software/c/projects/<KEY>/settings/automate`. Reach it via project automation, NOT the top-right gear→System (that's global config). Source: BADASS.

## 2026-06-12 — Automation-created issues are owned by "Automation for Jira" → deleting test artifacts needs Delete-ALL-issues, and project-lead ≠ in the Administrators role (BADASS)  [Tooling]
After testing the spawn flow, the auto-created stories had creator/reporter = **"Automation for Jira"**, so Robert (who has only delete-OWN via the permission scheme's `reporter` grant) got 403 deleting them - even though he'd just deleted the test Epic he created himself. Root cause chain worth remembering: (a) the project used the **shared "Default software scheme"** which already granted Delete Issues to the Administrators role, but (b) the CUST **Administrators project role had ZERO members** - Robert administers via site-admin, which does NOT auto-enrol him in a project's Administrators role, so the role-scoped delete grant never reached him. Fix was **adding his accountId to the CUST Administrators role** (`POST /rest/api/3/project/CUST/role/10002 {"user":[id]}`), NOT editing the shared scheme (which would hit every software project). **How to apply:** when a client/PM "can't delete" issues an automation created, don't assume the scheme is wrong - check **project role membership** first (`GET /project/{key}/role/{adminRoleId}`); an empty Administrators role is common when people admin via site-level rights. And always verify a permission scheme isn't shared before modifying it. Source: BADASS.

## 2026-06-12 — Validate a how-to by walking it from the user's actual seat in the live UI - navigation gaps are invisible to the author (BADASS)  [Tooling]
The CUST Admin User Guide's automation section was technically correct (right trigger, conditions, JQL) but Robert, building it live "from Nancy's perspective," hit a wall at almost every *navigation* step the author had taken for granted: where "Project settings" lives in the new Jira nav, gear→System landing on general config instead of Automation, the working direct URL slug being `/settings/automate` (not `automation`), the whole UI having been renamed "rules"→"flows" / "Create rule"→"Create flow", and a name+edit-permission dialog appearing only *after* "Save and enable". None of these are visible to whoever wrote the steps from memory or API knowledge - only to someone clicking through cold. **How to apply:** for any client-facing how-to aimed at a non-expert, the highest-value QA is to walk it yourself in the live UI as that user, and fix the doc **in place** (same GDoc link) as each gap surfaces - menu paths, exact button labels, direct URLs, and "the screen that pops up next". Pair it with screenshot slots. Bonus: build the thing during the walkthrough so the doc matches the real, working result rather than an idealized spec. This single session turned a "correct but unfollowable" guide into one Nancy can actually self-serve from. Source: BADASS.
