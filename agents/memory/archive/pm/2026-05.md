## 2026-05-29 — Never hand clients .md; extend already-shared GDocs in place (BADASS)  [Tooling]
Robert cannot share markdown with clients — client deliverables are Google Docs, full stop (he's corrected this more than once). And when new content belongs in a doc that's **already shared**, update that doc **in place** (same fileId/link), don't spin a new file. `gdrive-upload.js` only *creates* files; for in-place updates use the new helper `node assistant/gdrive-update-doc.js <local.md> <fileId>` — it renders the md via `md-to-html` and PATCHes the live Google Doc through Drive media update (`/upload/drive/v3/files/{id}?uploadType=media&supportsAllDrives=true`, Content-Type text/html), keeping the same shareable link. Fold the new section into the local source `.md` first, then push the whole doc. Did this for the BADASS "CUST - Admin User Guide" (added a Portfolio Board section as §7). See [[feedback_no_md_to_clients]]. Source project: BADASS.

## 2026-05-29 — Jira Plans / Advanced Roadmaps: what's REST-scriptable vs UI-only (BADASS)  [Tooling]
Building "a Plans view" splits cleanly into a scriptable data layer and a UI-only config layer — know which is which before promising a build:
- **Scriptable (REST):** the underlying issue data — `GET /rest/jpo/1.0/plans/{id}` returns the full plan config (issueSources, baselineStartField/baselineEndField, planningUnit). Create/date the issues that feed the view via the normal `/rest/api/3/issue` (or Rovo `createJiraIssue`).
- **NOT REST-exposed (UI-only):** saved **views**, **hierarchy** config, and the **dependencies display toggle**. `GET /rest/jpo/1.0/plans/{id}/views` and `/rest/jpo/1.0/hierarchy/global` both 404. So "save the view" / "turn on dependency lines" is click-work — hand it to whoever owns board hygiene (Nancy at BADASS) with exact steps, or drive it via Playwright on an authenticated session. Don't promise to script the view itself.
Plan baseline fields on BADASS Plan 34: start = `customfield_10015`, end = `dueDate`. Source project: BADASS.

## 2026-05-29 — "Client-relationship duration" timeline needs a dated parent per client (BADASS)  [Tooling]
Jira/Plans plots *issues with dates*, not *relationship spans*, so a "how long does each client engagement run" view has no native source. Pattern that works: one `client-engagement`-labelled Epic per client, summary `ENGAGEMENT: <Client>`, with Start (cf10015) + Due = the span; then a Plans view filtered to that label + grouped by Component (Client) + scale = Quarters → one clean bar per client, no task clutter (exactly what a Chief-of-Staff/investor view wants). Derive each span from the envelope (min start / max due) of that client's existing dated issues; for clients with no dated work the epic is created but its bar only renders once someone fills the two dates. Created CUST-793..797 this way. Source project: BADASS.

## 2026-05-22 — Enabling native Sprints on a new-Jira team-managed project (K2C, tooling)

Converting the K2C KAN board from simple Kanban to native Sprints. Key findings:

- **The REST features API cannot enable sprints on a new-Jira team-managed project.** `PUT /rest/api/3/project/{key}/features/{key}` with `jsw.agility.backlog` or `jsw.agility.sprints` both return `404 No such Project Feature`. The features endpoint lists 14 `jsw.agility.*` features (summary, pages, code, calendar, list_view, standup, etc.) but **no backlog/sprint feature at all** — board type is core config, not an API-toggleable feature.
- **The UI path (the only path):** in the new Jira, Backlog is a *board view*, not a settings toggle. Add the **Backlog** view via the `+` at the end of the view tabs (Summary / List / Board / Timeline / ...). Once Backlog exists, **Space settings -> Features -> Sprints** un-greys and can be toggled on. The Sprints feature card says "Requires a backlog" and stays greyed until the Backlog view is added. This is a Robert-only step — guide him to it, don't burn turns guessing API keys.
- **In the new Jira, "Project settings" is "Space settings"** — reached via the `...` next to the project/space name, not a sidebar link.
- **Sprint creation** (`POST /rest/agile/1.0/sprint`, body `name/startDate/endDate/goal/originBoardId`): sprint **names must be < 30 characters** or it 400s (`Sprint name must be shorter than 30 characters`). The backlog sequence = creation order and there is **no API to reorder sprints** — if a create fails mid-sequence, delete the sprints created after the gap and recreate them in order. Empty sprints delete cleanly (`DELETE`, 204).
- **`GET /rest/agile/1.0/sprint/{id}/issue` is board-filtered and unreliable for counts** — it showed 0 for a future sprint that actually held 15 issues, and 29 for an active sprint of 30. For ground-truth sprint membership use JQL `sprint = {id}`.
- **Moving issues into a sprint:** `POST /rest/agile/1.0/sprint/{id}/issue`, body `{"issues":[...]}`, 50 max per call, works for both active and future sprints, returns 204. Move standard issues only (Tasks/Stories/Bugs) — subtasks inherit the parent's sprint, epics don't get sprinted.
- Status and Sprint are independent fields: an issue can sit in status "To Do This Sprint" while assigned to native sprint S2. The K2C board has a legacy status column literally named "To Do This Sprint" that pre-dates native sprints and is now redundant — flag for renaming, don't change workflow unilaterally.

This supersedes the older learnings "KAN board has no sprint support" and "KAN board default status is To Do This Sprint" (2026-04-20) — as of 2026-05-22 the KAN board has native sprints. Source project: K2C.

## 2026-05-22 — Rolling-wave allocation: mirror the team's curation, don't re-plan (K2C, process)

When applying a multi-sprint plan to a live board mid-project, rolling-wave = detail the current + next sprint only, leave the rest as empty dated containers. For the **current/active sprint**, the most defensible allocation is to mirror what the team has *already* curated (here: the "In Progress" + "To Do This Sprint" issues) rather than re-deriving the sprint from the plan's focus line — the team set that scope in standups; second-guessing it is presumptuous. Exclude only the items that are *clearly* mis-placed (e.g. island tasks for milestones far in the future) and flag those for the team to groom rather than silently dropping them. For the **next sprint**, stage a first-pass set from the backlog matching the plan's focus, and explicitly label it provisional pending the next planning meeting. Source project: K2C.

## 2026-05-22 — K2C content-item subtask convention (K2C, process)

K2C now has a third epic-shape, sitting alongside the existing FEATURE epics (sibling Tasks) and CAMPAIGN island epics (5-child waterfall):

**Shape C — Content-item Tasks** (single ability / blessing / enemy variant / mount / etc., under ABILITIES / BLESSINGS / ENEMIES / MOUNTS umbrella epics):
- Parent Task = the content item (e.g. "Scepter of Khonsu", "Standard Horse").
- Three Subtasks: `<item>: design` (label `prod-design`), `<item>: art` (label `art`), `<item>: implementation` (label `code`).
- Several pre-existing items already had a single subtask holding the design spec content in the summary (e.g. KAN-149 "Reuse from base game / average stats" under KAN-148 Standard Horse). When topping these up, **leave the existing summary alone** (the spec content is useful in-place) and add the art + implementation siblings alongside. Don't rename/wipe to a generic "X: design" — you lose the content.
- Subtasks inherit the parent's Sprint, so the subtasks of a content item in S1 are in S1 automatically; backlog content items keep their subtasks in backlog.

When/why: this shape fits *content items* (one ability, one mount, one blessing) where the work is small enough to be one card with three discipline children. FEATURE epics (banner system, monarch rework) still get sibling Tasks because each discipline is substantial. Source project: K2C.

## 2026-05-21 — Hardening sprints: flex their length, keep production sprints fixed (K2C)  [Process]
When a project runs fixed 2-week sprints but contract milestone dates don't land on 2-week boundaries, don't bend the production sprints. Keep production sprints at exactly 2 weeks and make the LAST sprint of each milestone cycle a hardening sprint whose length flexes (1-2 weeks) so it ends ON the milestone delivery date. Hardening sprint = no new features, only stabilization/bug-fix/QA/cert/polish. This keeps the build rhythm predictable and absorbs all calendar slack in the one place it's useful. Knock-on: milestones that fall mid-week create small wobbles in a Friday-retro/Monday-planning cadence (retro on delivery day, planning next working day) — name those explicitly in the plan. A retro that lands on a milestone delivery day does double duty (sprint + milestone retro) — give it a longer slot. Source project: K2C.

## 2026-05-21 — Atlassian creds file key is `apiToken`, and a wrong key fails silently (K2C)  [Tools & Integrations]
`~/.claude/.atlassian-credentials.json` has keys `email`, `apiToken`, `site` — NOT `token`. Reading a non-existent key (e.g. `['token']`) yields an empty Basic Auth string, and `/rest/api/3/search/jql` then returns `{"issues":[],"isLast":true}` with HTTP 200 — a silent zero, not an auth error. Always sanity-check that the project actually has issues before trusting a 0 result. For a total issue count, `?maxResults=0` does NOT return a count on team-managed projects (returns errorMessages); POST `/rest/api/3/search/approximate-count` with `{"jql":"..."}` does. Source project: K2C.

## 2026-05-21 — Jira classic dashboard gadgets can be added via REST but NOT configured (BADASS, tooling)

You can create a dashboard and add gadgets via REST, but you cannot configure them. `POST /rest/api/3/dashboard/{id}/gadget` needs the gadget `uri` (e.g. `rest/gadgets/1.0/g/com.atlassian.jira.gadgets:pie-chart-gadget/gadgets/piechart-gadget.xml`), NOT a `moduleKey` - the classic gadgets only carry `uri`, and a moduleKey returns "module key ... not present in the directory". But gadget *configuration* (filter, stat axes, period) is UI-only: writing config via `PUT /rest/api/3/dashboard/{id}/items/{itemId}/properties/{key}` returns 201, yet the gadgets ignore it and render "This gadget hasn't been configured yet."

**How to apply:** When building a Jira dashboard via API, scope the deliverable as "dashboard created + gadgets placed" and hand the user a per-gadget UI-config cheat-sheet (which filter, which statistic). Don't promise a fully-rendered dashboard from the API. Same UI-only reality as Jira Automation rules and the cross-project bulk-move wizard. Source project: BADASS.

## 2026-05-16 — Google Docs API: insertText inherits paragraph style at boundary (BSC)

**Learning:** When using Docs API `insertText` to add content at the boundary between two paragraphs (e.g., at the `startIndex` of a heading), the new text joins the *second* paragraph and inherits its `namedStyleType`. Inserting before a HEADING_3 paragraph means the entire inserted block becomes HEADING_3 - including body text and blank lines. Same trap on the trailing side: appending after a HEADING_3 paragraph but at the next paragraph's startIndex also inherits.

**Why:** Bit me on the Equinox porting estimate - inserted a multi-paragraph Mac section before the Mobile H3 heading; everything became Heading 3. Had to do a follow-up `updateParagraphStyle` pass.

**How to apply:** When inserting via Docs batchUpdate, always follow with an explicit `updateParagraphStyle` request on the inserted range, setting `namedStyleType` to what each paragraph should be (NORMAL_TEXT for body, HEADING_X for headings). Cheaper to compute the new index range yourself than to re-fetch the doc - track the insertion length and offset. If multiple inserts are needed, do them back-to-front so earlier indices don't shift, OR split into multiple batchUpdate calls with a re-fetch between them. Helper template lives at `/tmp/edit_doc.js` from this session if needed again. Source project: BSC.

## 2026-05-16 — Inline GDoc project plan construction pattern (BSC)

**Learning:** Robert wanted a multi-section project plan with tables APPENDED inline to an existing GDoc (not as a separate linked doc). The reliable construction pattern - tested on BSC Equinox - is a 3-pass batchUpdate flow:

1. **Pass 1 - narrative**: Build the full plan content array (`{ t: 'h2'|'h3'|'p'|'tbl', text?, id? }`). Concatenate text items into one buffer with `\n` separators; emit a unique sentinel string (e.g. `<<<TBL:milestones>>>\n`) where each table goes. One insertText at end-of-body inserts everything as plain paragraphs.
2. **Pass 2 - styles**: Re-fetch the doc. Iterate paragraphs in the appended range, match each paragraph's text against the plan model, and emit `updateParagraphStyle` requests with `namedStyleType` = HEADING_2 / HEADING_3 / NORMAL_TEXT. Send in one batch.
3. **Pass 3 - tables (back-to-front)**: For each table sentinel, working from LAST to FIRST so earlier indices don't shift:
   - Re-fetch, find the sentinel paragraph.
   - `deleteContentRange` on [sentStart, sentEnd - 1] to strip the sentinel text but keep the paragraph boundary.
   - `insertTable` at sentStart with the right rows/cols.
   - Re-fetch, find the inserted table. Walk `tableRows[].tableCells[]`, collect `{idx: cell.content[0].startIndex, text, isHeader}` for each cell.
   - Sort cell inserts DESCENDING by idx. Submit as one batch of `insertText` requests - higher indices first means earlier requests don't shift later ones.
   - Re-fetch one more time, apply `updateTextStyle` with `bold: true` over the header row's cell ranges.

**Why this works:** Docs API's two main pain points are (a) insertText at a paragraph boundary inheriting the second paragraph's style, and (b) shifting indices when you do multiple inserts in one batch. Pass 2 fixes (a) by explicitly setting every appended paragraph's style. Sorting cell inserts DESC fixes (b) within a single batch. Re-fetching between major passes is cheaper than trying to compute shifts.

**How to apply:** Reference script at `/tmp/build_plan.js` (will be lost between sessions but the pattern is here). For projects that need RFM-style plans (K2C, BSC, future porting/co-dev proposals), this template covers Overview / Team / Milestones+Payment / Staffing Timeline / Workstreams / Risk Log / Comms / Alignment Items in ~3700 chars of source. ## 2026-05-09 — Modular team-unit model — full v3 structural template (BADASS)  [Session Learnings]
Codified the full shape that addresses Dieter's "team looks too services-y" investor-optics ask. Five top-level groups:
- Management (fixed)
- Marketing & Comms (own bucket — separates corporate brand from per-project marketing for investor visibility)
- Platform (relatively fixed; step-up per new project type / new platform supported, NOT per project count)
- Customisation Core (per-project Core teams instantiated from N project-type templates; each concurrent project = full Core duplication)
- Shared Services (specialist pool: art, UX, ops, client-facing roles; demand-driven for art/UX, fixed-then-step-up for ops)

Cost formula: `Mgmt + M&C + Platform + Σ(active_projects × template_cost) + scaled_shared_services + sub_overflow`

Three load-bearing rules:
1. **50% threshold:** roles >50% allocated on a single project sit in Customisation Core; ≤50% sit in Shared Services pool. Cleanest way to keep per-project Core lean without losing access to specialists.
2. **Sub overflow scales projects** (not FTE inflation) — bigger project = more subs added to Core. Concurrent projects = full Core duplication, no role-sharing across instances. Client-focus is the headline value-prop.
3. **Surplus hours flow upstream to Platform.** A 60% Customisation Team Lead has 40% available for Platform contribution. Strong investor narrative: every "Customisation" FTE also contributes to Platform, blunting the services-shop optic.

**How to apply:** Reusable for any modular team / cost-center redesign with a finance counterpart. The 7-section walkthrough (project-type taxonomy / per-template Core / Platform / Shared Services / staff retro-fit / scenarios / stakeholder choreography) was the right cognitive sequence — each section's answers gate the next. Source project: BADASS.

## 2026-05-04 — Surgical XML editing is the ONLY safe path for revising client xlsm files (BADASS)  [Session Learnings]
openpyxl `load_workbook(..., keep_vba=True)` + `save()` silently drops embedded PNG/EMF images (`xl/media/*`), most drawings (`xl/drawings/drawing*.xml`), drawing rels, calcChain, threadedComments, printer settings, and persons. For the BADASS P&L, this dropped Rosy's inline yellow text-box annotations on the 5y P&L sheet (cloud cost commentary) — load-bearing content that the file owner had carefully placed. The K2C learning already flagged client-xlsm round-tripping as risky; this is the concrete implementation answer when the user explicitly wants changes IN the file (not as a changeset doc).
**How to apply:** Open xlsm as `zipfile.ZipFile`, copy every entry verbatim to a new zip EXCEPT files you need to modify (typically: `xl/sharedStrings.xml`, `xl/worksheets/sheet*.xml`, `xl/styles.xml`, `xl/workbook.xml`, `xl/_rels/workbook.xml.rels`, `[Content_Types].xml`). Add new sheet XMLs as additions. Result: byte-for-byte preservation of everything else. Reference implementation: `skills/snippets/xlsm_surgical_edit.py` (BADASS May 4). Use openpyxl ONLY for files we own end-to-end with no embedded images/charts/annotations.
