## 2026-04-27 — Don't replace the live financial model — issue changesets instead (BADASS)  [Process]
Round-tripping a client-owned xlsm through any non-Excel tool (Google Sheets, ExcelJS, libreoffice, etc.) silently drops charts, EMF images, conditional formatting, themes, and macros. The data changes can be reconstructed; the file craftsmanship can't. Robert's working pattern: keep the file owner's xlsm canonical, deliver changes as a changeset doc (cells + new values + reasons) or a parallel Google Sheet for them to apply.
**How to apply:** When asked to "update" a client-owned financial model, default to producing a changeset doc rather than a re-saved file. Only re-save if explicitly asked.

## 2026-04-27 — Avoid mid-section row inserts in Dieter-style P&L sheets (BADASS)  [Process]
Section totals in BADASS's P&L use fixed SUM ranges like `=SUM(M6:M14)` (one per quarter column × ~70 columns × multiple sections = hundreds of formulas). Inserting a row mid-section requires rewriting every range manually — ExcelJS doesn't auto-extend SUM ranges. Overwriting an existing 0%-employment placeholder row (e.g. an "Animator" or other "Hold" role per the changeset doc) keeps formulas intact with zero edits.
**How to apply:** When adding a new role row in a P&L Staff sheet, first scan the target section for existing 0%-employment placeholder rows and overwrite one. Only insert a new row if no placeholder is available, and budget time for the SUM-range rewrites.

## 2026-04-27 — Bulk Jira migrations: split into parallel batched subagents (BADASS)  [Tooling]
For 79 issue creates, splitting into 3 parallel general-purpose subagents (21 + 28 + 30) finished each batch in ~80 seconds vs sequential. Each subagent kept its own context clean and the main session avoided 79 round-trips of API noise.
**How to apply:** Any bulk Jira/external-API operation > ~25 items — batch by ~30 and parallelize via Agent tool. Pass full data inline (PE-key + summary + type) so the subagent doesn't have to re-query the source.

## 2026-04-13 — Jira epic → milestone mapping rule (K2C, Robert's rule — REVISED 2026-04-23)  [Tools & Integrations]
**Revised rule:** assign each epic's `fixVersion` to the milestone where the epic actually **delivers** (not the milestone prior). Set epic `duedate` to the same milestone's release date so Releases page and Timeline view agree. Tasks under the epic carry their own fixVersions matching their individual delivery milestones.

**Why the revision:** the original "milestone prior" rule was useful for Releases-page scope-locking (epic appears on the milestone where its scope locks, even though it isn't built yet). But that interpretation breaks Timeline view — if `fixVersion = MS1` while `duedate = MS2`, the epic appears done on MS1's Releases page but Timeline shows the bar ending in MS2. Robert flagged the inconsistency on 2026-04-23 when reviewing the corrected campaign × MS map. For delivery-driven tracking (Timeline + Releases agreeing), align fixVersion with delivery.

**How to apply:**
- Pre-prod / process epics (PRE-PROD: Design / Art / Tech / Porting) → fixVersion MS1 (where they deliver = MS1) ✓ unchanged.
- Campaign island epics → fixVersion = milestone where the island ships playable (greybox or first-pass-art quality, whichever is the first deliverable form). For K2C: A/B → MS2, D/E/F → MS3, G → MS2 (risk-first sequencing), C → MS4 (deferred).
- Feature epics → fixVersion = milestone where the feature delivers in usable form (e.g., banner system delivers across MS2-MS3, target the milestone where the full feature is shippable).
- System / cross-cutting epics (Mounts, Abilities, Enemies, Blessings, QOL) → fixVersion where the system is feature-complete (MS3 for K2C since vertical slice is when the system stack is whole).
- Long-running epics (Porting, Polish & QA, Coordination) → fixVersion = the *final* milestone they're active in (MS6 for porting/polish, MS7 for coordination), not the first.
- Source project: K2C.

## 2026-04-23 — Sprint plan iteration pattern: ship as GDoc, take suggestions, re-version (K2C)  [Session Learnings]
When a user wants to review a sprint plan, the cycle that worked: (1) Draft the plan as markdown locally for editing flexibility. (2) Convert to HTML with native `<table>` elements and proper `@page` styling, NOT pipe-tables in MD — pipe-tables render as text in GDoc, even with `--convert`. (3) Upload via `gdrive-upload.js --convert` into the project's GDrive folder. (4) Take review via Suggesting mode (Drive Docs API can fetch suggestions inline via `documents.get?suggestionsViewMode=SUGGESTIONS_INLINE`) and comments via the Drive comments API. (5) For non-trivial structural feedback, write a new version (v2/v3) and rename the old one to "superseded by vN". Don't try to mutate the existing GDoc body programmatically — the Drive media-PATCH path returns 404 on Shared-Drive files unless `?supportsAllDrives=true` is appended to every request, and even then the conversion semantics are murky for native Google Docs. Source project: K2C.

## 2026-04-23 — `?supportsAllDrives=true` is required for ANY Drive API write on Shared-Drive files (K2C)  [Session Learnings]
Files uploaded by `gdrive-upload.js` into a Shared Drive (e.g., the K2C project folder) cannot be patched, renamed, or have content replaced via direct Drive REST calls without `?supportsAllDrives=true` (and `&supportsTeamDrives=true` for older endpoints) on the URL. Without it, the API returns a hard 404 even though the file is fully readable. Symptom: `gdrive-upload.js` succeeds (it's wrapped to support shared drives), but a subsequent `urllib.request` to the same file ID fails. Add the flag every time on direct REST calls. Source project: K2C.

## 2026-04-23 — MS1 reframe: prototypes-first, not docs-first (K2C)  [Session Learnings]
For pre-prod sprints leading up to a docs-only milestone, the higher-leverage shape is "four parallel prototype verifications + the docs stitched around them as evidence" rather than "first-pass drafts of every doc". Robert codified this on K2C v3: gameplay mechanic prototype + new-system prototype + visual benchmark + build-pipeline verification. The wins are: (a) tech risk doc anchors on real outcomes not theory, (b) MS1 client demo session is much more compelling than a doc dump, (c) team motivation is higher because they're shipping artefacts, (d) MS2 (Alpha) starts ahead because the prototypes seed the production code, (e) publisher feedback is faster because they've seen the proofs. Default to this shape for any pre-prod sprint plan. Source project: K2C.

## 2026-04-23 — Sprint structure: one full sprint + one hardening sprint locked to milestone date (K2C)  [Session Learnings]
For a 3-week pre-prod runway, structure as: 2-week Sprint A (build + first-draft) + 1-week Sprint B (demo + harden + ship), with Sprint B's last day = milestone delivery date. Critical knock-on: any client-facing draft (e.g., GDD to publisher) MUST land mid-Sprint A so feedback lands before Sprint B starts. Sprint B has no buffer for feedback that arrives late. Communicate this stagger explicitly in the plan as an MS handoff table. Source project: K2C.

## 2026-04-23 — Confluence ↔ Jira linking sweep — cleanest pattern (K2C)  [Session Learnings]
Don't link individual Jira tasks to Confluence; link only at the Epic level (Jira FEATURE / system / island / process Epics) and let tasks inherit via their parent Epic. Two-step procedure:
1. Jira side: `POST /rest/api/3/issue/{epic}/remotelink` with `globalId` set to a deterministic key (e.g., `k2c-confluence-design-{pageId}`) for idempotency. Body: `{"object":{"url":"https://...","title":"Design: <pagetitle> (Confluence)"}}`. Existing remote links can be checked with `GET .../remotelink` to skip duplicates.
2. Confluence side: prepend an `ac:structured-macro ac:name="info"` panel to the page body via `PUT /wiki/api/v2/pages/{id}` (storage format) with the Jira browse-URL as a hyperlink. Idempotency: check if the Epic key already appears in the body string before patching. Bump version number by 1.
Both endpoints use the same Atlassian API token. Pages with multiple owning epics (e.g., Platform Targets serving both KAN-4 PRE-PROD: Porting and KAN-18 PORTING) should list all owning epics in the same callout. Cadence: re-run after every spec sign-off; the sweep is idempotent so it's safe. Source project: K2C.

## 2026-04-23 — Comments + Suggestions on a GDoc — read both, but don't reply via API (K2C)  [Session Learnings]
Drive Comments API (`GET /drive/v3/files/{id}/comments`) returns anchored comments with `quotedFileContent` so you can map each comment to the paragraph it sits on. Inline suggestions (Suggest mode edits) are NOT in that endpoint — fetch via Docs API: `GET /v1/documents/{id}?suggestionsViewMode=SUGGESTIONS_INLINE` and walk `body.content[].paragraph.elements[].textRun` for `suggestedInsertionIds` / `suggestedDeletionIds`. Reply behaviour: don't post comment replies via the API when you're using user-OAuth credentials — replies will appear authored by the OAuth-token's user (Robert), which muddles the audit trail. Reply in chat instead, then update the doc body once the human agrees. Source project: K2C.

## 2026-04-23 — Cross-check Jira state against standup notes, Confluence labels, and team chat before treating it as ground truth (K2C)  [Session Learnings]
Jira lags reality. Before planning around a ticket's status, verify against: (a) the most recent standup notes (Gemini transcript or equivalent) for "we approved X" / "we decided Y" mentions; (b) Confluence Approved / Status labels on related design pages; (c) the team chat (Discord, Slack) for spec sign-offs that didn't make it into a meeting. **Why:** v1 of the K2C sprint plan had Banner / Anubis / Apesh design specs as "push to Done" tasks because Jira showed In Review. If a ticket is "stuck in In Review" for >5 days, assume it might already be approved offline and verify before scoping the work. Source project: K2C.

## 2026-04-23 — When an agent quality problem hits, ask "tooling fix or one-time?" — favour tooling (K2C)  [Session Learnings]

## 2026-04-23 — Monitor team chat (Discord, voice channels) for emerging scope, not just formal trackers (K2C)  [Session Learnings]

## 2026-04-23 — Separate sandboxes for different prototype concerns (K2C)  [Session Learnings]
When planning multiple prototypes in a sprint, default to isolated sandboxes when the concerns differ (gameplay vs art quality vs build pipeline vs perf). One shared sandbox tempts cross-contamination — gameplay prototype getting blocked because the art-bench scene refactored, or build-pipeline regressions hiding behind gameplay-prototype churn. **Why:** Robert explicitly said "art test level we keep separate for now" when the gameplay test level for STG + Banner prototypes was being scoped. Different concerns, different sandboxes. **How to apply:** at the start of any sprint with >1 prototype, ask "do these prototypes share a sandbox or each get their own?" Default to isolation when concerns differ; only share when prototypes are testing the same axis. Source project: K2C.

## 2026-04-23 — In-place updates > version bumps for distributed artifacts, unless the change is structural refactoring (K2C)  [Session Learnings]
Once an artifact (sprint plan, design doc, runbook) has been distributed to a team, prefer in-place updates with an "Updated <timestamp>" callout over spinning a new version. **Why:** Robert said "do the updates in v3, the team already have access" when I asked if I should roll v4. Bumping versions creates link rot, scatters comments across versions, and makes the team re-find the canonical artifact. Drive media-PATCH on Shared-Drive GDocs *does* work with `?supportsAllDrives=true`, so the technical capability exists — it's a UX call. **How to apply:** if the change is additive or refining, edit in place and add an "In-place update" callout near the top describing what changed. Only spin a new version when the structural rewrite is large enough that comments anchored to old text would be misleading or when the audience is genuinely new. Source project: K2C.

## 2026-04-17 — Phased playtest structure for indie co-op games (WMY)  [Playtest Planning]
For a game heading toward a Steam Next Fest with 2-3 months lead time, structure playtests in three phases with escalating audience size and telemetry depth:
1. **Friends & Family (10-20 ppl, 1 week):** Validates online connectivity + distribution pipeline. Telemetry optional — survey fallback works fine. Low quality bar = can ship early.
2. **Community Beta (50-100 ppl, 2 weeks):** Full telemetry required. This is where you get the behavioral data (mode preference, drop-offs) that shapes messaging for the public demo.

Key insight: don't block PT1 on telemetry readiness. A small manual test with survey data is infinitely better than waiting for the full analytics stack. Telemetry must be non-negotiable by PT2.

## 2026-04-16 — Game database listing verification — reliable endpoints (ToA)  [Game GTM]
When checking if a game is listed on the major DBs, these endpoints work without auth/JS and are far more reliable than WebFetch (most of these sites block the fetcher or are SPA/Cloudflare-gated):

- **Steam canonical metadata** (source of truth for all other DBs):
  `curl "https://www.protondb.com/proxy/steam/api/appdetails/?appids=<APPID>"` — returns Steam's full store payload (name, dev, publisher, genres, categories, platforms, screenshots, trailer, short/long desc, release date, prices, achievement count, supported languages). ProtonDB proxies this publicly, so it works without a Steam API key.
- **IGDB existence check**:
  `curl "https://www.igdb.com/search_autocomplete_all?q=<slug>"` — JSON autocomplete, returns game ID and URL without auth. The full page returns 403 to curl/WebFetch, so use this to confirm listing state.
- **PCGamingWiki existence check**:
  `curl "https://www.pcgamingwiki.com/w/api.php?action=query&srsearch=<title>&list=search&format=json"` — MediaWiki API, 0 hits = not listed. Also `action=query&titles=<title>&format=json` confirms page is missing.
- **ProtonDB reports**:
  `curl "https://www.protondb.com/api/v1/reports/summaries/<APPID>.json"` — 404 = no reports yet (the app page is auto-created from Steam, but the summaries endpoint only exists once at least one report is filed).
- **HLTB** and **Co-Optimus** both block scripted access (HLTB returns 404 on its search endpoint path variants, Co-Optimus is Cloudflare-gated). Confirm via DDG site-search (`duckduckgo.com/html/?q=%22<title>%22+site%3A<domain>`) — if the site-scoped query returns no `/game/` or `/games/` URL, the listing doesn't exist.
