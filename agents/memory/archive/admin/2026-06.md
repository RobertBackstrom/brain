## 2026-06-25 — Formula-driven Sheet build via node scripts (CSV→Gsheet) + gsheet-style.js is broken

**Learning (build a formula-driven Sheet without gspread):** `skills/google_sheets_auto.py` needs `gspread` which is NOT installed in `python3` (no venv) — it fails `ModuleNotFoundError`. Working path instead: write a CSV (labels + input values, computed cells left blank) → `node gdrive-upload.js file.csv <folderId> --convert` creates a Google Sheet. **Gotcha:** converting `nd_budget.csv` names the first TAB after the **filename** (`nd_budget.csv`), NOT `Sheet1`. Read it back with `mcp__gdrive__gsheets_read` (`sheetName` field) to confirm. Then set formula cells with `node gsheet-set-cell.js <id> "'nd_budget.csv'!B10==B4*(1+B5)" ...` — it uses `valueInputOption=USER_ENTERED`, so `=...` becomes a real formula and `$B$10` absolute refs work. Single-source inputs once, formulas reference them — meets db-230.

**Learning (gsheet-style.js is BROKEN as of 2026-06-25):** it posts snake_case range fields (`row_index`, `column_index`) to the Sheets `batchUpdate` REST endpoint, which requires camelCase (`rowIndex`, `columnIndex`) → `400 INVALID_ARGUMENT` on every request, so NO styling applies. Also prints "outcome cell conditional formatting (--outcome-cells) is reserved for future enhancement" — that flag is a no-op. Net: the db-230 colour-coding (white input / grey formula / red outcome) cannot be applied via this helper until DevOps fixes the field casing. The formulas/values are unaffected (those go through gsheet-set-cell). Flag to DevOps; consider a fix in `assistant/gsheet-style.js`.

**Learning (deliver links to Robert when he's away from desk):** `POST http://localhost:3777/api/discord/dm` with body `{"text":"..."}` sends a DM via the Death Board bot and reaches his phone (he keeps Discord on mobile). **Learning (Swedish music IP — no work-for-hire, must be EXPRESS):** URL 40a § (statutory employer transfer of copyright) covers **computer programs only**. Music copyright, sound-recording producer's rights, and performer's neighbouring rights do **NOT** pass to an employer by implication, even for an employee. **Learning (milestone-based EMPLOYEE pay — the LAS safeguard):** An employee's wage CAN be variable/milestone-based, but it must **NOT be made strictly contingent on a third party (the upstream client/RF) actually paying the employer** — LAS/Semesterlagen don't let you shift the business/credit risk onto the employee. ## 2026-06-10 — NEVER use `gsheets_update_cell` for numbers/formulas — it writes RAW (text). Use `assistant/gsheet-set-cell.js`

**Learning:** `gsheets_update_cell` (the gdrive MCP) writes with **`valueInputOption=RAW`**, so ANY value lands as a literal string: `"83200"` becomes the TEXT `'83200` and `"=B11*H8"` becomes literal text, not a formula. Text values are **excluded from SUM/arithmetic (treated as 0)**, so every dependent subtotal/total/margin silently computes the cell as zero. This is NOT a recalc lag (I initially misdiagnosed it as one and wasted a dozen tool calls re-reading, scratch-touching, and value-toggling — the reads were correct, the values were genuinely text). Robert spotted it: "you entered a '83200 instead of 83200."

**The fix already exists: `assistant/gsheet-set-cell.js`** — built by a prior session for exactly this. It hits `values:batchUpdate` with **`valueInputOption=USER_ENTERED`** (numbers become numbers, `=...` becomes a formula) using the gdrive OAuth creds. Usage:
`node assistant/gsheet-set-cell.js <file-id> "'<tab-name>'!H11=83200" "'<tab-name>'!I11=83200" ...`
After running it, the aggregate read-back was immediately correct (Oskar N11 456,500, margin 1,096,626) — confirming it was the write mode, not a cache.

**Praktisk implikation:** For ANY numeric or formula input cell in a Sheet, use `gsheet-set-cell.js`. Reserve the `gsheets_update_cell` MCP for **plain text labels only**. Preserve-formulas rule still holds (name only the specific input cells; never bulk-replace; never touch SUM/total/accrued cells).
