## 2026-05-29 — Dependency-free .xlsx generation on the VPS (no openpyxl/pip/libreoffice)

**Learning:** The VPS has **no openpyxl, no xlsxwriter, no pip/pip3, no node exceljs/xlsx, and no libreoffice/soffice** — so the usual "write an Excel" routes all fail. xlsx is just a zip of OOXML parts, so a minimal multi-sheet writer works with pure-Python `zipfile`: `[Content_Types].xml` + `_rels/.rels` + `xl/workbook.xml` + `xl/_rels/workbook.xml.rels` + `xl/worksheets/sheetN.xml`. Use **inline strings** (`t="inlineStr"`+`<is><t>`) to avoid sharedStrings indexing, numbers as `<v>`, and **formulas as `<f>` with no cached `<v>`** (Excel/LibreOffice recompute on open — gives the counterparty a live model). No `styles.xml` needed if you skip formatting. Reusable writer saved at `assistant/make_xlsx.py` (`write_xlsx(path, [(sheetname, rows)])`, cell = number | str | `('f','=A1+B1')`). Validated by parsing every part with minidom; **caveat — can't render-test without Excel/LibreOffice on the VPS, so ask Robert to open it once before it goes to a counterparty.**

**Praktisk implikation:** Default to `assistant/make_xlsx.py` when a counterparty wants a real Excel file (Jacob: "om du gör det i excel tar vi in den rakt av"). For files needing styling/yellow-fill/Changes Log, this minimal writer isn't enough — fall back to Google Sheet via `gdrive-upload.js --convert` then download as xlsx, or request openpyxl + libreoffice-headless from DevOps (candidate `db` ticket for VPS finance tooling).

## 2026-05-18 — Status fields trail execution; backwards-correction to reality is allowed

**Learning:** A tracker/ticket/contract status field MUST NOT be flipped forward to a state until the action that produces that state has actually been executed. Counter-example surfaced same day: `k2c_contracts_tracker.md` had 5 K2C sub rows marked "Signed 2026-04-22" when in reality the drafts were uploaded as Gdocs on Apr 22 but never sent for eSignature. Future agents reading the tracker were misled about contract state for ~3 weeks. Robert's rule: "never change a status until you executed the actual task." However, backwards-correcting (e.g., flipping a stale "Signed" to "Unsigned" because that's the current truth) IS allowed — that's repairing the record, not promising future state. Captured as `feedback_status_trails_execution.md`.

**Praktisk implikation:** When updating any tracker, ticket field, or contract registry row, write what is true *now*, never what is about to be true. If about to execute step X, mark X done when X returns success, not before. For pre-existing forward-marked statuses that turn out wrong, correct them to current reality as a stand-alone reality-correction note in the file (don't quietly flip without explaining why).

## 2026-05-18 — `_archive/` subfolder convention for superseded Gdocs in CZP legals folders

**Learning:** When a project legals folder accumulates stale Gdocs (superseded drafts, never-signed-and-now-rewritten contracts), the clean move is: create an `_archive/` subfolder via `gdrive-upload.js --create-folder`, then `--move` each stale file into it. Preserves the paper trail (file IDs and original filenames intact, just nested under `_archive/`), keeps the top level of the legals folder showing only live/active docs, and avoids the "delete vs keep stale next to live" mental load. Tried on K2C legals 2026-05-18: created `_archive/` (id `1XJ4vhk98XVLrzpOWnEQmy3TN0JN45tiO`) inside CZP legals (id `1LaDcBo8j_TvaloGJYM0aGCfbxHxMVaNh`), moved 7 stale files (5 K2C sub Gdocs + Lost Hive Gdoc + Lost Hive PDF). **Praktisk implikation:** Default convention for any project legals folder going forward. Don't rename stale files with `_DEPRECATED` suffix in-place — the suffix clutter is worse than a subfolder. Don't delete — Robert wants a paper trail. Use `_archive/` consistently across CZP projects (k2c_legals, em_legals, etc.).

## 2026-05-18 — Broker-deal contract pattern: Elias <> Cold Pixel via Robert (CZP not a party)

**Source:** Elias bizdev — Robert brokering a direct PR/marketing service contract between Elias Software AB and Cold Pixel AB. Robert's own CZP-Elias bizdev retainer is unaffected (sales scope) and the new Cold Pixel contract covers PR/marcomms (different scope).
**Category:** contracts, scope, filing, broker_deals

**The pattern:** Robert sometimes brokers a contract between two of his counterparties without being a party himself. In this case CZP is not in the money flow at all — Elias pays Cold Pixel directly, Robert just facilitated the introduction and drafts the paperwork as a value-add.

**Drafting rules for broker deals:**
1. **Robert is NOT a signatory.** Only the two counterparties sign. Don't add a "consultant" or "broker" signature block.
2. **Strip retainer/commission language** if the brokered deal isn't structurally the same as Robert's deal. Example: CZP-Elias is 28k retainer + 15% commission (sales). Cold Pixel-Elias is hourly only (PR/marketing), no commission, no retainer. Don't copy clauses that don't fit.
3. **Explicitly carve out scope overlap.** When the brokered service sits next to Robert's own engagement with the same client, Schedule A should explicitly state what the brokered party does NOT do, to prevent double-coverage and to keep Robert's commission attribution clean. E.g.: "Does not include sales/business development outreach (covered separately by Company's biz-dev engagement with Creation Zero Point Holding AB)."
4. **Notice block uses the two parties' emails, not Robert's.** kristofer@elias.audio + bibbi@coldpx.com, not robert@aurorapunks.com.

**Hourly-engagement variant (not a retainer):** When the deal is hourly with a flexible monthly budget (vs fixed retainer hours), Section 3 needs explicit clauses for both:
- §3.1 "This is an hourly engagement, not a retainer. No minimum monthly hours are owed by either Party absent a monthly scope agreed under Section 3.2."
- §3.2 MONTHLY SCOPE: "Prior to the start of each calendar month, Company and Service Provider shall agree in writing (email sufficient) on the indicative number of hours … and the priority areas of work."
- Schedule A "Engagement Model" mirrors the same language.
This is structurally different from the CZP-Elias 40h fixed retainer, even though the hourly rate is the same (700 SEK/h derived from 28k ÷ 40).

**Filing convention for broker deals:** Goes in the client project folder (`czp_projects/<Client>/legal/`), NOT under CZP-entity legals — because CZP isn't a signer. The folder convention `<prefix>_legals` (per [[feedback_czp_project_folders]]) applies to new folders, but pre-existing project subfolders named `legal` (without prefix) are kept as-is — don't rename without asking Robert.

**Workflow gate observed (avoided permission bypass):** First instinct was to share the gdoc with both external counterparties immediately after upload (Robert had said "send the gdoc for review first"). Tooling blocked this and reminded me of the contract_workflow DRAFT → APPROVE+SHARE step: share with Robert (writer) first for his skim, only then share externally with the counterparties as commenters once he says "ship it." Lock this sequencing in for any future broker-deal flow.

## 2026-05-16 — Microsoft SCoC attestation: two-stage requirement (cybersecurity contacts + legal attestation)

**Learning:** When Microsoft requires SCoC (Supplier Code of Conduct) compliance, it's a TWO-STAGE process: (1) **Cybersecurity contacts** (deadline typically ~May), due date roughly 17 days from initial notification; (2) **SCoC legal attestation** (deadline typically ~July/October), must be signed by someone authorized to sign legal documents on behalf of the company. Both are mandatory; failure to meet either deadline can result in supplier account suspension. First stage is administrative (2 contact names + details), second stage is contractual (legal attestation requiring signatory review + agreement).

**Praktisk implikation:**
- When a Microsoft SCoC notification arrives, immediately identify BOTH deadlines (contacts + attestation). Contacts deadline is urgent (~2-3 weeks). Attestation deadline is longer but non-negotiable.
- Assign contacts task to office manager / company secretary; assign attestation to whoever has authority to sign legal docs on behalf of the company (typically CEO/VD).
- For companies where the same person holds both roles, surface both requirements together so they can batch-action them.
- Check SupplierWeb to confirm which roles the person has (NVAAdmin = can assign roles; NVAContributor/ProfileManager = can complete attestation). If roles are missing, the NVAAdmin must assign them first.
- Log the deadline date prominently in the ticket and escalate if approaching without action.

**Example:** Aurora Punks Development Services AB (supplier 0003066327) received Apr 20 notification with May 7 deadline for contacts (overdue by 9 days as of May 16) and Apr 30 notification with July 29 deadline for attestation. Contacts stage appears to have been missed; attestation stage still has 74 days.

## 2026-05-13 — Runatyr — Q1 2026 momsdeklaration utan komplett bokföring

**Learning (Runatyr redovisningsperiod ändrad):** Skatteverkets registerutdrag från 2019 säger Runatyr AB redovisar moms "helt beskattningsår", men Robert bekräftade 2026-05-13 att perioden ändrats till **kvartal**. **Learning (kvartalsmoms-deadlines 2026):** Q1 = 12 maj, Q2 = 17 augusti, Q3 = 12 november, Q4 = 17 februari (året efter). Helgförflyttning gäller. Förseningsavgift 625 SEK utlöses automatiskt vid sen inlämning (Skatteförfarandelagen 48 kap 1 §). Tilläggsavgift 625 SEK efter 3 mån + 625 SEK efter 5 mån (totalt max 1 875 SEK för 1:a förseningen).

**Learning (momsdeklaration utan komplett bokföring):** När en kvartalsdeadline passerar och bokföringen inte är ifatt (typ Runatyr Bokio-arkivet tomt), bygg utkast från bank-CSV + verifierbara kortköp och presentera 3 scenarier (konservativ baseline / mellanläge / aggressivt deductible). Lämna in snabbt med konservativt scenario A för att stoppa förseningsklockan, korrigera via Skatteverkets "rättelse"-funktion när bokföringen är komplett. Bättre än att vänta 5 mån = 1 875 SEK i avgifter.

**Learning (svensk momssats per varugrupp — quick reference):**
- 25 %: standardsats (elektronik, hårdvara, programvara, professionella tjänster, restaurang för alkohol)
- 12 %: livsmedel, restaurang/catering (mat), hotell, vissa kulturtjänster
- 6 %: böcker, tidningar, persontransport, kultur (teater, konsert), idrott, friskvård
- 0 % momsfritt: banktjänster (ML 3 kap 9 §), försäkring, sjukvård, utbildning, fastighetsuthyrning utan tillval
- Marginal: begagnat (begagnatregeln, ML 9a kap) — moms beräknas på marginal, inte hela priset

**Learning (KJELL & CO, NINTENDO, COOP, BABYLON momsklassning):** Standardklassning vid Q-end utan kvittoverifiering: KJELL = 25 % (företagselektronik), NINTENDO CA = 0 % (US ehandel utan svensk moms, eller marginalbeskattat om svensk leverantör återförsäljer), COOP = 12 % (livsmedel) blandat med 25 % (övriga varor), BABYLON restaurang = 12 % (mat) eller 25 % (alkoholbar). Verifiera mot kvitto för exakt split.

**Learning (Runatyr→CZP outsourcing-avtal följs inte i praktiken):** Outsourcing-avtalet 2024-12-15 säger Runatyr ska fakturera CZP 100 000 SEK/mån (för Robot Lord Rising-arbete), men i Q1 2026 går bankströmmen omvänt (CZP→Runatyr som lån). Ingen Runatyr→CZP faktura syns i bankströmmen Q1. Detta är ett strukturproblem som behöver lösas på avtalsnivå — antingen följa avtalet (med faktura + moms varje månad) eller skriva om avtalet till noll-fakturering med lånerevers istället. Påverkar moms (ingen utgående moms om ingen faktura) + bokföring (omklassificering av flöden) + skatterätt (risk för omkarakterisering vid revision).

**Learning (Skatteverket Mina sidor momsdeklaration UI-path):** För att lämna in en kvartalsmomsdeklaration: `skatteverket.se/foretag` → BankID-inlogg → "Skatter och avgifter" → "Moms" → "Lämna momsdeklaration" → välj period → fyll i rutorna → "Skicka in". Bekräftelse via Mina sidor. Återbetalning sker till Skattekonto, kan föras vidare till Foretagskonto via "Skattekonto" → "Återbetalning".

**Learning (momsrutor — practical mapping):** Standardrutorna för en svensk AB med endast SE-försäljning + SE-inköp:
- 05: Momspliktig försäljning exkl moms (det Runatyr fakturerar)
- 10: Utgående moms 25 % (= 05 × 0,25)

Övriga rutor (06–08 EU/utland, 20–24 EU-inköp, 30–32 omvänd skyldighet) blir 0 för en helt-SE-verksamhet.

## 2026-05-13 — Runatyr — Mappstruktur korrigerad: Avtal ska INTE ligga i Moms

**Learning (mappstruktur enligt god bokföringssed — utökad):** Min initiala 4-mapps-struktur (Inkomster/Utgifter/Bank/Moms) räcker inte. ## 2026-05-07 — Deferred-pay contractor invoices: AP/Fortnox booking question

**Source:** WMY Peter onboarding — Nikola/Shosha proposed Peter works for ~€5k payable to Aurora as a deferred "invoice waiting to happen" after EA launch (wmay-020)
**Category:** accounting + contractor_onboarding
**Tags:** deferred_payment, fortnox, revenue_recognition, sv_tax, indie_contractor_patterns

When AP onboards a contractor (Peter, etc.) on a deferred-pay structure proposed by a cash-constrained client, the AP-side accounting treatment matters as much as the contract clause. Two patterns worth distinguishing:

1. **Invoice booked at delivery, payment deferred** — AP issues an invoice when the work is delivered (or at a milestone), client books it as accounts payable, payment terms = "due within X days of [trigger]". AP recognises revenue at invoice date; VAT triggers normally; AP carries a receivable until paid. This is the standard treatment and what Fortnox handles naturally — the only twist is monitoring the trigger event and chasing payment if it slips.

2. **Unbooked obligation until trigger** — no invoice is issued until the trigger event happens. AP doesn't recognise revenue, doesn't book a receivable, doesn't trigger VAT. Lower visibility on AP's books but higher risk: if the trigger never happens and there's no invoice, there's nothing for AP to claim against in a client insolvency. From an audit perspective this can also obscure a real economic relationship — a Bolagsverket / SKV reviewer may want to see why hours of work delivered are not reflected as revenue or as an accrued receivable.

**Default recommendation:** push for pattern (1) with a clear payment-terms clause tied to the trigger event. Avoid pattern (2) unless Lawyer explicitly approves it for a specific reason (e.g. revenue would otherwise hit at a tax-disadvantageous moment). Coordinate with Lawyer on the deferral clause itself before pricing the contract — see lawyer_learnings.md 2026-05-07 entry.

**How to apply:** when a client proposes a deferred-pay structure, before agreeing on the AP side: (a) confirm whether the contractor expects to be paid by AP at delivery and AP carries the receivable, or whether the contractor accepts the same deferred terms as AP (cash flows through, no AP-side bridging risk); (b) decide which Fortnox-side booking pattern applies; (c) coordinate with Lawyer on the deferral clause. Only then commit AP to the structure. Cross-link to lawyer_learnings.md and the WMY instance at `assistant/followups/wmay-020-staffing-oscar-peter.md`.

## 2026-05-05 — Google Docs API: paragraph style inheritance on insertText

**Learning:** When inserting multi-line text via `documents.batchUpdate` → `insertText`, **each new paragraph inherits the namedStyleType of the paragraph it was split from**. If you insert "Title\nLine1\nLine2\n" and then apply `HEADING_3` to the "Title" range only, all subsequent inserted paragraphs render as HEADING_3 too — they were spawned from the styled "Title" paragraph.

**Symptom on the NGC Side Events doc:** I styled only the title to H3, and Google Docs rendered the When/Where/Host/Signup body lines as H3 as well — a wall of huge text instead of a clean heading + body block.

**Fix:** Insert one paragraph at a time, applying `updateParagraphStyle` and `updateTextStyle` (with explicit `bold: false` reset) per paragraph. Insert in **reverse order** so the same `insertAt` index stays valid across iterations.

```js
for (let i = paragraphs.length - 1; i >= 0; i--) {
  await api('POST', `/v1/documents/${id}:batchUpdate`, token, {
    requests: [
      { insertText: { location: { index: insertAt }, text: p.text } },
      { updateParagraphStyle: { range, paragraphStyle: { namedStyleType: p.style }, fields: 'namedStyleType' } },
      { updateTextStyle: { range, textStyle: { bold: false }, fields: 'bold' } },
      // optional: bold a prefix range like "When:"
    ],
  });
}
```

Always **explicitly reset** bold on body lines, then bold the prefix range — leftover bold otherwise carries from the previous paragraph.

## 2026-05-01 — Invoice factoring: credit committee rejection can come same-day; clarify ongoing costs

**Context:** CZP signed an invoice factoring agreement with Prioritet Finans AB (Swedish receivables financing company, "Expansion företagare" product line) on Apr 29. Credit committee rejected it Apr 30 (same day as welcome email). Robert asked if ongoing costs would auto-cancel or require active cancellation.

**Learning:** When a financial product (credit facility, factoring, etc.) gets rejected by the provider's credit committee *after signed*, expect same-day or next-day rejection notice. The timeline: (1) pre-meeting research → (2) sales meeting → (3) agreement drafted & signed → (4) welcome email sent → (5) credit committee review (parallel, not sequential) → (6) rejection on account of credit assessment. Front-line sales (like Jessica Kemppainen) often can't influence the credit committee's decision.

**Follow-up checklist when rejected:**
- What ongoing costs (setup fees, monthly service fees, application costs) apply even after rejection?
- Are those costs automatic or do they require active cancellation? (Some providers auto-charge and require opt-out; others bill only on activation.)
- What happens to any deposits or commitments already paid?
- Is there a formal notice required to close the relationship, or is rejection enough?

**Why:** Invoice factoring and other credit products often have parallel tracks: (1) legal/sales (which moves fast) and (2) credit committee (which moves slower). Don't assume "signed = approved." Always confirm with the provider what costs survive rejection — especially recurring monthly fees, which can silently continue if not explicitly cancelled.
