**Reusable learnings (Steam automation):**
1. **Steam Guard email codes are now agent-readable** because sales@ (a Google Group) delivers to robert@ which the Gmail MCP reads. Codes land in thread; grab the NEWEST message's "Login Code". Steam reuses the same code within a short window and sends from location = "Germany" for VPS logins (vs Sweden for Robert). See [[devops_learnings]] (2026-07-10 sales@ group fix).
2. **The Steam login code field is a 5-segment box**, not a plain input — `#authcode`/`#twofactorcode_entry` are hidden backing inputs. `page.fill('#authcode')` FAILS ("element not visible"). Fix: focus the segmented box (click it) then `page.keyboard.type(code, {delay:150})`.
3. **partner.steamgames.com does NOT SSO from a store.steampowered.com login** — it's a separate domain requiring its own sign-in (account+password+Guard again). Click the blue "Sign in" button (class `blue_button`, DOM text "Sign in") to reveal the inline login form.
4. **Persistent Playwright profile** (`launchPersistentContext(userDataDir)`) keeps the partner session alive across separate script runs/turns — essential for multi-step form flows. Use `chromium-1226/chrome-linux64/chrome` executablePath (headless_shell 1228 isn't installed); require playwright from `/home/assistant/.npm/_npx/e41f203b7505f1fb/node_modules/playwright`.
5. **FATAL self-kill footgun:** `pkill -f "steam-profile"` (or any pattern matching the current command line) kills the running shell → empty logs, exit 1. Kill chrome by exact name: `pkill -9 -x chrome`. Background jobs via bare `&`/nohup get reaped when the tool call returns — use the harness `run_in_background` instead for scripts that must outlive the call (e.g., waiting on a code/captcha file the orchestrator writes).
6. **Steamworks partner-onboarding field validation is strict ASCII:** allowed chars = alpha/numeric/blank/& - , ' / # . — and it explicitly rejects non-English diacritics and "+". Concrete hits: signee name "Robert Bäckström" → must be **"Robert Backstrom"**; phone "+46704416979" → must drop the "+" → **"0046704416979"**. **State/Province is REQUIRED even for Sweden** (leave blank → errorRequiredField) — put the city/län ("Stockholm"). 7. **CAPTCHA (partner captcha.php):** downloadable via `fetch` inside the authed page context → save PNG → upscale 6x (PIL LANCZOS) → readable by vision. Charset **includes "@"** (seen twice). Wrong guess just regenerates on reload (each script run = fresh captcha), so it's low-risk to attempt; only the same-run captcha is valid (fill+submit must be one run).

### 2026-07-15 — Steam app Transfer Tool flow end-to-end + the "receiving account needs an EXECUTED SDA" gate [project: apb / apb-026]
- **Transfer Tool = `/pub/apptransfers/301411`** (visible only to an Actual Authority user). It lists exactly the org's OWN apps (self-scopes — third-party/other-org titles never appear), each a checkbox `name=appids[]`. Select → "Transfer Selected" → `/pub/initiateapptransfer/...?appids[]=...` recipient screen.
- **Recipient is specified by EMAIL, not Partner ID** — the email of an **Actual Authority** user on the RECEIVING account (for CZP 418393 that's aurorapunks_user = sales@aurorapunks.com). Effective date is a jQuery-UI datepicker (`#effective_date`, `#ui-datepicker-div`); earliest selectable = 1st of the current month (prev disabled). "Initiate Transfer" is NOT final: it emails the transferee to accept → returns to transferer to confirm → **Valve final approval**. Pending transfers show on the transferer's apptransfers page with a **"Cancel Transfer"** button (JS confirm dialog — set `page.on('dialog', d=>d.accept())`). Re-initiating mints a NEW token+transferid (grab the newest "New App Transfer Request" email).
- **Acceptance page checkboxes are `<a href="javascript:ToggleCheckbox('checkbox_legal')">` widgets** backed by hidden inputs (names `legal`, `legal2`, `legal3` = 3 required Legal Promises; `share_apps`, `share_financial` = 2 optional share-back — leave those OFF when the source entity is being wound down). Toggle via `ToggleCheckbox('checkbox_legal')`; verify the hidden input value flips to `"true"`. (Clicking the widget element twice via nested-selector matches toggles it back OFF — dedupe to the outermost widget.)
- **KEY GOTCHA:** accepting a transfer FAILS with *"your Steamworks account may not have the appropriate agreements in place to accept transfers or you aren't the actual authority and signatory"* if the RECEIVING account's **Steam Distribution Agreement is not EXECUTED**. A brand-new partner (CZP created 2026-07-13) has the SDA "signed" on its own side (shows on `/newpartner/partnersda/?agreement_type=1` with a signed date) but it isn't in the account's **Signed Agreements** list (`/pub/view/<pid>`) until **Valve counter-signs** it ("effective as of the date Valve provides notice of acceptance"). Until then, transfers can't be accepted. There's no self-serve "finalize SDA" button; it clears when Valve processes the new partner (days) or via a Steam support nudge. The transferee's Actual-Authority status is NOT the cause when the CSV shows AA=1 — it's the SDA.
- Effective-date-vs-SDA-date is a red herring: setting the effective date = the SDA sign date did not clear the error; only actual SDA execution does.

## 2026-07-13 — Post-bankruptcy mobile republish: entity + dev-account setup (Hooja / hoj / czp)
**Category:** corp structure / platform accounts / bankruptcy transition
**Tags:** APDS, konkurs, CZP-Holding, republish, Google-Play, Apple-Developer, DUNS, PlayFab, bundle-ID, MENA, publishing-vehicle

When a mobile title is delisted because its developer/publishing entity went bankrupt, republishing under a new entity is a NEW-APP flow, not a restore. Reusable playbook (deliverable: `czp/hooja_republish_entity_setup.md`):

1. **Entity choice = two-phase.** Fastest path is to reuse the SAME successor entity already chosen for the other storefronts (here CZP Holding AB, 559182-7471, VAT SE559182747101, dba "Aurora Punks") - one payee + one D-U-N-S + one tax profile across Steam/PS/Google/Apple, and it matches apb-026/apb-015. BUT loading consumer IAP/ad + third-party-IP risk onto Robert's personal HOLDING company (which holds all his equity stakes) is poor isolation. Recommend: Phase-1 publish under the holding for speed, Phase-2 spin out a wholly-owned publishing subsidiary before the vehicle scales to multiple titles / MENA revenue. Always check the holding's **verksamhetsföremål** permits operating/publishing (CZP's 2019 bolagsordning already says "mobile game development + investments," so OK).
2. **D-U-N-S is the shared prerequisite** for BOTH Google Play org accounts and Apple org enrollment. Free from D&B/Bisnode; check for an existing number first (dnb.com UPIK). Precedent: Robert got a WLBS D-U-N-S (350685539) in 2022 for Apple, Sifferrådet (Henrik) assisted. Each legal entity needs its OWN D-U-N-S.
3. **Timelines (2026, verified via web):** Google Play org verification ~5 business days after D-U-N-S+docs, $25 one-time. Apple: D-U-N-S ~5 bd from D&B + up to 2 bd for Apple to receive; org enrollment verification 2-4 weeks (legal-authority + D-U-N-S checks); $99/yr. **Longest lead = Apple Paid Applications Agreement + App Store Connect banking/tax** - nothing sells until that's green, start it the instant enrollment clears. Wall-clock to "both stores accepting a build" ~3-6 weeks.
4. **Scrutiny risk:** a director tied to recently bankrupt games entities (APDS, WLBS) can draw extra verification friction on a fresh org account. Have registreringsbevis + D-U-N-S confirmation + authority proof ready. Do NOT try to reinstate/inherit the bankrupt entity's account - build fresh (same lesson as Steam apb-026, where Valve directed app-by-app transfer to a NEW account, not a mirror-swap).
5. **New app = new bundle/package ID under the new entity's namespace, loss of all ratings/reviews/installs.** Old IDs (`com.AuroraPunks.Hooja`) tie to the terminated accounts; decide the new ID naming early (it's permanent, baked into the build). Bundle-ID change + re-sign is a GameDev task.
6. **PlayFab title** is owned by whatever Microsoft/Azure account created it (often the bankrupt entity) - needs transfer to a CZP Studio or a fresh title; may be simplest under the same MS account CZP uses for Xbox/ID@Xbox.
7. **Facts to verify before executing** (don't assume the memory): which entity ACTUALLY held the store accounts. For Hooja, a Sept 2024 Hektor mail says it was on **Aurora Punks AB's** Google Play account, not APDS - and AP AB is NOT bankrupt, so the APDS-caused-delisting narrative needs reconciling. Reconcile account-holder + real delist cause before filing.
8. **IP chain-of-title + estate assets gate publishing, not setup.** Entity/account scaffolding can proceed while the IP question (Hooja = "external client vs Own IP 50%" + music-artist license) waits on Lawyer + konkursförvaltare. No upload before that gate clears. The signed APDS-estate Asset Transfer Agreement (apb-006) is still missing from Drive - it's the doc that would carry the rights to CZP; locate via Carler before relying on the "CZP bought the assets" claim in apb-026.

## 2026-07-13 — OpenSign bevakning-batch: sign line MID-document (not last page) → extractTextAnchors across ALL pages + explicit pageNumber
**Project:** Aurora Punks / CZP (APDS-konkurs bevakningar, mål K 4429-25) | **Category:** e-signature, opensign, corpbot-tooling
